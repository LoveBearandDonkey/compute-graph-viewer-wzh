# 训练性能分析「报告形态」竞品分析与策划

> 背景：`index_v3.html` 目前是**工具形态**——IDE 三栏、多页签、点选钻取、AI 对话。
> 本文策划它的孪生形态：**报告形态**，弱交互、竖版 A4、图多于字、总分总。

---

## 0. 先定义清楚：工具 ≠ 报告

两者不是"同一内容的两种皮肤"，读者和任务都不同。这是所有设计决策的源头。

| | 工具形态（现状） | 报告形态（要做的） |
|---|---|---|
| 读者 | **跑了这次 profiling 的人**，自己带着疑问来 | **没跑过的人**：主管、隔壁团队、三个月后的自己 |
| 任务 | 排查：我怀疑 X，去验证 | 交付：告诉我结论、依据、下一步 |
| 阅读路径 | 非线性，随机跳转、反复回溯 | **线性**，从头读到尾，一次读完 |
| 信息获取 | 用户主动找（筛选/排序/hover/展开） | **作者主动给**，读者零操作 |
| 证据 | 可探索的活数据（可缩放泳道、可平移图） | **定格快照 + 标注**，"我指给你看" |
| 结束状态 | 找到了原因 | 有了一份可转发、可归档、可打印的东西 |
| 失败模式 | 找不到入口 | 读到一半不知道在讲什么 |

**一句话**：工具里是「你去找」，报告里是「我指给你看」。

## 1. 竞品分析

### 1.1 横向对比

| 竞品 | 评分机制 | 结构 | 交互度 | 最值得学的一点 |
|---|---|---|---|---|
| **Chrome Lighthouse** | 0–100 分域评分 + 顶部圆环 | 评分 → Opportunities（有收益量化）→ Diagnostics → **Passed audits（折叠）** | 弱：仅展开/折叠 | ①每条建议直接标"可省 1.2 s"，收益即排序依据；②**Passed audits 阴性结论**必须有位置 |
| **GTmetrix / WebPageTest** | A–F 等级 + 分项条 | 摘要卡 → 分项 → 瀑布图 → 建议 | 弱–中 | 摘要页把"一张主图"当结论载体：瀑布图本身就是叙事 |
| **三甲体检报告**（纸质原型） | 总检结论 + 逐项"参考区间/↑↓" | 封面 → **总检结论与建议** → 分项检查（带参考值）→ 医师签字/复查建议 | 零 | ①**参考区间**是关键：孤零零一个 31% 没意义，"31%（参考 >40%）↓"才有；②总检结论在最前，细节在后，读者可随时停止 |
| **麦肯锡式咨询报告** | 无 | Pyramid：结论先行，每页一个 message | 零 | **标题即结论**（action title）。不写"MFU 分析"，写"MFU 31%，算力三分之二时间在等" |
| **Ascend msprof-analyze advisor** | 无统一分 | 按 computation / scheduling / communication / memory 分维度列问题与建议 | 弱（HTML 表格） | 维度划分与我们的指标同源，是天然的章节骨架；但它**只有表格没有图**，正是我们的差异点 |
| **Meta HolisticTraceAnalysis** | 无 | Notebook：temporal breakdown / idle-time breakdown / kernel breakdown / comm-comp overlap | 中（notebook） | 指标口径与本项目高度重合；**每个分析就是一张标准图**，可直接对标图表清单 |
| **NVIDIA Nsight Systems** | 无 | GUI 为主，`nsys stats` 出表 + expert-system 规则提示 | 强（纯工具） | 反面参照：**几乎没有报告形态**，产出无法转发给非专家 |
| **W&B Reports** | 无 | 图表面板 + 叙述段落自由拼装 | 强（活数据） | 介于两者之间；提醒我们**别做成"能编辑的 dashboard"**，那是第三种东西 |
| **Datadog 定时 PDF** | 无 | dashboard 快照直接转 PDF | 零 | 反面参照：**把交互界面直接打印 = 图被截断、tooltip 信息全丢**。这正是要避免的做法 |
| **AWS Well-Architected Review** | 支柱风险计数（HRI/MRI） | 评审范围 → 风险清单（按支柱）→ 改进计划 → 附录 | 零 | **改进计划单列一章**，带优先级与责任；报告的终点是行动而非诊断 |

### 1.2 提炼：必抄的 6 条

1. **结论前置 + 可随时停止阅读**（体检报告 / Pyramid）。第 1 页读完就能开会；后面每一页都是"如果你还想知道为什么"。
2. **标题即结论**。章节名从名词（"指标看板"）改成判断句（"算力利用率 31%，主要卡在通信未掩盖"）。
3. **参考区间**。现有 `data-warn` 阈值（如 `overlap_ratio warn=70`）在工具里藏在 tooltip，报告里必须**印在指标旁边**。
4. **收益量化即排序**（Lighthouse）。`actions[].benefitNum` 已有，直接做"预计收益 −8.4%"的排序与条形。
5. **阴性结论要占版面**（Passed audits / 体检"未见异常"）。`r.noProblems` 现在在工具里几乎不可见，报告里应有独立一节——它证明分析的完备性。
6. **以行动计划收尾**（Well-Architected）。最后一章是排期表 + 收益/难度四象限，不是"总结一下"。

### 1.3 明确不抄的 3 条

- ❌ **不做 dashboard 转 PDF**（Datadog 式）。当前页面直接打印必然崩：泳道横向溢出、tooltip 信息丢失、暗色底吃墨。
- ❌ **不做可编辑报告**（W&B 式）。那会变成第三个产品，且破坏"归档件"的确定性。
- ❌ **不做纯表格报告**（advisor 式）。用户明确要求"图表多于文字"，表格只用于附录和证据。

## 2. 四条硬约束（把用户提的特征转成可执行规则）

### 约束 A：弱交互 —— "打印出来不丢任何信息"

这是**验收标准**，不是原则。逐条落地：

| 工具里的交互 | 报告里的处置 |
|---|---|
| 指标卡 `?` tooltip（口径解释） | 拆两处：判定语印在卡下方；完整口径进**附录 A** |
| 关键问题左右分栏 + 点选详情 | **摊平成线性章节**，每个问题一节，无需点击 |
| 问题排序下拉（严重度/收益/难度） | 作者定一种（**按收益降序**），在标题注明"按预计收益排序" |
| Timeline 可缩放泳道 | **定格快照 + 圈注/箭头/尺寸线**，配图注写清时间窗口 |
| 计算图可平移 | 只截**问题相关子图**，节点名直接标注 |
| MFU 明细抽屉 | 展开为附录里的一张拆解表 |
| 芯片型号下拉（MFU/显存分母） | 生成报告时**固化选中值**，并在图注写明"按 910B1 378.88 TF 折算" |
| Tab 页签（算子/显存/Timeline） | 变成章节；每章只保留**该章结论所需的那几张图** |

允许保留的交互只有三样：**目录锚点跳转、附录折叠、右上角"在工具中查看"深链**（屏幕可见、打印隐藏）。

### 约束 B：竖版 A4 —— 显式分页，不赌自动流式

CSS 自动分页在长表格/长问题块上一定会失控（图被切两半、标题落在页尾）。方案：

- **显式分页容器**：`.rp-page { width:210mm; min-height:297mm; }`，内容由模板按固定容量分配。
- **问题块用定容模板**：证据图固定高度、文字块设字数上限、证据表固定 Top-N（超出→附录）。保证「一个问题 = 一页或两页」，不出现半页孤儿。
- 兜底再加 `break-inside: avoid`，但不依赖它。

### 约束 C：图多于字 —— 定量目标

每页**至少一个图形元素**；正文文字**每页不超过 ~180 字**。长文本（`issue.evidence` / `impact` / `stepsRaw`）在报告里必须**结构化压缩**：

- `evidence` → 一张证据图 + 一行数字断言
- `impact` → 一个量化条（占 step 百分比）
- `steps` → 编号清单，每步一行，超 3 步折叠到"详见工具"

### 约束 D：总分总 —— 三段闭环

```
总  执行摘要（1 页）        结论 / 头号瓶颈 / 收益上限 + 健康度 + 时间去向主图
分  指标体检 → 时间解剖 → 问题逐条（每问题 1–2 页）
总  行动计划 + 阴性结论 + 附录
```

关键：**开头的"总"和结尾的"总"不重复**。开头回答"结论是什么"，结尾回答"接下来做什么、按什么顺序、做完怎么验"。

## 3. 页面清单（约 13–17 页 A4）

| 页 | 章节 | 主图 | 数据源 |
|---|---|---|---|
| P1 | **封面** | 健康度徽章（大数字 + 等级） | `title/subtitle/taskType/reportDate/meta.range` |
| P2 | **执行摘要** ★ | PHS 仪表盘 + 优化后预估对比 / **step 时间构成堆叠条** | `phs`, `summary`, `breakdown` |
| P3 | **指标体检表** | 分组横条图（本次值 vs 参考区间） | `results` + `metrics`（三层：结果/构成/结构） |
| P4 | **可信度与采集口径** | CV / 有效 step / warmup 小卡 | `metricTrustBar` 同源数据 |
| P5 | **时间去向解剖** | 泳道快照 + 关键路径标注 | swimlane 快照 + `critical_path_ratio` |
| P6 | **多卡一致性**（有 `rankStats` 才出） | Rank step 分布 + 慢卡标注 | `rankStats` |
| P7 | **算子热点** | Top-10 耗时条形 + 分类占比环 | `opStats` |
| P8 | **显存**（有数据才出） | 显存曲线 + 峰值构成 | memory-analysis 数据 |
| P9…Pn | **问题逐条** ★ | 每问题：证据图 + 影响量化条 | `issues[]`（按 `benefitNum` 降序） |
| Pn+1 | **行动计划** ★ | **收益 × 难度四象限散点** + 排期表 | `actions[]` |
| Pn+2 | **已排查未见异常** | 勾选清单 | `noProblems` |
| Pn+3 | 附录 A：指标口径与阈值 | 表 | 现 tooltip 文案 |
| Pn+4 | 附录 B：数据来源与可复现 | 表 | `meta`, `diskFileInfo` |

★ = 三个"总"的位置。**条件章节（P6/P8）无数据就整章不出**，不留空占位——报告里的空占位等于减分。

```
│  │   证据图（定高 60mm）   │  ▓▓▓▓▓▓░░░░ 18%  │  ← 图左，量化右

├──────────────────────────────────────────────┤

```

## 4. 图表清单 × 数据可得性核对

| 图 | 类型 | 数据 | 现状 |
|---|---|---|---|
| 健康度仪表盘 + 前后对比 | gauge | `phs.current/estimated` | ✅ 已有（`phsChartWrap`） |
| 分项雷达 | radar | `phs.subItems` | ✅ 已有（`subItemsChartWrap`） |
| step 时间构成堆叠条 | stacked bar | `breakdown` | ✅ 已有（`metricBreakdown`） |
| 指标 vs 参考区间 | bullet chart | `metrics` + `data-warn` | ⚠️ **需新做**（现在是 14 张卡片，报告里要合成一张 bullet 组图） |
| Rank step 分布 | dot/box | `rankStats` | ⚠️ 需新做 |
| 算子 Top-10 | h-bar | `opStats` | ⚠️ 现为表格，报告要图 |
| 分类占比 | donut | `opStats` 分类汇总 | ⚠️ 需新做 |
| 收益 × 难度四象限 | scatter | `actions.benefitNum` + `difficulty` | ⚠️ **需新做，价值最高**——一张图讲清"先做什么" |
| 泳道快照 | 静态 SVG | swimlane 数据 | ⚠️ 需新增"导出定格 SVG"能力 |
| 显存曲线/峰值构成 | line/donut | memory 数据 | ⚠️ 现为 **canvas，打印会糊，需转 SVG** |

> **关键技术决定：报告里所有图用 SVG，不用 canvas。** canvas 按 CSS 像素栅格化，打印/缩放必糊；SVG 矢量输出到 PDF 是清晰的。现有 `memoryTrendChart` / `memoryCompositionChart` 是 canvas，报告态需要独立的 SVG 渲染分支。

`difficulty` 目前是中文字符串（"低/中/高"），做散点前需要一个映射表，建议在渲染层做，不改 parser。

## 5. 与工具形态的关系：同源双出口

```
        report.md
            │  parseReport()
            ▼
        r（唯一数据对象）
       ╱             ╲
  renderTool(r)   renderReport(r)     ← 新增
  index_v3.html   report.html
   探索/钻取         线性/归档
       ╲             ╱
        「在工具中查看 →」深链（屏幕可见 / 打印隐藏）
```

- **报告不是终点，是入口**：每章右上角一个小链接跳回工具对应页签并定位（如 `index_v3.html#issue=3.2`）。打印时该链接以脚注形式降级为"详见 PTO 工具 问题 3.2"，不留悬空箭头。
- **工具加一个出口**：标题栏加「导出报告」→ 新窗口打开 `report.html?src=<报告id>`。
- **parser 不改**。报告形态只消费 `r`，不新增解析字段；缺字段的章节整章隐藏。这保证老报告 md 照样能出报告。

## 6. 技术方案

**新文件**（不改 `index_v3.html` 主体）：

```
AI_Profiling_Tool/
  report.html          报告页外壳 + 页面模板
  report.css           A4 版面 + @page + @media print
  report-render.js     renderReport(r)：r → 页面序列
  report-charts.js     报告专用 SVG 图表（bullet / scatter / donut / h-bar）
```

复用：`app.js` 的 `parseReport()`（需抽出为可独立引用，或 report.html 直接引 app.js 并用 `PTO_DISABLE_NAV_AUTOLOAD` 之类的开关跳过工具初始化）。

**版面 CSS 骨架**：

```css
@page { size: A4 portrait; margin: 16mm 15mm 18mm; }

.rp-page {
  width: 210mm; min-height: 297mm;
  padding: 16mm 15mm 18mm;
  background: var(--surface-1);
  break-after: page;
}

@media print {
  :root { color-scheme: light; }          /* 报告固定浅色，不跟随暗色模式 */
  .rp-page { box-shadow: none; margin: 0; }
  .rp-screen-only { display: none !important; }   /* 深链、返回顶部等 */
  * { -webkit-print-color-adjust: exact; print-color-adjust: exact; }
}
```

**设计系统合规**：颜色/间距全部走 `vendor/pto-design-system/tokens/*`。泳道快照复用 `patterns/swimlane-task`，图表色板与 Timeline 图例同源（计算绿 / 通信蓝 / 空闲灰）——跨形态语义一致是这份报告可信度的一部分。

若 A4 页壳复用价值确认，**建议沉淀为新 pattern `report-a4-page`**（当前 `patterns.json` 里没有报告类 pattern），含页眉页脚、页码、定容内容槽。

**导出 PDF**：直接用浏览器打印（Ctrl+P → 另存为 PDF），不引 jsPDF / html2pdf——它们对 SVG 和中文字体的处理反而更差。

## 7. 三种落地形态，推荐哪个

| 方案 | 说明 | 优 | 劣 |
|---|---|---|---|
| **A. 纯打印页** | 只为打印优化，屏幕上就是一叠 A4 | 最像 PDF | 屏幕阅读体验差（左右留白浪费） |
| **B. 长滚动 + 打印自动分页** ✅ | 屏幕上连续滚动 + 目录侧栏，打印时按 `.rp-page` 分页 | 一套代码两种态；屏幕/PDF 都好用 | 需要同时调两套版面 |
| **C. 幻灯片式 16:9** | 每页一屏，翻页阅读 | 适合评审汇报 | 不是 A4，与"竖版"要求冲突 |

**推荐 B**。理由：报告的实际消费场景八成是"在浏览器里被转发的链接"，两成才是真打印 PDF；B 两个场景都覆盖，且 A4 容器在屏幕上也能提供"这是一份正式文档"的心理暗示。C 可作为后续的"汇报模式"另开一档，不在本期。

## 9. 三个需要拍板的问题

1. **报告谁生成？** 用户在工具里点"导出"（前端实时渲染）还是 skill 侧产出静态 HTML 归档？前者简单，后者才真正可归档（不依赖 md 源文件还在）。
2. **泳道快照怎么来？** 用当前视口截图，还是报告侧按问题时间窗口重新渲染一段定宽 SVG？后者质量高得多，但要给 timeline 渲染器加一个"无交互定宽输出"模式。
3. **单卡 vs 多卡报告是同一模板吗？** 现在 `taskType` 已能区分六种（单机单卡/单机多卡/多机多卡/RL/推理/集群）。建议**同一模板 + 条件章节**，而不是六套模板。
