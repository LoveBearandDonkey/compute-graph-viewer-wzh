# 两份 Level2 诊断报告对比结论（20260610 vs 20260526）

> 对象：`level2_profiling_analysis_20260610/report.md` 与 `ascend_analysis_20260526/report.md`，二者用同一份 `level2/`（PP=2 / DP=2 / TP=1，单机4卡 device 0/1/4/5，step13）profiling 数据、同样调用 AscendProfKit 由 Opus 分析。
> 关联背景：`ascend_analysis_20260526/report_comparison_20260526_vs_20260605.md`（526 vs 605 对比）。本份延续其口径。

---

## 一句话结论

**两份报告的"头号问题"完全一致、不矛盾**——都判定为 **PP 流水级间负载不均**（末级 rank2/3 比首级 rank0/1 多算 ~169ms）**叠加零计算通信重叠**（Overlapped=0），单步 ~810ms、无慢卡（极差 0.17%）。

真正"相差"的是 **健康度评分（49 vs 63）、lm_head 根因定性、以及次要问题的深度**，而这些差异**几乎全部来自"工具链可用性 + 评分口径"，不是底层数据打架**。

**就证据可信度而言：0610 那份更准、更可信**——它相当于把 0526 升级到了 605 的工具水平（`msprof-analyze` / `advisor` 真的跑通了），所以判断更接近 605，只是评分口径又和 605 不同，绝对分落点居中（526=63 / 610=49 / 605=36）。

---

## 1. 最根本的差异：工具链通了 vs 没通

这是后面所有差异的总根因。

| 维度 | 526 | 610 | 说明 |
|---|---|---|---|
| `msprof-analyze` | ❌ Windows 上 python/sqlite3 跑不起来，**纯手算 CSV/JSON** | ✅ **跑通**，落地 10 个 recipe | 见各自 §5 "Advisor 状态" |
| advisor | ❌ 失败 | ✅ 对末级 rank2 跑通 | — |
| 拿到的派生指标 | 仅 `per_rank_summary` + `op_diff_r2_vs_r0` | cluster_time_summary / compute_op_sum / hccl_sum / communication_time_sum / cann_api_sum / freq_analysis / slow_rank + advisor Roofline | 610 多出一大批 |

- **526**：报告自述工具链是瘸的，只能从 CSV/JSON 手算 `op_diff`。诚实，但证据链单薄。
- **610**：`msprof_analyze/<mode>/` 与 `advisor/rank_2/` 均实际产出，因此拿到了 526 拿不到的派生指标。

> 这与 605 相对 526 的升级是**同一回事**——环境从"瘸腿"变"可用"。

---

## 2. lm_head 根因被纠正：tiling 猜测（526）→ memory-bound 实测（610）

- **526 §3.2**：猜 `MatMulV3 MIX_AIC` 是 **tiling 非最优 / MIX_AIC 兜底**，建议 vocab padding 到 32 倍数、cast bf16 改走纯 AI_CORE——**纯假设，无实测支撑**。
- **610 §3.1**：用 advisor 把 `Cast/Exp/Sub/RealDiv/Mul 4096,1,151936` 判为 **`vec_mte2_mte3`（访存）bound**、词表投影 `MatMulV3` 判为 **`mte2` bound**，证明真正瓶颈是 **MTE2 搬大张量的内存带宽受限（memory-bound）**，不是 tiling。修复方向因此变成**融合 CrossEntropy 省 HBM 往返**，而非调 tiling。

**610 正确**，与 605 当初纠正 526 的点完全一致。**526 的"tiling"那条结论不应采纳。**

---

## 3. 健康度评分 49 vs 63：评分口径不同，不是数据矛盾

两份的**计算子项数值一样（都是 39% 占用率代理）**，差在评分框架：

| 子项 | 526（63分/B+） | 610（49分/B） | 差异原因 |
|---|---|---|---|
| 场景/权重 | 集群慢卡场景：计算0.222 / 通信0.333 / 调度0.333 / 均衡0.111 | 大模型训练默认：**计算0.444** / 通信0.333 / **调度0.222** /（无均衡） | 610 计算权重翻倍 |
| 计算 | 39 | 39 | 一致 |
| 通信 | 65 | 63 | 基本一致 |
| **调度** | **82**（= 1 − Free/step） | **50**（=(compute+transmit)/step） | **口径根本不同** |
| 均衡 | 46（有这一维） | 无 | 610 删掉 |

两个拉分点：

1. **调度从 82 掉到 50**：526 只用"1 − 空闲/总时"，**没把 bubble 等待算进调度**；610 把"末级有效占比"当调度，**等于把 PP bubble 又罚了一次**（计算已因 bubble 被压低，调度再扣一遍）——这正是基准文档批评 605 的"对同一个问题罚两遍"。
2. **计算权重 0.222→0.444 翻倍**：计算 39 是最低子项，权重一翻，整体被拖得更狠。

> **结论：526 的 63 偏乐观、610 的 49 偏悲观（调度双重扣分），两个 PHS 绝对分都不要当成可比硬指标。** 真实健康度落在 **49~63 之间**。
> 三份横向看：605 用 MFU=7% 当计算项→36（最悲观）；610 用占用率 39%→49；526 权重最轻→63。**610 居中。**

## 4. 次要问题：610 因有 advisor，多挖也多挪了几条

**610 新增（全靠 advisor / 派生指标）**：

1. §3.5 动态 shape `NonZero` 触发 host 强制同步 + `ACLNN_CACHE_LIMIT` / `HOST_CACHE_CAPACITY` 未设。
2. §3.7 AI Core 频率 1650MHz（疑 throttling）。
3. §3.4 micro-batch 偏少放大 PP warmup/cooldown bubble。

**判断分歧（同一现象、两份不同定位）**：

- **HCCS 带宽**：526 §3.4 列为 **P1 行动项**（利用率 62%、建议合并大包）；610 **降级到 §4「已确认无问题」**，认为带宽中等但不是瓶颈（瓶颈是暴露与等待）。这是一处真实判断差异，倾向 610——该项被 PP wait 掩盖。
- **ApplyAdamWV2**：526 §3.6 当"单实例 3.68ms 突发"（→ 分布式优化器分片）；610 §3.6 当"亲和 API 未用"（→ 换 `NpuFusedAdamW`）。angle 不同，量级都小（P2）。

**610 反而漏了的**：

- 605 当初用 `hccl_sum` 发现的**共享词嵌入 allReduce 错位**（rank2 121ms vs rank0 34ms，同 622MB），610 虽然也有 hccl_sum，**报告里未体现**。若要与 605 完全对齐，这是可补查的点。

## 6. 实操建议

1. **照 610 干活**，但把它的 **PHS=49 视为"偏悲观下限"**、526 的 **63 视为"偏乐观上限"**；瓶颈定性两份都对。
2. **两个 P0 动作**（两份共识）：
   - **PP 重新分层**：末级少放 1–2 层 Transformer，补偿 LM-head + loss + 输出嵌入的额外开销，目标两级 computation 均衡到 ~315ms。
   - **打开通信-计算 overlap**：`--overlap-grad-reduce` / `--overlap-param-gather`（当前 Overlapped=0）。
3. **526 中"LM Head MatMul 是 tiling 问题"这条不要采纳**，按 610 当 **memory-bound** 处理：融合 CrossEntropy 免一次性物化 `[4096,151936]` fp32 中间张量 / 对 vocab 维开 TP 切分 / bf16 权重免 Cast。
4. 额外跟进 610 §3.5（动态 shape NonZero 同步）与 §3.4（micro-batch 偏少）；并**补查 605 §3.4 的共享词嵌入 allReduce 错位**在本数据是否存在（610 漏报）。
