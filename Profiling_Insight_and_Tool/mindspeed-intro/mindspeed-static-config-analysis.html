01 / Concrete rule counterexamples

人有我优：总量规则之上，
再检查算法真正需要的约束。

下面不是概念示意，而是当前 Demo 已落地的公式。每个案例都展示一个“常见规则能通过、细分算法会失败”或“同一配置因框架口径不同而结论不同”的反例。

R01 · MINDSPEED ULYSSES CP已实现

Head 能被 TP 整除，仍不代表 Ulysses 合法

Ulysses 会在 TP 之外继续按 CP 拆分注意力头，因此校验因子不是 TP，而是 TP×CP。

heads=24 · TP=4 · CP=4 通用：24 % 4 = 0 → 通过 Ulysses：24 % (4×4) = 8 → 拒绝 MINDSPEED_ULYSSES_HEADS_DIVISIBLE_BY_TP_CP

优势：从“并行度可乘”深入到“算法切分单元可落地”。

R02 · MINDSPEED RING CP已实现

序列能被 CP 整除，仍可能不满足 Ring

Ring 口径需要序列长度被 2×CP 整除；只查 seq % CP 会漏掉半环切分问题。

sequence=4098 · CP=2 通用：4098 % 2 = 0 → 通过 Ring：4098 % (2×2) = 2 → 拒绝 MINDSPEED_RING_SEQUENCE_DIVISIBLE_BY_2CP

优势：不是把 CP 当一个数字，而是识别 CP 算法。

R03 · DYNAMIC PIPELINE已实现

62 层不能均分 8 个 Stage，但可以合法动态分层

简单规则只会报 62 % 8 != 0。MindSpeed-LLM MCore 动态 PP 允许非均匀分层，但必须同时满足列表长度、层数总和、Profile 与 VPP 互斥关系。

layers=62 · PP=8 · VPP=1 uniform：62 % 8 != 0 → 拒绝 dynamic：[8,8,8,8,8,8,7,7] → 长度=8、总和=62 仅 mindspeed-llm-mcore Profile 接受

人无我有式差异：不是更苛刻，而是能表达合法的非均匀解。

R04 · FRAMEWORK PROFILE已实现

同样的 62 层分配，不同框架不能混用表达法

MindSpeed-LLM MCore 使用 num_layer_list；MindFormers offset 使用 VPP×PP 矩阵。当前核心会先校验 Profile，再校验矩阵形状与每个虚拟 Stage 是否为正整数。

MCore：[8,8,8,8,8,8,7,7] MindFormers：offset [[0,0,0,0,0,0,-1,-1]] 把 list 套到 MindFormers，或把 offset 套到 MCore → 拒绝 差异显式返回，不静默选择框架口径

优势：把“公式是否正确”提升为“公式对这个框架是否正确”。

R05 · EP DOMAIN SEMANTICS已实现

EP 是否进入 World Size，不能一概而论

当前核心显式建模三种 EP 口径。相同的 DP=2、TP=4、EP=4，在不同域语义下会得到不同合法性和 Rank 公式。

split：DP % EP = 2 % 4 → 不合法 mf：(DP×TP) % EP = 8 % 4 → 合法 orthogonal：EP 进入 world；其余两种不进入 world = DP×PP×TP×CP×(orthogonal ? EP : 1)

人有我优：避免把某个框架的 EP 公式冒充行业统一真理。

R06 · MOE COHERENCE已实现

Rank 乘积正确，也可能是自相矛盾的 Dense / MoE 配置

模型没有路由专家时，EP 必须回到 1、Top-K 必须为 0；有专家时，还要检查专家数能否被 EP 整除、Top-K 是否超过专家总数。

routed_experts=0 · EP=4 · top_k=2 仅看 world size：可通过 Dense 语义：EP != 1 且 top_k != 0 → 两项拒绝 Expert FFN / TP 仅在专家张量并行开启时检查

优势：检查字段之间的状态一致性，而非孤立检查数值范围。

数量不是更多

05 / Ascend affinity audit

更亲和昇腾、HCCL、CANN？
也用输入与结果说话。

已实现能力给出可复算案例；只有经验系数的标“部分实现”；当前契约尚不能表达的 CANN 版本关系明确标“尚未实现”。

已实现 · MindSpeed CP

案例：同样 CP=2，Ring 比普通切分多一层约束

规则直接抽取自 MindSpeed arguments.py，不是通用 Megatron 维度乘积的改写。

sequence=4098 · CP=2 · algo=ring 普通切分：4098 % 2 = 0 MindSpeed Ring：4098 % (2×2) = 2 → 拒绝 诊断码：MINDSPEED_RING_SEQUENCE_DIVISIBLE_BY_2CP

同类已实现：Ulysses 还会检查 heads % (TP×CP)。

已实现 · MindSpeed-LLM PP

案例：62 层在 PP=8 下不是只能判失败

MindSpeed-LLM MCore 动态 PP 能表达非均匀 Stage；核心同时检查列表长度、总和、Profile 和 VPP 互斥。

layers=62 · PP=8 · VPP=1 均匀 PP：62 % 8 != 0 动态 PP：[8,8,8,8,8,8,7,7] → 合法 Profile：mindspeed-llm-mcore

价值不是“更宽松”，而是准确表达 MindSpeed-LLM 已支持的合法配置域。

部分实现 · HCCL 容量预留

案例：并行域越多，通信预留越高

当前理论容量按活跃通信域计入 HCCL buffer，并对 EP 额外增加一个通信域；系数为每域 0.2 GiB×2。

TP=4 · PP=8 · DP=2 · CP=2 · EP=4 活跃域 5 个 + EP 额外域 1 个 = 6 communication reserve = 6×0.2×2 = 2.4 GiB / Stage 输出位置：reserve_parts_gib.communication

这是可复算的理论预留，不是 HCCL 算法、拓扑或版本校验。

部分实现 · 显存容量

案例：卡容量会改变风险等级，卡型号暂时不会

估算器使用 card_memory_gib 计算占用比例和 80% / 88% 阈值，但尚未根据卡型号自动带出带宽、算力或特性约束。

假设某 Stage 理论总量 = 48 GiB card_memory=64 GiB → 75% · normal card_memory=32 GiB → 150% · over 只改 910B / 910_93 名称 → 当前校验结论不变

因此它是“容量参数亲和”，还不是“卡型规则亲和”。

尚未实现 · CANN

案例：当前无法判断版本组合是否兼容

稳定输入契约尚无 CANN、驱动、torch_npu 版本字段，也没有算子特性与版本的兼容矩阵。

CANN=A · torch_npu=B · MindSpeed=C 当前：无法表达 → 不产生兼容性诊断码 目标：版本字段 + 特性矩阵 + 来源版本

这里没有“已实现案例”可展示，页面不把源仓知识冒充当前能力。

待抽取 · 昇腾专项规则

上游已经有证据，当前核心还没有落地

MindSpeed Auto Settings 已按设备类型裁剪 CP 搜索；arguments.py 还包含 MC2 / CoC、Ampipe、Hybrid CP 与自适应 HCCL buffer 等关系。

910B / A2G：单卡 CP 序列低于 8K 时裁剪 910_93：单卡 CP 序列低于 4K 时裁剪 当前 Demo：尚未实现，未分配稳定诊断码

进入 config-core、补齐来源引用和 Golden 测试后，才会改标“已实现”。

06 / Rule inventory

以及下一批待实现规则。

清单直接依据当前 validate-parallel-config.js。已实现项均有稳定代码；待实现项只列规则族，不提前伪造诊断码。

诊断码 ≠ 严格意义上的“规则条数”

诊断码是稳定输出标识：可以对应硬约束、Profile 兼容差异或告警。同一个能力族常拆成多个判定，例如动态 PP 分别检查“需要列表、列表长度、层数总和、Profile、与 VPP 互斥”。因此页面报告 27 个诊断码，而不包装成 27 条彼此独立的算法定律。
