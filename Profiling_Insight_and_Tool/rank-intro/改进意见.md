本文只讨论主流的 TP / PP / DP / EP 组合，并采用“EP 从 DP 域中切出”的口径，暂不考虑 CP、SP 以及其他特殊切分方式。在这个口径下，DP 是配置里的数据并行度，EDP = DP / EP，EDP 才是一套完整专家模型的副本数。

讨论激活时，首先要区分“层间边界激活”和训练时为反向保存的各种中间激活。这里主要讨论前者：对连续的 Transformer Layer，Layer 输出通常可以抽象成形状为 [B, S, H] 的 hidden state，其存储大小由形状和数据类型决定，与张量中的数值大小无关。因此，在模型结构不变的重复层之间，边界激活的逻辑大小通常相同。

讨论一个 Layer 时，还要区分“同名 Layer 集合”和“Layer 实例”。例如模型有 46 个 Layer，每个 EDP 副本都有自己的 Layer0 和 PP Stage0。所有 EDP 中的 Layer0 合在一起，是同名 Layer 集合；某一个 EDP 中的 Layer0，才是一个具体的 Layer 实例。

在实际执行中，每个 EDP 是一条相对独立的完整流水线。不同 EDP 不需要等到彼此完成 Layer0，才继续执行 Layer1；PP Stage 之间的激活传递也只沿同一个 EDP 内部的流水线发生。不同 EDP 之间不交换前向激活，它们的主要同步发生在反向阶段的梯度归约，并且必须在对应的权重更新前完成。实现上梯度归约可以与反向计算重叠，不必理解为等所有反向计算完全结束后只做一次通信。

一个 EDP 内部包含 EP 个专家并行位置。对于普通的 Attention、Norm 等部分，每个数据流主要由对应的 TP ranks 协同计算；进入 MoE 模块后，token 会在同一个 EDP 内的 EP ranks 之间执行 dispatch，专家计算完成后再 combine 回原来的数据流。因此，EP 改变的是 MoE 层内部 token 的临时分布，不应把 Layer 输出长期画成彼此独立的 EP 激活分片。

PP 负责把不同 Layer 放到不同 Stage，并在 Stage 边界传递激活，不切分单个 Layer 的激活张量。DP 表达不同的数据流，EDP 表达完整专家模型的副本；它们都不是把同一份激活切成几块。TP 会影响 Layer 内部张量和计算的分布，但具体哪些激活被切分、哪些在通信后恢复完整，要以算子的 TP 布局为准，不能简单理解为所有激活都被 TP 均匀切开。

讨论权重时，TP 通常切分 Linear 等大权重，但 Norm、Router 等小权重可能在 TP 组内复制。EP 是把不同专家分配给不同 EP ranks，每个专家的权重仍是完整专家权重，而不是由 EP 再切成多片。不同 EDP 上对应的权重是逻辑相同、物理独立的副本，通过梯度同步保持数值一致。在常规均衡配置下，同类 rank 的权重存储量通常接近。

因此，DP × Layer 画布应先表达 EDP 的独立性：外层按 EDP 分成多条完整流水线，每条流水线内部再展示 PP Stage、Layer、EP 和 TP ranks。选择某个 Layer 时，应明确区分“某个 EDP 中的 Layer 实例”和“所有 EDP 中的同名 Layer 集合”；默认查看实例层，只有在做跨副本比较时才选择同名 Layer 集合。

## “8-内存分配”页承接 Infra 观测的业务分析

“8-内存分配”页目前已经把一个 step 内权重、梯度、优化器态、激活、临时区/碎片预留的变化，以及它们与前向、反向、更新阶段的关系讲清楚。若继续承接实际业务数据，页面的定位应从“解释一个 Rank 的显存组成”扩展为一条诊断路径：**先在全 Rank 视角发现异常卡，再锁定异常时刻和 step 阶段，然后判断问题属于真实业务占用、异步延迟释放、内存池空闲、进程级额外保留还是碎片，最后下钻到算子、流、调用栈和内存块。**

有三个统一口径需要先明确：

1. 算子分配、算子持有、算子保留、进程保留是不同层级的存量曲线，**不能相加**。同一时刻的峰值也不一定由同一个算子事件产生。
2. 差值只应在同一 Rank、同一设备、同一时间轴、同一组件口径下计算。尤其算子分配/保留可包含 PyTorch 与 GE，而算子持有依赖流信息；没有先按组件对齐时，直接相减可能得到没有业务意义的结果。
3. 当前页面里的数据是用于解释概念的确定性合成数据。它适合承载诊断交互和解释框架，但要输出生产结论，必须接入实际的 `memory_record`、`operator_memory`、step marker、流、内存块和调用栈数据。

### 一、内存峰值分析：峰值由谁构成，是否真的必须占用

峰值分析不是只找一条最高曲线，而是回答三个连续问题：**峰值发生在哪个 step 阶段、峰值由哪一层内存抬高、其中哪部分可被优化。**四条曲线可理解为四个观察层级：

- **算子分配（Operator Allocated）**：算子当前逻辑上已分配、仍在使用的内存，主要反映模型张量、激活、梯度、优化器临时量和 workspace 对真实业务容量的需求。
- **算子持有（Operator Activated）**：流仍持有的内存；其中可能包含已经逻辑释放、但由于其他流仍在使用或事件尚未完成而不能回到池中的块。
- **算子保留（Operator Reserved）**：框架/GE 已向设备取得并留在内存池中的内存，既包括正在使用的块，也包括可复用但尚未归还设备的空闲块。
- **进程保留（APP Reserved）**：整个进程在设备侧保留的内存。它还可能覆盖通信库、运行时、图执行器、自定义算子等未完全归入算子曲线的部分。

因此，生产页面应在峰值时刻 `t*` 同时展示四条曲线的值、相邻事件的增量、step 阶段和 Top 算子，而不是把四个数做堆叠。容量风险也应同时看峰值绝对值、距 HBM 上限的安全余量，以及该峰值是否跨多个 step 稳定复现。

|---|---|---|---|
| 算子分配在前向阶段随激活累积上升，并在反向阶段按相反顺序下降；多步峰值稳定 | 峰值主要来自正常激活生命周期，是模型、序列长度、MBS、流水线在途微批共同决定的真实业务占用 | 评估 activation checkpoint/recompute、缩短序列或 MBS、减少在途微批、调整 PP；用吞吐损失与显存收益共同决策 | 现有 step 周期、激活详情、in-flight 微批和 PP Stage 视图可直接解释峰值为什么出现在该阶段；接入真实曲线后可把 `t*` 游标同步到对应 Layer/算子 |

### 二、GAP 分析：延迟释放与内存池空闲分别浪费在哪里

GAP 分析的业务目的，是把“算子保留很高”拆成两个性质不同的问题：**内存已经不再由当前算子逻辑使用、但仍被流持有；内存已经回到池中、但处于空闲。**在组件口径已对齐且存在流信息时，可采用以下解释性指标：

- 延迟释放量：`Delayed(t) = max(Operator Activated(t) - Operator Allocated(t), 0)`。
- 内存池空闲量：`Idle(t) = max(Operator Reserved(t) - Operator Activated(t), 0)`。
- 延迟释放最大占比：`max_t(Delayed(t) / Operator Reserved(t))`。
- 内存池空闲最大占比：`max_t(Idle(t) / Operator Reserved(t))`。

最大占比必须同时带出**发生时刻、绝对 GB、持续时间和所在 step 阶段**。只看百分比会放大低水位时的瞬时尖峰；生产排序更适合把最大值与 `字节 × 持续时间`（byte-time）并列。若缺少 Activated/流信息，只能得到 `Reserved - Allocated` 的合并 GAP，不能再强行拆成上述两类。

| 观测现象 | 诊断结果 | 下一步操作 | 可以用“8-内存分配”页做什么 |
|---|---|---|---|
| 延迟释放占比只在跨流同步边界出现窄尖峰，随后快速归零，且不抬高 step 峰值 | 正常异步执行窗口；逻辑释放早于设备真正完成使用，不一定需要优化 | 记录为基线，关注绝对 GB 和持续时间；只有在放大峰值或拖慢下一次复用时才处理 | 在周期时间轴上把这段画成“待流完成”的斜纹层，并显示逻辑释放→实际释放的时间差，帮助用户区分异步语义与泄漏 |
| 延迟释放在多个算子之后长时间维持高位，直到 step 尾或全局同步才下降 | 某条慢流、事件依赖或跨流复用链阻止内存回池；同步点可能同时成为性能木桶 | 按 Stream 排序延迟释放 byte-time，定位最后访问者和 Active Release Time；联查长尾 kernel、事件等待与不必要的 stream 切换 | 选中 GAP 最大区间，点亮对应 Rank、流和算子链；把“谁申请、谁最后使用、谁阻塞释放”串成一条因果链 |
| 内存池空闲占比在首个 step 上升，后续稳定且空闲块在相同阶段反复复用 | 分配器预热与缓存命中，属于用空间换取减少设备 malloc/free 的正常策略 | 不因空闲比例高就立即清池；比较后续 step 的复用率、设备申请次数和吞吐 | 用多 step 叠加图区分“首步预热”和“持续浪费”；当前单 step 页面可先展示池空闲从何阶段形成、下一阶段是否被重新占用 |
| 内存池空闲长期高位、复用率低，且存在大量尺寸不同的小块 | 动态 shape、频繁变长序列、workspace 尺寸抖动或池策略造成低效缓存，并可能继续演化为碎片 | 按尺寸区间和生命周期分池；稳定 bucket/shape，检查分配器 split/expand 策略，必要时在安全边界释放整段空闲 segment | 将“碎片/预留”下钻为块尺寸直方图、可复用率和最大连续块；从异常块反查产生它的算子/shape |
| 两类 GAP 都不高，但仍接近或触发 OOM | 容量主要被真实业务分配或进程级其他组件占用，而不是释放/缓存效率问题 | 回到峰值构成，优化激活、梯度、优化器状态、通信 buffer 或并行切分；核对是否有未纳入算子口径的 APP 占用 | 用五档业务账本与“进程其他”共同解释容量去向，并避免给出清缓存这类无效建议 |

### 三、堆栈图规律性与内存碎片：从“形状”判断生命周期是否健康

这里的规律性应同时比较**单 step 内部的形状**和**多个 step 之间能否重复**。健康训练通常具有稳定的相位特征：权重与优化器状态形成基线；激活在前向累积、反向消费；梯度在反向生成并维持到更新；优化器临时区只在更新附近出现。第一个 step 还可能包含图编译、懒初始化、优化器状态首次创建和内存池预热，所以不能用首步直接判定泄漏。

碎片也不能只用 `Reserved - Allocated` 下结论。这个差值同时包含正常缓存、延迟释放和真正不可利用的碎片。更可靠的判据是：总空闲量看似足够，但**最大连续可用块小于本次申请**，或者存在大量 inactive split/non-releasable 块并伴随分配重试、清池或 OOM。因而要把时间曲线与时刻 `t*` 的 segment/block 布局联动起来。

| 观测现象 | 诊断结果 | 下一步操作 | 可以用“8-内存分配”页做什么 |
|---|---|---|---|
| 稳态 step 的峰谷位置、层次顺序和峰值高度基本重合 | 生命周期与调度规律稳定，可作为健康基线；轻微幅度变化可能来自 token 数或通信抖动 | 保存基线签名，后续按阶段峰值、曲线相似度和各档面积做回归监控 | 复用现有完整 step 播放与四条 Layer 轨道，增加多 step 半透明叠加和“与基线差异”开关 |
| 前几个 step 的基线阶梯式上升，随后平台稳定 | 多为懒初始化、优化器状态首次创建、图编译或内存池预热，不应直接判断泄漏 | 将 warm-up 与 steady-state 分开统计；确认平台出现后不再增长，并标注首次创建的对象 | 用权重/优化器态/临时区详情解释哪一档只创建一次；允许用户把首步从异常检测基线中排除 |

### 四、Rank 间内存负载不均：先找同角色同伴，再判断异常

Rank 不均不能直接用“全卡最大值减最小值”判断，因为 PP、TP、EP 天然让 Rank 承担不同角色：不同 PP Stage 的层数、首尾 Embedding/LM Head 和在途微批数不同；不同 TP 分片可能因词表或维度不能整除而略有差异；不同 EP Rank 会因 token 路由拿到不同专家负载。正确做法是先建立**同角色比较组**：同设备型号、同 PP Stage、同 TP 位置、同 EP 专家分片位置，在不同 EDP/DP 副本之间比较；再把差异拆成业务分配、延迟释放、池空闲和进程其他四部分。

对每组建议同时报告峰值 GB、峰值时刻、组内中位数、`max / median - 1`、高位持续时间和异常 Rank。这样既能发现一张卡的孤立异常，也能区分“整组都高”的结构性配置问题与“组内单卡高”的运行时问题。

| 观测现象 | 诊断结果 | 下一步操作 | 可以用“8-内存分配”页做什么 |
|---|---|---|---|
| 不同 PP Stage 峰值有稳定梯度，但同 Stage 的对等 Rank 接近 | 多为流水线调度、层数、首尾层或在途微批造成的结构性差异，不是单卡故障 | 评估按参数量/激活量而非层数重切 PP，调整 virtual pipeline 和 micro-batch 调度；以 stage 容量上界做规划 | 当前页已经展示 PP 分段和不同 stage 的 in-flight 数，可按 Stage 聚合峰值并解释差异来自哪一档 |
| 同一 EP 位置在多个 EDP 副本中都偏高，且高值主要来自激活/算子分配 | 热点专家或路由偏斜；相同专家分片重复成为热点，属于负载分配问题 | 查看每专家 token 数、capacity/drop、dispatch/combine；调整路由均衡损失、专家放置、EP/ETP 或热点专家复制 | 用现有 EP token 桶和持有专家详情，把异常 Rank 映射到专家集合；从 Rank 组直接跳到对应 MoE Layer |
| 只有一个对等 Rank 的算子分配显著偏高，峰值跟输入 shape/token 数同步 | 数据分片不均、变长序列未充分 bucket、异常 batch 或局部分支导致真实工作量偏高 | 核对 sampler、padding/bucket、该 Rank 的 batch/sequence/token 统计及随机种子；复现同一输入确认 | 在 Rank 卡上并列展示输入规模、激活量和同组中位；利用激活分片视图说明多出的内存落在哪些 Layer |
| 只有一个 Rank 的延迟释放 GAP 高，而算子分配与同伴接近 | 内存需求本身均衡，异常来自该卡的慢流、事件等待、通信长尾或设备执行长尾 | 联查该 Rank 的 stream、kernel 和通信 timeline；定位最后访问与实际释放，排除硬件/链路异常 | 在 Rank 矩阵上用独立的“延迟释放热力”着色，点击后保持 step 游标并联动流与通信域 |
| 只有一个 Rank 的池空闲/碎片高，并呈跨 step 累积 | 该 Rank 经历了不同的分配历史、动态 shape 或异常大 workspace；属于 allocator 局部状态差异 | 对比对等 Rank 的块尺寸谱、最大连续块、分配栈和算子 shape；必要时隔离内存池或重设分配策略 | 将同角色 Rank 的块地图并排对比，突出“同样保留量、不同可用连续空间”，避免只比较总 GB |
| 同一节点的多张卡 APP Reserved 同时偏高，而算子三条曲线接近其他节点 | 节点级运行时、通信 buffer、残留进程或拓扑相关资源占用，不是模型负载不均 | 按 Host/Component/PID 核查 HCCL、runtime、自定义服务和僵尸进程；比较节点配置与通信域 | 由 Rank 卡阵向上聚合到 Node，增加“进程其他”层；一眼区分单 Rank、单节点和全局问题 |
| 异常高 Rank 随 step 轮换，组中位稳定 | 更像数据/路由随机性而非固定坏卡；但容量规划仍受最坏 Rank 决定 | 用 P95/P99 和连续多步最大值评估风险；检查路由均衡与输入 bucket，避免只修某一张卡 | 提供多 step Rank 热力播放和“固定热点/轮换热点”分类，保留现有 Rank→Layer→专家的下钻路径 |
