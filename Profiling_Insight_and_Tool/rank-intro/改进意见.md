### 背景
本文只讨论主流的 TP / PP / DP / EP 组合，暂不考虑 CP、SP 以及其他特殊切分方式。
本文不发射讨论非主流的极端、冷门情况。

### 到处都有激活，真正被切分的一个激活单元有多大？

首先，因为采用“EP 从 DP 域中切出”的口径，在这个口径下，DP 是配置里的数据并行度，EDP = DP / EP，EDP 才是一套完整专家模型的副本数，一个EDP是一个独立的实例。跨实例之间激活不会相互计算和通信。

也就是说，本案例的训练，一个step下有2个EDP在各跑各的。



激活在 Layer 输出通常可以抽象成形状为 [B, S, H] 的 hidden state，其存储大小由形状和数据类型决定，与张量中的数值大小无关。因此，在模型结构不变的重复层之间，边界激活的逻辑大小通常相同。

讨论一个 Layer 时，还要区分“同名 Layer 集合”和“Layer 实例”。例如模型有 46 个 Layer，每个 EDP 副本都有自己的 Layer0 和 PP Stage0。所有 EDP 中的 Layer0 合在一起，是同名 Layer 集合；某一个 EDP 中的 Layer0，才是一个具体的 Layer 实例。

在实际执行中，每个 EDP 是一条相对独立的完整流水线。不同 EDP 不需要等到彼此完成 Layer0，才继续执行 Layer1；PP Stage 之间的激活传递也只沿同一个 EDP 内部的流水线发生。不同 EDP 之间不交换前向激活，它们的主要同步发生在反向阶段的梯度归约，并且必须在对应的权重更新前完成。实现上梯度归约可以与反向计算重叠，不必理解为等所有反向计算完全结束后只做一次通信。

一个 EDP 内部包含 EP 个专家并行位置。对于普通的 Attention、Norm 等部分，每个数据流主要由对应的 TP ranks 协同计算；进入 MoE 模块后，token 会在同一个 EDP 内的 EP ranks 之间执行 dispatch，专家计算完成后再 combine 回原来的数据流。因此，EP 改变的是 MoE 层内部 token 的临时分布，不应把 Layer 输出长期画成彼此独立的 EP 激活分片。

PP 负责把不同 Layer 放到不同 Stage，并在 Stage 边界传递激活，不切分单个 Layer 的激活张量。DP 表达不同的数据流，EDP 表达完整专家模型的副本；它们都不是把同一份激活切成几块。TP 会影响 Layer 内部张量和计算的分布，但具体哪些激活被切分、哪些在通信后恢复完整，要以算子的 TP 布局为准，不能简单理解为所有激活都被 TP 均匀切开。

讨论权重时，TP 通常切分 Linear 等大权重，但 Norm、Router 等小权重可能在 TP 组内复制。EP 是把不同专家分配给不同 EP ranks，每个专家的权重仍是完整专家权重，而不是由 EP 再切成多片。不同 EDP 上对应的权重是逻辑相同、物理独立的副本，通过梯度同步保持数值一致。在常规均衡配置下，同类 rank 的权重存储量通常接近。

因此，DP × Layer 画布应先表达 EDP 的独立性：外层按 EDP 分成多条完整流水线，每条流水线内部再展示 PP Stage、Layer、EP 和 TP ranks。选择某个 Layer 时，应明确区分“某个 EDP 中的 Layer 实例”和“所有 EDP 中的同名 Layer 集合”；默认查看实例层，只有在做跨副本比较时才选择同名 Layer 集合。

## “8-内存分配”页：以 Rank 为横轴的观测说明

如果每张观测图的横坐标都是 Rank，那么页面回答的首先不是“某张卡随时间发生了什么”，而是：**在同一个观测口径下，各 Rank 的内存是否均衡，哪个 Rank 偏高，以及偏高来自哪一层内存。**发现异常 Rank 后，再下钻到该 Rank 的时间轴、step 阶段、算子、流、调用栈和内存块，解释异常为什么发生。

### 一、先明确横轴、纵轴和一个数据点分别表示什么

- **横坐标**：Rank ID。Rank 是离散类别，不是连续数值；R23 与 R24 相邻不代表它们在并行拓扑中相邻。若用折线连接各点，连线只帮助观察高低起伏，不能把“斜率”解释成趋势。
- **纵坐标**：当前选中指标的值。容量类指标使用 GB，比例类指标使用百分比。
- **当前采样模式**：Rank `r` 上的点表示同一时刻 `t` 的值，例如 `Allocated_r(t)`。它适合判断这一时刻哪些 Rank 不一致。
- **整 Step 结果模式**：Rank `r` 上的点表示该 Rank 在整个 step 内的峰值或最大占比，例如 `max_t Allocated_r(t)`。它适合找每个 Rank 的最坏情况，但各 Rank 的最大值可能发生在不同时间，不能把这些点当成同一时刻的系统快照。

页面应同时保留这两种模式。先用“整 Step 结果”找异常 Rank，再切到该 Rank 的峰值时刻；需要理解当前阶段的全局分布时，再看“当前采样”。

同一 Rank、同一时刻、同一组件口径下，四层内存可记为：

- `A_r(t)`：算子分配（Operator Allocated）。
- `H_r(t)`：算子持有（Operator Activated）。
- `R_r(t)`：算子保留（Operator Reserved）。
- `P_r(t)`：进程保留（APP Reserved）。

相邻层之间的差值为：

- 延迟释放量：`D_r(t) = max(H_r(t) - A_r(t), 0)`。
- 内存池空闲量：`I_r(t) = max(R_r(t) - H_r(t), 0)`。
- 进程其他占用：`O_r(t) = max(P_r(t) - R_r(t), 0)`。

四层是包含关系，不是四份可以相加的内存。只有采样时刻和组件口径一致时才能计算差值；尤其不能用“算子持有峰值减算子分配峰值”代替延迟释放，因为两个峰值可能不在同一时刻。

### 二、Rank 横轴图的通用观察顺序

1. **先固定比较条件**：同一个 step、同一个采样时刻或同一种整 Step 聚合方式、同一设备型号、同一组件口径。
2. **先分角色，再比高低**：优先比较同 PP Stage、同 TP 位置、同 EP 专家分片位置、不同 EDP/DP 副本的 Rank。不同角色之间天然可能有容量差，不能直接用全局最大值减最小值判断异常。
3. **先看分布形态**：看全局是否整体抬高、是否按 Stage 呈稳定台阶、是否周期性重复、是否只有一个 Rank 尖峰、是否同一节点成簇偏高。
4. **再看同组偏离**：给出同角色组的中位数、P95、最大值以及 `当前值 / 组中位数 - 1`。孤立高点比“全组一起高”更像运行时异常。
5. **最后联读相邻指标**：Allocated、Activated、Reserved、APP Reserved 要按包含关系逐层比较，定位多出的容量落在哪一层。
6. **选中异常 Rank 下钻**：显示产生该点的时刻、step 阶段、绝对 GB、占 HBM 比例、持续时间，以及对应的 Top 算子、Stream、组件和内存块。

### 三、算子分配图（Operator Allocated）怎么看

**一句话结论**：表示这张卡在对应时刻承载多少真实业务内存，越高越好，越均衡越好。

**纵轴数据**：

- 当前采样：`A_r(t)`，表示 Rank `r` 在时刻 `t` 仍由算子逻辑使用的真实张量内存。
- 整 Step 结果：`A_r^peak = max_t A_r(t)`，表示该 Rank 在本 step 内真实业务分配的最高水位。

它主要覆盖权重、激活、梯度、优化器状态、更新临时量和算子 workspace。某个 Rank 的点高，表示这张卡在对应时刻或峰值时刻承载了更多真实业务内存，不等于存在泄漏。

| Rank 图形态 | 数据代表的含义 | 进一步观察 |
|---|---|---|
| 所有 Rank 都高，且形态相近 | 全局业务容量偏高，常由 MBS、序列长度、在途微批或模型规模决定 | 看占 HBM 比例和峰值阶段，评估重计算、MBS、序列长度或并行切分 |
| 不同 PP Stage 呈稳定台阶，同 Stage 内接近 | Stage 层数、首尾层、在途微批或调度造成的结构性差异 | 按 Stage 分组，不把台阶直接标成异常 |
| 同一 EP 位置在多个 EDP 副本中重复偏高 | 可能是热点专家、专家放置或稳定的路由偏斜 | 对照每专家 token 数、capacity/drop、dispatch/combine |
| 同角色组只有一个 Rank 明显偏高 | 该 Rank 的输入 token/shape、局部分支或 workspace 需求偏大 | 对照 batch、sequence、token、算子和 Layer 构成 |
| 高点随 step 在不同 Rank 间轮换 | 更像数据或路由随机性，不像固定坏卡 | 看多 step 的 P95/P99 和最坏 Rank，而不是只修一张卡 |

### 四、算子持有图（Operator Activated）怎么看

**一句话结论**：算子持有包含算子分配，算子持有高出算子分配的部分，是跨流使用、事件未完成或长尾 kernel 导致的延迟释放，是需要注意的部分，这一部分可以有，但应越小越好。

**纵轴数据**：

- 当前采样：`H_r(t)`，表示 Rank `r` 上仍被设备流持有、尚不能安全回收到内存池的内存。
- 整 Step 结果：`H_r^peak = max_t H_r(t)`。

算子持有包含算子分配，因此“持有高”可能只是因为真实分配本身高。判断延迟释放必须在同一个 Rank、同一时刻比较 `H_r(t)` 与 `A_r(t)`：

- `A` 与 `H` 同时升高且两者接近：主要是真实业务占用。
- `A` 接近同组 Rank，但 `H` 单独偏高：多出的 `H - A` 才表示跨流使用、事件未完成或长尾 kernel 导致的延迟释放。
- 某节点或通信域内多个 Rank 的 `H - A` 同时偏高：优先联查通信长尾、同步等待和流依赖。

该图不能单独证明泄漏。短时尖峰可能只是正常的异步执行窗口；还要看 GAP 的绝对 GB、持续时间，以及它是否推高后续容量峰值或阻止内存复用。

### 五、算子保留图（Operator Reserved）怎么看

**一句话结论**：算子保留包含算子持有，算子保留高出算子持有的部分，表示Rank 的内存池空闲或缓存较多，是需要注意的部分，这一部分可以有，但应越小越好。

**纵轴数据**：

- 当前采样：`R_r(t)`，表示框架或 GE 已向设备申请并留在算子内存池中的总量。
- 整 Step 结果：`R_r^peak = max_t R_r(t)`。

算子保留包含算子持有。要判断高点的含义，应在同一时刻查看 `R_r(t) - H_r(t)`：

- `H` 与 `R` 接近：保留量主要仍被流持有，池内空闲不大。
- `H` 接近同组 Rank，但 `R` 明显偏高：该 Rank 的内存池空闲或缓存较多。
- 首个 step 后 `R` 升高、后续稳定并反复复用：通常是分配器预热和正常缓存。
- 某 Rank 的 `R - H` 跨 step 持续累积且复用率低：可能存在动态 shape、尺寸不匹配或低效池策略。

`R - H` 大不等于存在碎片。碎片需要额外证据：总空闲量足够，但最大连续可用块小于本次申请，或出现 inactive split/non-releasable 块、分配重试、清池或 OOM。

### 六、进程保留图（APP Reserved）怎么看

**一句话结论**：进程保留包含算子保留，高出算子保留的部分，是HCCL 通信 buffer、runtime、图执行器等，是需要注意的部分，这一部分可以有，但应越小越好。

**纵轴数据**：

- 当前采样：`P_r(t)`，表示该 Rank 所在进程在设备侧保留的全部内存。
- 整 Step 结果：`P_r^peak = max_t P_r(t)`。

进程保留是最接近整卡容量压力的口径。它可能包含算子保留之外的 HCCL 通信 buffer、runtime、图执行器、常驻 workspace、自定义算子和其他进程上下文。

- `P` 高且 `A/H/R` 也按相近幅度高：容量主要由算子账内业务推高。
- `A/H/R` 与同组 Rank 接近，只有 `P` 偏高：多出的 `P - R` 指向通信、运行时或其他未进入算子账的组件。
- 同一节点多张卡的 `P - R` 同时偏高：更像节点级服务、通信域、残留进程或拓扑相关预留。
- 单个 Rank 的 `P` 接近 HBM 上限：无论来源为何，都已经形成实际 OOM 风险，应同时显示剩余安全余量。

APP Reserved 与 Operator Reserved 只有在设备、进程、组件和采样时刻对齐后才能做差，不能把不同采样来源的两个峰值直接相减。

### 七、延迟释放最大占比图怎么看

**纵轴数据**：

- 当前采样占比：`qD_r(t) = D_r(t) / R_r(t)`。
- 整 Step 结果：`qD_r^max = max_t qD_r(t)`。

每个 Rank 的点表示“算子保留中，有多大比例已经不再由算子逻辑使用，但仍被流持有”。使用比例而不是只看 GB，可以比较内存体量不同的 Rank；但比例会放大低水位时的瞬时小尖峰，因此高点必须同时展示：

- 最大占比；
- 该时刻的延迟释放绝对量 `D_r(t*)`；
- `t*` 所在的前向、反向或更新阶段；
- 高位持续时间或 `字节 × 持续时间`（byte-time）；
- 最后访问该内存的 Stream、kernel 或等待事件。

| Rank 图形态 | 数据代表的含义 |
|---|---|
| 单个 Rank 占比和绝对 GB 都高，Allocated 与同伴接近 | 该 Rank 存在明显的慢流、跨流依赖或异步长尾 |
| 一组通信相关 Rank 在同一阶段同时偏高 | 可能存在 collective 长尾、同步等待或通信流阻塞 |
| 占比很高但绝对量很小、持续极短 | 低水位下的比例放大，通常不应排在高 GB、长持续问题之前 |
| 各 Rank 都在同步边界出现窄尖峰并快速归零 | 更像正常异步语义，可作为基线而非直接判异常 |

### 八、内存池空闲最大占比图怎么看

**纵轴数据**：

- 当前采样占比：`qI_r(t) = I_r(t) / R_r(t)`。
- 整 Step 结果：`qI_r^max = max_t qI_r(t)`。

每个 Rank 的点表示“算子保留中，有多大比例已经回到内存池、当前没有被流持有”。高值说明池内闲置比例高，不直接说明这些空间不可复用，也不直接说明存在碎片。

- 多个 Rank 在首个 step 偏高，后续下降或稳定复用：通常是预热和缓存命中。
- 单个 Rank 长期偏高，同时复用率低：该 Rank 可能经历了不同的动态 shape、workspace 或分配历史。
- 占比高但最大连续空闲块仍足以满足后续申请：是可复用缓存，不宜仅因比例高就清池。
- 占比和绝对 GB 都高，最大连续空闲块却小于失败申请：才有较强的碎片证据。

该图也必须同时显示池空闲绝对 GB、持续时间、复用率、最大连续空闲块和失败申请尺寸。没有 block/segment 数据时，只能称为“内存池空闲偏高”，不能直接标记为“碎片”。

### 九、六张 Rank 图如何合起来归因

| 同一 Rank 的组合现象 | 应优先解释为 |
|---|---|
| Allocated 高，其他三层随之升高，两类 GAP 占比正常 | 真实业务内存高：激活、梯度、优化器态或 workspace |
| Allocated 正常，Activated 高，延迟释放占比和绝对量都高 | 跨流延迟释放、慢 kernel 或事件等待 |
| Activated 正常，Reserved 高，池空闲占比和绝对量都高 | 内存池缓存或低效复用；是否碎片仍需块级证据 |
| Reserved 正常，APP Reserved 高 | 通信、runtime、图执行器或其他进程级占用 |
| 四个容量指标都不突出，但某个比例很高 | 可能是低水位比例放大，先看绝对 GB 和持续时间 |
| 同角色组全部偏高 | 结构性配置、输入规模或阶段负载问题 |
| 同角色组只有一个 Rank 偏高 | Rank 局部输入、路由、流、分配器或节点运行时问题 |

这套归因必须沿同一 Rank 纵向读取，不能把 R23 的 Allocated、R54 的 Activated 和 R87 的 Reserved 拼成一条因果链。

### 十、图表应补充的读数和交互

为了让“横轴是 Rank”的图真正可诊断，每张图至少应提供：

- 当前模式：当前采样或整 Step 结果；当前采样还要标出 step 百分比和阶段。
- Rank 的 PP、TP、EP、EDP/DP、Node 与 Device 角色标签，并允许按同角色分组。
- 当前值、组中位数、相对组中位数偏差、全局 P95/P99 和本指标最高 Rank。
- 容量类图统一 GB 纵轴并标出 HBM 上限或安全线；比例类图固定为 0%～100%。
- 峰值点对应的时刻 `t*`。不同指标的 `t*` 分别记录，不暗示它们同时发生。
- 点击 Rank 后，保留该 Rank 作为主语，在六个指标间切换，并联动到单 Rank 时间轴。
- 下钻证据按指标收敛：Allocated 看张量/算子/Layer，Activated 看 Stream 和最后访问，Reserved 看池和 block，APP Reserved 看组件/PID，比例图补充绝对 GB 与持续时间。

推荐保留固定的拓扑顺序来发现 Stage、EP、Node 等结构性图案，同时提供“按数值排序”作为临时视图。排序后必须保留 Rank ID 和角色标签，避免把排序后的相邻柱误认为拓扑相邻。

### 十一、口径边界

当前页面中的数据是用于解释交互的确定性合成数据，能够说明“图应该怎么看”，但不能据此输出生产环境结论。生产分析至少需要接入并对齐 `memory_record`、`operator_memory`、step marker、Stream、内存块、组件/PID 和调用栈数据。

如果缺少 Operator Activated 或流信息，只能计算 `Reserved - Allocated` 的合并 GAP，不能强行拆成延迟释放与池内空闲；如果缺少 block/segment 数据，也不能仅凭 GAP 宣称存在碎片。
