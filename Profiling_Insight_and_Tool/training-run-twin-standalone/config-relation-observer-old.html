            把一份训练配置调对，本质上是在一张互相牵制的约束网里找可行点： 五个并行维度不是五个独立的旋钮，它们彼此相乘、又同时被模型结构、集群拓扑和单卡显存三面夹住。 这份文档写的就是这张网 —— 每条约束从哪来、违反了会怎样、以及某一项调不动时该动哪一项。 约束卡左缘的色条是类别：红=硬约束（违反则起不来），橙=软约束（能起来，但踩在性能悬崖上），蓝=取决于所用框架的口径。

            一份配置要过三关

            三关的失败方式完全不同，代价也差着数量级：

            关要满足什么不满足时
            配得通并行维度的乘积对得上卡数，整除关系自洽启动器当场拒绝，秒级失败
            切得开切分维度整除得了被它切的模型结构框架建图时报错，分钟级失败
            跑得下最紧的那张卡装得下前几个 step OOM —— 而这时通常已经排了几小时队

            越靠后的关卡，失败成本越高：前两关是确定性的整数运算，开训前就能算死； 第三关要把权重、梯度、优化器状态、激活和运行时开销逐项估出来， 但它同样是算得出来的 —— 不必等 OOM 才知道。

            整网区那个「模型」下拉不在其中：它选的是一整套预设（层数、hidden size、专家规格、注意力形态…）， 是这张约束网的输入，而不是网上的一个可调节点。

            Total Layer decoder 层数 · num_layers Model Architecture

            堆叠多少个 transformer decoder block。它是模型结构参数，不是并行参数 —— 改并行度只是换个方式跑同一个模型，改层数则是换了一个模型，权重不再通用。

            它与 hidden size 一起决定模型有多深多大。深度带来的是表达能力的层次， 所以同参数量下「深而窄」和「浅而宽」是两种不同的取舍，而不是等价的。

            调大
            • 要更强的模型容量，且倾向于加深而非加宽
            • 复现某个已发布的模型规格
            调小
            • 只想跑通流程做冒烟验证
            • 显存实在不够，且并行度已无处可加

            DP Data Parallel · 数据并行度 Model Architecture

            同一份完整模型被复制多少份，每份吃不同的数据分片，每步末把梯度 all-reduce 到一致。 副本之间是复制关系而不是切分关系。

            它解决的是「算得太慢」，不是「装不下」 —— 这是五个维度里唯一一个加了不省显存的。把 DP 从 2 拉到 8，总卡数翻两番， 每张卡上的权重、梯度、优化器状态一个字节都没少。唯一的例外是开了优化器并行， 那时优化器状态会沿 DP 维分片。

            调大
            • 要提高吞吐、缩短一个 epoch 的墙钟时间
            • 全局 batch 需要更大
            • 开了优化器并行，想让优化器状态分得更细
            调小
            • 卡要让给真正能省显存的维度
            • 全局 batch 已过大，收敛质量下降
            DP
            一定联调
            • Total Rank —— 乘积变了
            • 全局 batch = MBS × DP × 累积步数
            考虑再调
            • Micro Batch —— 反向补回全局 batch
            • EP —— 切出口径下要满足 DP % EP
            PP Pipeline Parallel · 流水线并行度 Model Architecture

            把模型按层切成若干段（stage），每段放一组卡上，micro-batch 像流水线一样依次流过： 第一段算完把激活传给第二段，自己接着算下一个 micro-batch。

            它解决的是「单卡放不下这么多层」。在五个维度里它的通信量最小 —— 相邻 stage 之间只传一份边界激活，而且是点对点，不是集合通信。 正因如此，PP 是最适合切在节点边界上的一维。 代价是流水线气泡：首尾填充与排空阶段有卡在空转，比例约 (PP − 1) / micro_batch_num。

            调大
            • 单卡装不下这么多层，且不想加通信更密的 TP
            • 要跨节点扩展 —— PP 通信最稀，最扛得住跨机
            调小
            • 气泡占比过高（micro-batch 数喂不满流水线）
            • 层数不够分，出现空 stage
            • stage0 在飞的激活反成瓶颈（PP 越大它压得越多）
            PP
            一定联调
            • Total Rank —— 乘积变了
            • Total Layer —— 必须 ≥ PP
            • 各 stage 的层数划分与首末段的额外负担
            考虑再调
            • Micro Batch —— 压气泡要更多 micro-batch
            • Node —— PP 最适合切在节点边界
            TP Tensor Parallel · 张量并行度 Model Architecture

            把单个算子的权重矩阵按行或列切开，多张卡各算一片，再把结果拼回去。 切的是注意力头和 FFN 的 intermediate 维。

            它是见效最直接的一维 —— 参数和激活一起降，而 PP 只降参数、CP 只降激活。 代价也最重：每层前向反向各要 all-reduce 一次激活，是通信最密的维度， 而且这些通信都在关键路径上、无法与计算重叠掉。 所以 TP 组一旦跨出节点就是性能悬崖 —— 吞吐可能掉一半以上。

            调大
            • 显存缺口大且要立刻见效（两头一起降）
            • 单层权重本身超过单卡容量
            调小
            • TP 组被迫跨节点
            • 头数 / KV 头数 / intermediate 除不尽
            • 切得太碎，矩阵乘掉出高效区间
            TP
            一定联调
            • Total Rank —— 乘积变了
            • 单卡显存（参数与激活同时变）
            • 受 num_heads / n_kv_heads / intermediate 整除约束
            考虑再调
            • Node —— TP 组必须收在节点内
            • 序列并行开关（决定激活还能不能再切一刀）
            CP Context Parallel · 上下文并行度 Model Architecture

            把一条序列按 token 位置切成若干段分给不同卡。 attention 要看全局，所以各卡之间用 ring 的方式轮转传递 KV。

            它专治长序列。激活随序列长度线性增长，attention 的中间量甚至是平方级 —— CP 是唯一直接压这一项的维度。序列不长时它没有意义：白付一轮 ring 通信， 而省下的激活本来就不是瓶颈。要求 seq % (2×CP) == 0 而不只是 CP， 是因为因果注意力下序列前段计算量远小于后段，得对半交叉分配才能均衡负载。

            调大
            • 序列拉长后激活爆了
            • attention 的中间量已是显存主要来源
            调小
            • 序列本来就不长，CP 只是白付通信
            • 序列长度除不尽 2×CP
            CP
            一定联调
            • Total Rank —— 乘积变了
            • 受 Seq Length 整除约束
            考虑再调
            • Seq Length —— 两者是同一件事的两头
            • Micro Batch —— 都在压激活，先动便宜的那个
            Routed Expert 路由专家总数 · 表单标注 Routed MoE

            每个 MoE 层里可供路由的专家个数。每个 token 经 router 打分后， 只激活其中得分最高的 Top-K 个，其余专家这一步不参与计算。

            它是 MoE 的核心手段：用总参数量换模型容量，而单 token 的计算量不变。 解决的是「想要更大的模型，但不想让每个 token 都付更多算力」。 代价全部落在显存与通信上 —— 一个 92B 的 MoE 模型可能有 97% 的参数在专家里。

            调大
            • 要提高模型容量，又不想增加单 token 计算量
            • 专家已经分化充分，还有余量继续细分
            调小
            • 总参数量装不下，且 EP 已加到通信划不来
            • 专家过多导致 token 被摊薄，单个专家训练不充分
            Routed
            Expert
            一定联调
            • EP —— 必须能被 EP 整除
            • 单卡显存（MoE 模型的参数大头）
            • Top-K 的上限
            考虑再调
            • Top-K —— 两者之比即激活率
            • 负载均衡损失的权重
            Top-K 每 token 激活几个专家 · num_experts_chosen MoE

            router 为每个 token 打分后选出前 K 个专家，token 被复制 K 份分别送过去， 算完再按权重加权合并回来。

            它是「容量 / 算力」这条杠杆上的支点：K 直接决定 MoE 层的实际计算量， 也直接决定 all-to-all 要搬多少 token。 K 和专家总数之比就是激活率 —— 同样 256 个专家，K=8 和 K=2 是两种完全不同的模型。

            调大
            • 要提升效果，让更多专家参与每个 token
            • 专家利用率过低，大量专家长期收不到 token
            调小
            • MoE 层耗时过长，计算量压不下来
            • all-to-all 搬运量成为瓶颈
            • 算子临时区峰值把显存顶穿
            Top-K
            一定联调
            • MoE 层的计算量与 all-to-all 搬运量
            • 算子 workspace 峰值（∝ K × 一层 token 张量）
            考虑再调
            • Routed Expert —— 保持激活率不变
            • EP —— K 大则跨卡搬得更多
            Shared Expert 共享专家数 · 表单标注 Shared MoE

            不参与路由、所有 token 都要过的专家。它和被选中的 K 个路由专家的输出相加。

            它承接通用知识，让路由专家腾出容量去学差异化的部分， 同时给每个 token 一条恒定存在的通路 —— 这在训练早期尤其重要， 那时 router 还没学好，路由结果不稳定甚至塌缩。 注意它在 EP 域内每张卡都有一份完整副本，EP 帮不上忙，显存吃紧时它是纯负担。

            调大
            • 出现路由塌缩或长期负载不均
            • 希望有一条不依赖 router 的稳定通路
            调小
            • 显存吃紧 —— 它是唯一不被 EP 摊薄的专家
            • 路由已足够稳定，通用通路的收益在递减
            Shared
            Expert
            一定联调
            • 单卡显存 —— 每卡一份完整副本，不随 EP 摊薄
            • 每 token 实际过的 FFN 数 = K + 共享数
            考虑再调
            • Top-K —— 一起看总激活量
            • 负载均衡损失的权重
            EP Expert Parallel · 专家并行度 MoE

            把一个 MoE 层的专家分散到多张卡上，每张卡只持有 专家总数 / EP 个。 token 先按路由结果 all-to-all 发到专家所在的卡，算完再 all-to-all 收回来。

            它是 MoE 模型减少单卡显存的主力 —— 专家参数常占全模型 95% 以上， 而这一维正好切在这块最大的肉上。代价是每个 MoE 层要做两次 all-to-all， 而 all-to-all 是全连接通信模式，对拓扑最敏感：EP 域一旦跨出超节点， 省下的显存很可能被通信时间吃回去，表现为 MoE 层耗时随 EP 增大不降反升。

            调大
            • 专家权重装不下 —— 这是最主要的理由
            • 想扩规模又不动模型结构
            调小
            • all-to-all 跨机后 MoE 层耗时不降反升
            • 专家数不够分（除不尽）
            • EP 域跨出了超节点边界
            EP
            一定联调
            • Routed Expert —— 必须被 EP 整除
            • 正交口径下 Total Rank；切出口径下 DP
            • 单卡显存（专家那一段 ÷ EP）
            考虑再调
            • Node —— 把 all-to-all 收在超节点内
            • Top-K —— 一起决定搬运量
            Total Rank 总卡数 · world_size Cluster

            这次训练占用的 NPU 总数，等于各并行维度的乘积，也必须等于启动器实际拉起的进程数 （msrun 的 --worker_num）。

            它不是一个独立旋钮，而是五个维度的结果。直接给它一个目标值， 等于反过来要求系统配平其他维度 —— 而配平的方式不唯一： 同样是 2048 卡，可以是 DP 大而 PP 小，也可以反过来，两者的显存与吞吐完全不同。 所以它更适合当作「预算」来看：先定预算，再决定怎么花。

            调大
            • 要更快跑完，或模型/序列变大后必须扩容
            • 申请到了更多资源
            调小
            • 集群紧张，大规模作业排队时间过长
            • 只做小规模验证，不需要全量资源
            Total
            Rank
            一定联调
            • DP/PP/TP/CP/EP 中至少一项 —— 乘积必须对上
            • Node —— 必须整除
            • 启动命令里的 worker_num
            考虑再调
            • 几乎没有「可选」联动 —— 它的联动全是硬绑定
            Node 节点数 · 物理服务器台数 Cluster

            参与这次训练的服务器台数。每节点卡数 = 总卡数 / 节点数， 而这个数由硬件形态定死（昇腾 910B 一节点 8 卡），不是可以随意填的量。

            它真正决定的是并行维度落在哪一侧的互联上：同节点内走高速片间互联， 跨节点走网络，两者带宽差着数量级。所以「节点数」不只是个规模数字 —— 通信最密的 TP 该收在节点内，all-to-all 的 EP 域该收在超节点内， 通信最稀的 PP 才适合切在节点边界上。

            调大
            • 总卡数变大后必然增加（每节点卡数是定值）
            调小
            • 想把通信密集的维度收进更少的节点里
            • 减少跨机网络上的通信域个数
            Node
            一定联调
            • 每节点卡数 = Total Rank / Node，必须整除
            • 启动命令里的 local_worker_num 与 node_rank 范围
            考虑再调
            • TP —— TP 组不该跨节点
            • PP —— 最适合切在节点边界
            • EP —— all-to-all 域尽量收在超节点内
            卡型号 NPU 硬件规格 Cluster

            选定的 NPU 型号。它是枚举而不是量 —— 影响这份配置的主要是单卡 HBM 容量， 其次是算力与互联形态。

            它是第三关的分母：同一份配置换一款 HBM 更大的卡，所有并行度都能松一档。 现实中它往往是给定的而不是可选的 —— 集群里有什么卡就用什么卡， 所以它更多是作为「已知条件」进入这张约束网，而不是作为调节手段。

            换大卡
            • 显存反复吃紧，并行度已无处可加
            • 为省显存而付的通信代价已经划不来
            通常不可选
            • 集群只有这一种卡 —— 多数情况下它不可选
            • 混合型号会让负载均衡与通信都变复杂
            卡型号
            一定联调
            • 单卡显存上限 —— 三条警戒线全部按它算
            • 框架可用显存上限（要留一截给通信与工作区）
            考虑再调
            • 每节点卡数 —— 不同型号的整机形态不同
            • 计算精度（不同代次支持的 FP8 / FP4 不同）
            Micro Batch 单次前向的样本数 · MBS Cluster

            一次前向/反向真正喂进去的样本数。注意它不是全局 batch —— 全局 batch = MBS × DP × 梯度累积步数，而只有 MBS 直接进显存。

            激活显存与它成正比，而且它不参与任何切分、不撞任何整除约束 —— 这使它成为压显存时最容易先试的一项。反过来，它太小则算子跑不满算力， 单卡效率下降；在流水线里它还与 micro-batch 数一起决定气泡占比。

            调大
            • 算子效率低，小 batch 喂不满算力
            • 想减少梯度累积步数、缩短一步的墙钟时间
            调小
            • 激活爆了 —— 这是最便宜的一刀
            • stage0 在飞的 micro-batch 压得太多
            Micro
            Batch
            一定联调
            • 激活显存（线性）与算子 workspace 峰值
            • 全局 batch = MBS × DP × 累积步数
            考虑再调
            • 梯度累积步数 —— 把全局 batch 补回来
            • PP —— micro-batch 数决定气泡占比
            Seq Length 序列长度 · seq_length Cluster

            一条训练样本的 token 数。它同时是这个模型训练出来之后的上下文长度上限 —— 不是一个纯粹的性能参数，而是能力参数。

            它是激活显存的主导因子：常规激活随它线性增长， 而 attention 的中间量在不开 FlashAttention 时随它平方增长。 拉长序列几乎必然要同时动 CP 或重计算，否则显存曲线会陡起来。

            调大
            • 目标场景需要更长上下文
            • 做长序列续训（通常是分阶段逐步拉长）
            调小
            • 激活装不下，且 CP 已经加到通信划不来
            • attention 耗时占比过高
            Seq
            Length
            一定联调
            • 激活显存与 attention 耗时
            • 必须被 2 × CP 整除
            • 位置编码的外推设置（RoPE base 等）
            考虑再调
            • CP —— 长序列的正规解法
            • Micro Batch —— 两者乘积是每卡 token 数

            五个并行维度各切什么

            五个维度切的是完全不同的东西，这决定了它们各自的通信代价， 也决定了加它到底能不能换来显存余量：

            维度切什么通信省显存？
            DP切数据，每副本一份完整权重每步末 all-reduce 梯度一次不省
            PP切层，每卡只背本 stage 那几层相邻 stage 点对点传激活，最稀省
            TP切张量：注意力头、FFN 的 intermediate每层前反向各 all-reduce 一次激活，最密省
            CP切序列长度attention 内部 ring 传 KV省激活
            EP切专家，每卡只持有一部分路由专家MoE 层 all-to-all 收发 tokenMoE 下省得最多

            「显存不够就加卡」只有加 TP / PP / EP / CP 时才成立。 把 DP 从 2 拉到 8，总卡数翻两番，每张卡上的权重、梯度、优化器状态一个字节都没少 —— DP 副本之间是复制关系而不是切分关系。DP 买的是吞吐，不是余量。

            这条有一个重要的例外：开了优化器并行（ZeRO-1 / FSDP 一类）之后， 优化器状态会沿 DP 维分片。由于优化器状态通常占权重相关字节的四分之三 （fp32 master weight + momentum + variance 共 12 字节，对 bf16 的 2 字节权重）， 这一开关对显存的影响往往比再加一维并行还大。

            world_size 与 rank 编址

            并行维度的乘积就是这次训练要占的卡数，它必须等于启动器实际拉起的进程数 （msrun 的 --worker_num、torchrun 的 nproc × nnodes）。 对不上时启动器不会替你猜，直接失败。

            world_size = DP × PP × TP × CP × EP ← EP 独占 rank 的口径 world_size = DP × PP × TP × CP ← EP 从 DP 切出的口径（见下一节）

            全局 rank 号怎么排

            把五个维度的坐标压成一个整数，通常按这个顺序展开 —— stage 最外，EP / TP / CP 最内：

            r = s·(DP·EP·TP·CP) + d·(EP·TP·CP) + p·(TP·CP) + c·TP + t n = ⌊r / 每节点卡数⌋ s 层所在 PP stage d DP 序号 p EP rank t TP 序号 c CP 序号 n 物理节点号

            这个顺序不是随意的。越靠内的维度，同组的 rank 号越连续， 也就越可能落在同一个物理节点内、走机内互联而不是跨机网络。 所以通信最密的维度（TP）排在最内层，通信最稀的维度（PP）排在最外层 —— 编址顺序本身就是一次通信优化，而不只是编号习惯。

            层与专家怎么落到维度上

            • 层 → PP stage：尽量均分，前 L mod PP 段各多 1 层。 46 层切 4 段 → 12, 12, 11, 11。首段还要多背 embedding，末段多背 LM head， 所以各 stage 天然不等重。
            • 专家 → EP rank：等分连续切，p = ⌊e / (E / EP)⌋。 每个 EP rank 拿到 E / EP 个专家。

            EP 与 DP：正交还是从 DP 切出

            读任何一份 MoE 训练配置，第一件要确认的事是：EP 占不占自己的 rank。 两种口径都存在，而它们对同一组数字的解释完全不同 —— 搞反了，卡数会差出一个 EP 倍。

            正交从 DP 切出
            world_sizeDP×PP×TP×CP×EPDP×PP×TP×CP
            EP 的 rank独占与 DP 复用同一批卡
            额外约束只要 E % EP == 0再加 DP % EP == 0
            专家的数据并行度等于 DPEDP = DP / EP

            切出式的意思是：一张卡既是某个数据并行副本的成员，又是某个 EP rank 的持有者。 这也是 Megatron 系（含 MindSpeed-LLM）与 MindFormers 的做法 —— EP 不进 world_size 的乘积， 而是把已有的 DP 组再切一刀。切完之后专家权重只在剩下的 DP / EP 维上复制， 这一维就叫 EDP（expert data parallel）。

            同一组数字的两种读法

            以 openPangu 2.0 flash 的参考配置为例： DP=8, PP=4, TP=1, CP=1, EP=64，总共 2048 张卡。

            正交读法： 8 × 4 × 1 × 1 × 64 = 2048 DP 就是 8 切出读法： DP = 2048 / (4 × 1 × 1) = 512 EDP = 512 / 64 = 8 ← 配置里写的那个 "8"

            两种读法算出来的总卡数一样，但「DP」指的不是同一个东西： 正交读法里它是数据并行度，切出读法里那个 8 是专家的数据并行度，真正的 DP 是 512。 看一份配置时，判断依据是它跑在什么框架上，而不是字面。

            值得注意的是：两种口径下卡的排布是同一个。 那 512 张卡本来就该排成 8 × 64 的网格 —— 区别只在于你把行叫做「DP」还是「EDP」。 也正因为如此，这个混淆很难被卡数对不上暴露出来，只能靠事先问清楚。

            切分维度与模型结构的整除关系

            每个切分维度都在切某个具体的模型结构量，切不整就无处安放。 这一组是最常见的「配置看着合理、一建图就报错」的来源。

            num_layers ≥ PP 硬约束

            每个 pipeline stage 至少要分到 1 层，否则会有空 stage 占着卡什么也不算，还要在流水线里占一拍。

            层数除不尽 PP 是允许的（多出来的层分给靠前的 stage），少于 PP 才是错。

            num_heads % TP == 0 硬约束

            TP 切的是注意力头，每张卡分到整数个头。 头数常常不是 2 的幂（如 48、28），而 TP 习惯上按 2 的幂取，两者很容易对不上。

            建图阶段报维度不匹配，报错信息通常指向 QKV 投影的权重形状。

            n_kv_heads % TP == 0　（GQA / MQA 模型） 硬约束

            GQA 的 KV 头数远少于 Q 头数（如 28 Q : 4 KV），它才是真正卡住 TP 上限的那个数。 TP 超过 KV 头数就得把 KV 复制到多张卡上 —— 显存与带宽都白付，多数框架直接拒绝。

            这是 GQA 模型 TP 开不大的根本原因，和参数量无关。

            intermediate_size % TP == 0 硬约束

            FFN 沿 intermediate 维切。MoE 模型的 moe_intermediate_size 往往比 dense 的小一个数量级 （典型值 1024 对 9216），所以同一个模型里 MoE 层比 dense 层更早卡住 TP。

            即使整除得开，切得过碎也会让矩阵乘掉出高效区间，性能先垮在切分粒度上。

            seq_length % (2 × CP) == 0 硬约束

            CP 沿序列维切分。要求 2 倍而不只是 CP，是因为因果注意力下序列前段的计算量远小于后段， ring attention 要把序列对半交叉分配才能让各 rank 负载均衡。

            num_experts % EP == 0 硬约束

            路由专家要能均分到每个 EP rank。除不尽意味着有的卡多背一个专家， 这一维的显存与计算量当场就不齐了 —— 而 all-to-all 是同步的，最慢的那张卡决定整层的耗时。

            top_k ≤ num_experts 硬约束

            一个 token 选不出比总数还多的专家。

            Top-K 还决定 all-to-all 要搬多少 token，以及 MoE 算子临时区的峰值 —— 见「单卡显存由什么构成」。

            DP % EP == 0 依实现而定

            只在「EP 从 DP 切出」的口径下成立：专家组要能在数据并行组内均分， 否则某些 DP 副本拿不到完整的专家集。EP 正交的口径下没有这条。 严格写法还要把专家内部的张量并行算进去：DP × TP % (EP × ETP) == 0。

            并行维度落到物理拓扑上

            前一组约束来自模型，这一组来自机器。它们的共同点是：都不在模型定义文件里， 却同样能让一份配置跑不起来 —— 或者跑起来慢得没意义。

            总卡数 % 节点数 == 0 硬约束

            每节点卡数要是整数，且这个数由硬件形态定死（昇腾 910B 一节点 8 卡），不是可以随便填的量。

            TP 组不跨节点：TP ≤ 每节点卡数 软约束

            TP 每层前反向都要 all-reduce 一次激活，是通信最密的一维，必须吃机内互联。 一旦 TP 组跨出节点，这些 all-reduce 全部落到跨机网络上 —— 带宽差着数量级， 而它们又都在关键路径上，无法与计算重叠掉。

            这是典型的性能悬崖：配置合法、训练能跑，但吞吐可能掉一半以上。

            EP 的 all-to-all 域尽量收在超节点内 软约束

            EP 越大，MoE 层 dispatch/combine 的 all-to-all 参与方越多。 all-to-all 的代价随参与节点数增长，而且它天然是全连接通信模式，对拓扑最敏感。 大 EP 省下的显存，可能被跨机 all-to-all 的时间吃回去。

            表现为 MoE 层耗时随 EP 增大不降反升，而计算量并没有变。

            PP 的 micro-batch 数 ≥ PP 软约束

            流水线的 micro-batch 数太少，气泡（bubble）占比就上去了： 1F1B 下气泡比例约 (PP − 1) / micro_batch_num。 要把气泡压到 10% 以下，micro-batch 数大致得是 PP 的十倍。

            但 micro-batch 数受全局 batch 约束，两头都紧时只能回头压 PP。

            单卡显存由什么构成

            第三关是唯一一个「配得通、也切得开，却仍然跑不起来」的关卡。 要估它，得先把一张卡上的显存拆成六段，再看每一段被哪一维切：

            段大小被谁切
            权重参数量 × 2（bf16）见下表
            梯度参数量 × 2
            优化器状态参数量 × 12（fp32 master + momentum + variance）
            激活≈ 34 · mb · s · h 每层（不重计算时）÷ TP、÷ CP，× 在飞的 micro-batch 数
            运行时底座驱动 + context + kernel binary，几个 GB不随配置变
            预留 buffer / 碎片通信 buffer + 算子临时区 + 分配器碎片随并行配置变，见下

            参数相关的三段各自被谁切

            MoE 模型不能套 dense 的 12H²/层 经验公式： 一个 92B 的 MoE 模型可能有 97% 的参数在专家里，套 dense 公式会算出一个完全错的数。 必须逐项分算：

            这一项被谁切
            路由专家÷ EP，再 ÷ ETP（若有）　← MoE 下减容器的主力
            共享专家÷ TP。在 EP 域内每卡复制一份完整的，EP 帮不上忙
            Attention / Dense MLP÷ TP
            router / gate不切。量级小，但逐层累加不完全可忽略
            Embedding / LM Head看是否沿词表维做 TP —— 这是个开关，不是默认行为
            以上全部÷ PP，体现为「这张卡只背本 stage 那几层」
            DP不切，除非开了优化器并行（那时优化器状态 ÷ DP）

            三条不能省的细节

            • 各 stage 不等重。层数本来就可能不均（46/4 → 12,12,11,11）， 首段还多背 embedding、末段多背 LM head。 看平均值没有意义 —— OOM 只需要一张卡爆，要看的是最紧的那张。
            • 激活要乘在飞的 micro-batch 数。1F1B 下 stage s 同时压着 PP − s 份未反向的激活， stage0 最紧。忽略这一项会系统性低估最危险的那张卡，而且 PP 越大低估越多。
            • 运行时开销不是固定百分比。按已用量抽一个比例，等于把一个几乎不随模型变的量做成正比项： 大 EP / 大 PP 的轻卡被低估（光驱动加通信域就不止那点），重卡又虚高。

            预留那一段随什么变

            项跟着什么走
            通信 buffer∝ 通信域个数。每个 >1 的并行维一个，MoE 的 all-to-all 另起一条
            算子 workspace∝ 一层的 token 张量。峰值由单个最大算子决定，不是全部层的和
            分配器碎片∝ 已用量。六段里只有这一项本来就该按比例算

            为什么不能卡到 100%

            上面算的都是稳态值，而通信 buffer 与碎片本身还在逐 step 波动。 经验上越过 70% 之后这点波动就足以把余量吃光，越过 88% 基本是在等 OOM —— 那时候「还没满」并不等于「跑得下」。留出的那一截不是浪费，是波动的容身之处。

            显存不够时该动哪一维

            这是前面所有约束真正咬合的地方：每一项都能换来显存，但每一项的代价落在不同的地方， 而且都会反过来触发前两关的约束。

            动这个省下什么代价会撞上
            提 EP路由专家的权重/梯度/优化器状态，MoE 模型里最大的一块 all-to-all 通信域变大E % EP、可能还有 DP % EP
            提 PP每卡少背几层，三段参数一起降 流水线气泡变大；stage0 的在飞激活反而增加num_layers ≥ PP、micro-batch 数
            提 TP参数与激活一起降，见效最直接 通信最密的一维，跨节点即悬崖头数 / KV 头数 / intermediate 的整除，以及每节点卡数
            提 CP只降激活，长序列下才有意义 attention 内部多一轮 ring 通信seq % (2×CP)
            开重计算激活大幅下降，可到原来的十分之一量级 多一次前向，算力换显存不撞整除约束，是最容易先试的一项
            开优化器并行优化器状态 ÷ DP，权重相关字节里最大的一块 每步多一轮 all-gather需要 DP > 1 才有效
            降 micro-batch激活线性下降 算子效率下降，且要靠梯度累积把全局 batch 补回来micro-batch 数与流水线气泡
            加 DP什么都不省 —只增吞吐，是这张表里唯一的例外
            顺序上的经验：先试不撞任何整除约束的那两项（重计算、优化器并行）， 它们只在算力和一轮通信上付账；再考虑 EP / PP，它们要重新对整除关系； TP 放到最后 —— 它同时被模型结构和节点边界两头夹住，是最容易一提就撞墙的一维。
