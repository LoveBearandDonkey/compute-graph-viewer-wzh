# Config & Relation Observer · 配置兼容规则升级计划

对 `config-relation-observer` 三个模块规则层的一次审视结论与落地清单。

审视范围：

- [js/config-relation-observer.js](js/config-relation-observer.js) — `validate()` / `reconcile()` / `derive()`，整页唯一数据源
- [js/config-relation-capacity.js](js/config-relation-capacity.js) — 单卡容量的显存口径
- [js/config-relation-yaml.js](js/config-relation-yaml.js) — MindFormers yaml + msrun 启动命令的落盘口径

**总结论**：现有 5 条校验规则本身没有写错的，问题是「规则集太薄 + 三个模块各拿一套隐含假设」。
最大的一处偏差是 EP 被硬编码成正交维（`world = DP×PP×TP×CP×EP`），而主流实现里 EP 是从 DP 组内切出来的、不独占 rank。

### 行 1 落地记录（2026-08-21）

开关是 MoE 区标题右侧的 `#croEpMode`，默认「EP 切出」。实现上多出计划里没写的两处，都是行 1 自身的正确性所必需：

- `derive()` 新增 `edp = 正交 ? DP : DP/EP`，集群矩阵的 d 轴与两处按 DP 副本遍历的查询改读它。不这么做，切出档下 `ranksPerStage` 会比 world 大一个 EP 倍，矩阵直接画错。**几何和标签仍与改动前逐位相同**，行 3 只剩改名。
- `FIELD_SPECS.dp.max` 1024 → 8192：切出档的 DP 大一个 EP 倍，旧上界会在换算时夹掉值、连带改动 Total Rank。

**遗留的口子（行 2 关掉）**：把 DP 调到小于 EP（如 DP32 / EP64）时，world 公式仍然自洽、不报错，但 `edp` 退化到 1，矩阵会按 1 行 × EP 列画出比 Total Rank 更多的格子。补上 `DP % EP == 0` 的校验即消失 —— 行 2 已落地，见下。

### 行 3 落地记录（2026-08-21）

行 1 落地后页面出现了自相矛盾：表单里 DP 写着 512，矩阵左侧却标着 DP0–7。行 3 紧接着做完。

- 新增 `dAxisName(counts)` 一处判定：切出档且 EP>1 → `EDP`，否则 `DP`（稠密模型 EDP≡DP，不平添新词）。矩阵的行标签 / 组与块的 aria / 格子提示 / 格子 aria 全部走它。
- `coordsOfRank` 那行坐标文案在三处重复（关系卡片、计算血缘、事件详情），合并成 `coordLine(topology, co)` 一份，d 轴名字随口径变。
- Layer 导航的查询范围键（`#croDpScope`）文案改由 `syncDpScopeLabels()` 写：它选的正是「查一个模型副本还是全部」，副本的编号轴就是 d 轴。

**表述成本按计划里预判的那样高于实现成本**，换算式落在三处：Cluster 区标题右侧常驻一行（`矩阵纵轴 = EDP 8（DP 512 ÷ EP 64）…`，放标题行是因为矩阵的纵向预算是量 `.cro-cluster__grid` 来的，多一行会直接从格子上扣）、每个格子的悬浮提示、以及容量栏口径浮层新增的 EDP 条目。

### 行 2 落地记录（2026-08-23）

第一批收口。DP 与 EP 都是 2 的幂，所以「整除」就是 `DP ≥ EP`，实现上没有取模之外的复杂度，落点有三处：

- `validate()` 增 `!moeOrthogonal && dp % ep !== 0`。错误文案刻意把 **DP 和 EP 两个 label 都写进去** —— `emit()` 是按 `FIELD_SPECS.label` 做子串匹配来标红 stepper 的，这条错是两个字段共同造成的，两个都要红。（行 1 那条 world 公式的括注反过来，是为了**避免**误标红才把 "EP" 写成"专家并行"，两处的取舍方向相反，别照抄。）
- `reconcile()` 增修复分支：锚在 EP 上就抬 DP（Total Rank 跟着涨，与调大其它并行维手感一致），撞 `dp.max` 或锚在别处时改为把 EP 减半到能整除。减 EP 不会破坏上面那条 `routedExpert % ep`，两者都是 2 的幂。
- `isAllowedParallelValue()` 的 dp 分支增同一条。**这处不加，前两处等于白做**：拖 Total Rank 时 `fitParallelWorld` 会自己配平出一个当场报错的 DP。EP 不需要对称的一条 —— 切出档下它已被候选列表摘掉。

跑了一遍规则层（只跑 `validate`/`reconcile`，不起页面）：默认两档、旧口子 DP32/EP64、EP 抬到 1024、Total Rank 拖到 64 / 128 / 16384、DP 顶格 8192、稠密 Qwen2，**每一档的矩阵格子数都等于 Total Rank**，旧口子那档 EP 被自动收到 32。

**补一个配平卡死角（同日，来自"DP 能不能比 EP 小"的追问）**：上面第三条给 DP 钉了下限（DP ≥ EP），于是当 `pp/tp/cp` 都已降到 1、`dp` 又正好等于 `ep` 时，拖 Total Rank 往下会无维可动 —— 页面停在一条「乘积与 Total Rank 不符」的红字上，而用户看不出该去动哪枚 stepper（改前是不报错但把矩阵画错，等于把一个**静默错误换成了死胡同**）。`fitParallelWorld` 拆成外层 + `fitParallelWorldOnce`：一轮配平后若仍在目标之上且 `dp ≤ ep`，就让 EP 减半再补一轮 —— 切出档 EP 不进 world，降它不改乘积，只是把 DP 的下限放开。只在这一种不收敛上降 EP（量程外的目标降了也没用），且 `anchor === "ep"` 时不降（不把用户刚拨的那枚拨回去）。

改完把随机点 stepper 的模拟扩到两档共 **21.7 万个状态**：`dp < ep`、专家除不尽、格子数≠Total Rank、落在报错态，四项全是 0。

口径文档同步了两行：`term-dp` 的「切出口径下要满足 DP % EP」从「考虑再调」升到「一定联调」（它现在是硬约束了），`term-ep` 里那条「切出口径下 DP」补上「必须被 EP 整除」。

顺带把 `expertDataParallel()` 里「校验尚未落地，见升级计划行 2」的注释改掉 —— 那个 `Math.floor` 现在是防御性兜底，不再是已知缺陷。

### 计划外：stepper 支持手输（2026-08-23）

不在上面 14 行里，是行 2 讨论中长出来的一条 —— 2 的幂梯子拨不出 `DP=120`、`PP=3` 这类真实存在的配置，而这恰恰是讲「口径」时最需要举的例子。

**分工**：加减键维持原样（只走 2 的幂 + 联动配平）；手输负责精确指定，**不做任何联动** —— 用户明确指定一个数时，替他改掉另外三四个是错的手感。

**不兼容时的三段式**（用户定的 B 档）：当场标红「输入的那一枚 + 与它冲突的那几枚」→ **整页图形停止更新** → 表单下方横幅给出建议修法与两个出口。

- **停更是这套设计的核心**，不是附赠品。这页最会骗人的错误就是「数字和图形各说各话」（行 1、行 2 消掉的都是这一类）。冻结掐在两处：`emit()` 里不发 `cro:change`、不调 listeners；`topology` getter 在冻结期间返回上一组自洽拓扑 —— **只掐事件不掐 getter 会漏**，视图侧在窗口尺寸变化时会直接读它重算集群矩阵列数。
- **建议修法就是 `reconcile` 本身**，只是结果不落到 config 上（`proposeFix` 跑一份副本）。唯一要补的是 `anchor === "totalRank"`：补它的差额要解整数分解，而 `fitParallelWorld` 只在 2 的幂梯子上找解 —— 那是加减键该有的手感，不为手输放开，所以单独补了一条「让 DP 独自吃掉差额」的直解。
- **三个出口**：「一键应用」落建议（被改的字段闪联动高亮）、「取消修改」整份退回最近一次自洽快照（不是只还原最后一个字段 —— 手输可能连着改了几个）、或者直接点加减键把错数步进回档位。为了第三个出口，`stepValue` 的 `×2 / ÷2` 换成了 `snapPow2`：从 120 加减是回到 128 / 64，而不是在 240 / 60 上继续翻倍（值本来就在梯子上时逐位不变）。

**顺带把 `reconcile` 的修复分支从「反复减半」改成「取最近的合法值」** —— 减半那套修不动手输进来的数（120 减半是 60，仍然不整除 256）。EP 的两条整除约束借机合成了一条：EP 必须是 `gcd(专家数, DP)` 的因子（正交档只看专家数）。改完重跑 21.7 万状态的 stepper 模拟，四项指标仍全为 0，**加减键的行为逐位未变**。

**已知缺口**：手输 `Node` 给不出建议（横幅只剩「取消修改」）—— 它的修复要动 Total Rank，而 Total Rank 又由并行度乘积定死。这个缺口在**行 6** 落地后自然消失（那时 Node 变成受约束派生，不再是自由字段），故不单独补。

### 行 4 / 行 5 落地记录（2026-08-24）

第二批开头两行一起做 —— 它们是同一类约束（并行度对着一个**非并行**的量取整除），
但行 4 里藏着前三行都没出现过的一种情形，值得单记一笔。

**这两条约束页面本来就写着，只是没落成规则。** `term-tp` 的「一定联调」里早写着
「受 `num_heads` / `n_kv_heads` / `intermediate` 整除约束」，`term-cp` 正文直接给了
`seq % (2×CP) == 0` 连同它的理由。所以这次是**代码去追平文档**，文档侧只补了两句
「已落成硬校验」，没有行 3 那种表述成本。

**行 4 的形状与行 2 的 EP 同构**：TP 必须是 `gcd(heads, kvHeads)` 的因子（无 GQA 时
就是 `heads`）。算下来两个预设的合法档位是 openPangu 48 头 → 1/2/4/8/16、
Qwen2 28Q:4KV → 1/2/4。**计划里那句「48 头模型在 TP=64 处被拦」少说了一半 ——
32 同样除不尽**（48/32 = 1.5），实际是 16 封顶。

**行 9 是这份清单里第一条「capacity 与 yaml 各讲一套故事」的病**，两边的假设**正好相反**：
capacity 按「不重计算 + 开 SP」取 `actPerLayer: 34`，yaml 却写死 `recompute: True` +

**四档系数，来源是 Korthikanti et al. 2022（Megatron 那篇激活重计算论文）§4 的 sbh 系数式**：

| | 仅 TP | TP + SP |
|---|---|---|
| 不重计算 | 每卡 `sbh·(10 + 24/t)` → 系数 `10t + 24` | 每卡 `sbh·34/t` → 系数 `34` |
| 全重计算 | 每卡 `sbh·2` → 系数 `2t` | 每卡 `sbh·2/t` → 系数 `2` |

（`activationBytes` 统一再除以 TP，所以不含 `/t` 的那两档要先把 t 乘回来。）
自洽性检查：**TP=1 时四档收敛成 34 与 2 两个数**，与 SP 无关 —— 这正是它该有的样子。
`5·a·s/h` 那一项仍未计入，也没补：它只在不走 FlashAttention 的实现里才显著。

**默认档下 YAML 视图逐字不变**（两个默认值就照抄原先写死的那两行），**变的是容量柱**：
默认是全重计算，激活系数从 34 掉到 2，激活段大幅缩短 —— 这正是计划里预告的那个变化，
只不过方向是「原先高估了」。

那行的原话是「不参与切分、不进 world_size，只决定单卡装多少」，而 SP 是实打实在切

### 行 16 / 行 17 落地记录（2026-08-26）

它们各自暴露了页面一处隐含假设。

---

**行 16 的实质不是「多一枚开关」，是页面此前画了一条错误的红线。**
`seq % (2×CP)` 是 ring attention 专属的（因果掩码下序列前段算得少、后段算得多，
要对半交叉分配才均衡），而 MindSpeed MM 特性表里标 CP 的模型多数走 Ulysses ——
它沿**头**维做 all-to-all，序列长度爱是多少是多少。对那批配置，页面此前给的是一条
不存在的约束。

**新增字段 `cpMode` 进 `FLAG_SPECS`（第二枚带 `options` 的），不是进 `FIELD_SPECS`**：
它没有量程、不进 world、不参与配平，与 `shardMode` 同类。默认 `"ulysses"`。
**默认档逐位未变** —— 两个预设的 CP 都是 1，两档在 CP=1 时说的都是同一件「不切」。

**它和 EP 口径长得像，但不是同一种东西，这点值得记一笔。**
`moeOrthogonal` 是「同一批卡的两种读法」，切一下**一个数都不该变**（页面为此专门
验过六段逐位相同）；`cpMode` 换的是真的算法：拦的字段不同、并行度上限不同、通信形态
不同。唯一相同的是**显存** —— 两档都让每卡留 `S/CP` 份激活，capacity 一个数不动。
这一点必须在口径浮层里明说（已加在「序列长度」那一行）：不说的话用户拨一下发现容量柱
纹丝不动，只会以为开关没接上。

**Ulysses 那条约束是页面第一条「把两个可调字段绑在一个乘积上」的硬校验**：
`num_heads % (TP × CP) == 0`（TP 先切过一轮头，CP 接着切剩下的）。落点因此比行 4 多一层：

- `structurallyAllowed` 从只判 `tp` 扩成判 `tp / cp / vpp` 三个字段，**tp 与 cp 互为条件**：
  cp>1 时 TP 的合法集要看 cp，反之亦然。两边都跳档（不是只跳一边），否则加减键能把
  页面推进一个 `reconcile` 修不动的报错态。openPangu 实测可达档：
  `tp=1 → CP 1/2/4/8/16`、`tp=2 → 1/2/4/8`、`tp=4 → 1/2/4`、`tp=8 → 1/2`。
- 悬浮理由多一档：TP 到顶时若 CP 也在切头，尾句从「这几个数都是模型常量」改成
  「头数改不了，但 **CP 是可调的**，把它调小就给 TP 腾出了档位」—— 这一头卡住时，
  出路第一次不在模型常量之外，得说出来。
- `reconcile` 按锚点决定动谁（Ulysses 的对手是 TP，Ring 的对手是 seqLen），与
  「序列除不尽 2×CP」同形。

**⚠️ 验证跑出来一个真 bug，值得单记：联动修出来的值必须留在 2 的幂梯子上。**
CP 的合法基数会带奇因子 —— `heads 48 / TP 8 = 6`，`nearestDivisor` 会给出 3 或 6。
`fitParallelWorld` 只在 2 的幂上配平，于是 CP=3 让 world 永远卡在 `3·2^k`、
凑不回 `2^15` 的 Total Rank，页面停在一条**它自己造出来的**红字上（3 万步走查里出现 10 次）。
前 15 行没踩到，是因为此前所有修复分支的基数恰好都是 2 的幂
（`tpShardBasis` = 16、`gcd(专家数, DP)` 两边都是 2 的幂）。新增
`nearestPow2Divisor` 只给这一处用 —— **手输仍可停在 3**（那是用户明确指定的，validate 也认），
但联动不该产生一个用户没要求、页面又收不回来的数。

软警告新增一条 `Ulysses 档：TP × CP > 每节点卡数`：两者争同一批头也争同一条链路，
组内卡数是**乘起来**的 —— TP 单独没超节点、乘上 CP 就超了，是这一档特有的坑。
顺带把行 7 那条 GQA 的 KV 复制警告从只看 `TP` 改成看 `TP × CP`（Ulysses 档）；
**⚠️ 判据改对了，但穷举验过：在当前两个预设上仍然不可达**（Qwen2 的 TP 被
`gcd(28, 18944) = 4` 顶死，Ulysses 档下 `TP×CP` 又必须整除 28，2 的幂梯子上只凑得出
1/2/4，全都整除 KV 头数 4）。留着是因为换个 heads:kvHeads 比值更大的模型它就活了，
而那时若判据只看 TP，Ulysses 档会漏报。

yaml 新增 `context_parallel_algo`（只在 CP>1 时写，`ulysses_cp` / `colossalai_cp`），
`context_parallel` 与 `model_parallel` 的行尾注释按档分写。顺手补了 `L()` 一直缺的一条

---

**行 17 的账全在激活上，这正是它值得做的理由。** VPP 一张卡都不多占（**不进 world 的乘积**），
它只是把本卡已有的那几层再拆成 VPP 段轮流跑：气泡按 `1/VPP` 缩小，代价是每张卡同时压着的
未反向激活变多。页面此前把 `inflight = PP − s` 写死成非交错 1F1B，「各 PP Stage 峰值」
那排小柱**已经画着这一项、却没有旋钮能动它**。

**在飞份数用交错式 1F1B 的逐 stage 式，而不是论文那个整体因子：**

```
inflight(s) = [ 2(PP−s−1) + (VPP−1)·PP + 1 ] / VPP
```

前半是 warmup 要多灌的份数，`+1` 是正在算的那一份，`÷ VPP` 是因为每一份只压着
**一个 chunk**（本卡层数的 1/VPP）、要折回「整段 stage」的单位。
`s = 0` 时它化简成 `PP·(1 + (PP−1)/(PP·VPP))` —— **正是 Korthikanti et al. 2022 §2.2
给的交错式内存惩罚因子**（本页 `actPerLayer` 的四档系数也出自这一篇），
`PP ∈ {2,4,8} × VPP ∈ {2,3,4}` 九组逐位相等，已核。
两条分支**不能合并成一个式子**：VPP=1 时框架走的是另一套调度（Megatron 在 vpp 为空时
用非交错路径），把上式代到 VPP=1 会算出 `1.75×PP`，那不是页面此刻画的东西。

实测（openPangu 48 层 / PP4 / 2048 卡 / ZeRO-1，Stage0 → Stage3 的激活 GB）：

| | S0 | S1 | S2 | S3 |
|---|---|---|---|---|
| VPP=1（在飞 4 / 3 / 2 / 1） | 0.94 | 0.70 | 0.47 | 0.23 |
| VPP=2（在飞 5.5 / 4.5 / 3.5 / 2.5） | 1.29 | 1.05 | 0.82 | 0.59 |
| VPP=6（在飞 4.5 / 4.17 / 3.83 / 3.5） | 1.05 | 0.98 | 0.90 | 0.82 |

读法：**整排小柱一起抬高，而且变平** —— 末段抬得比首段还多（VPP=6 时 0.23 → 0.82，
而首段只从 0.94 到 1.05）。VPP 越大首段越接近非交错档，末段却越重，因为
`inflight(末) = ((VPP−1)·PP + 1)/VPP` 随 VPP 单调升向 PP。

**VPP 比 PP 严格，而这一条在默认预设上立刻咬人。** 交错式要求每段等长，
`层数 % (PP × VPP) == 0`；而本页的 PP 允许不均分（46/4 → 12,12,11,11）。
openPangu 的 **46 层连 PP=4 都除不尽**，`46 % (4×v)` 对任何 v>1 都不为 0 ——
**默认档下 VPP 只能是 1**。这不是缺陷而是这一行最该讲的一句话，落到三处：
`MODEL_PRESETS` 的注释、VPP 加号的联动、`term-vpp` 正文。

按加号时**抬 `Total Layer`（46 → 48）而不是收 VPP**：它是这条约束里唯一一个改了
**不连累卡数**的对手字段（动 PP 会改 Total Rank）。所以 VPP 走的是「有对手字段」那条路
（步过去再联动修，与 `pp > totalLayer` 同形），`structurallyAllowed` 里只判
「PP=1 时没有流水线可交错」这一半。`reconcile` 里这一段放在**配平之后** ——
PP 可能刚被 `fitParallelWorld` 改过。
`nearestVpp` 不能写成 `nearestDivisor(层数/PP, …)`：层数未必被 PP 整除，那样会取到一个
乘起来仍除不尽的档。

**⚠️ 明确的已知简化：本页只建模 VPP 的调度代价，不改层 → stage 的画法。**
真实交错式流水下 stage0 持有的是分散在全模型各处的几段（chunk 0、chunk 4……），
而 Layer 导航 / 整网 deck / 集群矩阵仍按连续分段显示。改这一处要动 deck pattern 的
`stageRanges` 契约（它收的是连续区间 `[lo, hi]`），`derive()` 的 `stages` 也得从
「一段」变成「一组段」，牵连面远超这一行 —— 与 `MOE_SHARD_MIN` / `fsdpPrefetch` 一样
写进 `term-vpp` 让用户看得见，而不是埋在注释里。

yaml：VPP 在 MindFormers 里**不在 `parallel_config` 段**（分写在 `parallel.pipeline_config`
与 `model_config` 两处），所以只在 VPP>1 时给两行 `#` 标注 —— 与行 15 的 FSDP2 同一种处理：
本页算的是什么、落到框架里对应哪个键都写出来，但不伪造一个可以直接照抄的项。
`micro_batch_num` 从 `4×PP` 改成 `max(4×PP, PP×VPP)`（VPP ≤ 4 时数一个没变），
因为交错式的 warmup 本身就要灌 `(VPP−1)·PP` 份，micro-batch 少于它，交错换来的气泡收益直接归零。

### 行 18 / 行 19 落地记录（2026-08-26）

做完之后 batch 行也长出了一枚「高级选项」折叠 —— 判据与 parallel 那一行**不是同一条**，
这是这轮最值得记的一处。

---

**行 19 兑现的是行 9 自己记下的缺口。** 那条 title 的末句原话就是「要调中间档，这枚开关得
换成一枚有档位的控件」。34 与 2 之间差着一个数量级，而**实际调优最常落的正是中间**。
`FLAG_SPECS.recompute` 整枚换成 `recomputeMode`（第三枚带 `options` 的），
**`"full"` 就是原先那个 `true`**，所以默认档一个数都没变（实测峰值仍是 10.9 GB / 17%，
与行 15 / 17 记录逐位相同）。

**四档的系数不是估的，是从行 9 同一篇里读出来的。** Korthikanti et al. 2022 §4 把每层
`34·sbh` 拆成 **attention 11 + FFN 19 + LayerNorm 4**，其中 10 是 TP 复制的、24 是 TP
切得动的（10 = 两个 LN 输入 4 + 两段 block 输入 4 + 两个 dropout mask 2；
24 = attention 内部 8 + FFN 内部 16）。于是：

| 档 | 留下什么 | 开 SP | 关 SP |
|---|---|---|---|
| 关 | 全留 | 34 | 10t + 24 |
| 选择性 | 重算 FFN 段，只留它的输入 | **17** | 9t + 8 |
| 按层数 | 前 N 层按全开、其余按关 | 逐层混合 | 逐层混合 |
| 全开 | 只留每层输入 | 2 | 2t |

自洽性检查：**TP=1 时三个系数收敛成 34 / 17 / 2，与 SP 无关** —— 与行 9 那两档同一个性质，
已断言。实测激活 15.9 → 8.0 → 0.9 GB，**选择性正好是关的一半**（比值恰为 17/34）。

**⚠️ 「选择性」的口径必须写出来，因为真实框架里它不是一个定值。**
MindFormers 的 `select_recompute` 收的是**算子名正则**，常见默认只挑 FFN 里的 SiLU / mul，
落点在 17 与 34 之间；本页取「整个 FFN 段」这一端。而 **Megatron 的
`--recompute-granularity selective` 没有列成一档** —— 它重算的是 attention 里的
softmax/dropout（`5·a·s²/h` 那一项），而本页按 FlashAttention 建模、这一项**本来就不计入**
（行 9 的记录里已注明），那一档在本页等于「关」。列进去等于给用户一个拨了什么都不变的档。
两处都写进了 title、`term-recompute` 与 yaml 的行尾注释。

**「按层数」是这一栏第一个逐 stage 分别生效的旋钮。** 实测 N=4：

| | S0 | S1 | S2 | S3 |
|---|---|---|---|---|
| 关（12/12/11/11 层全留） | 15.9 | 12.0 | 7.3 | 3.7 |
| 按层数 N=4 | 10.9 | 8.2 | 4.8 | 2.4 |

读法：**整排小柱一起变矮、而且变平** —— Stage0 降 5.0 GB、末段只降 1.3 GB，
因为同样重算一层，在飞份数多的那一段省下的绝对值就多。这正是行 19 预告的
「激活段可以停在中间高度」。

**⚠️ 明确的已知简化：N 是一个统一的数，不是逐 stage 各填一个。** MindFormers 的数组允许
`[8,4,4,0]` 这种按 stage 定制（真实调优里确实有人这么单独压 Stage0），而本页只给一个 N ——
PP 最大 128，一行表单摆不下 128 枚 stepper。截断（`min(N, 本段层数)`）已经让各段不等，
但计划里那句「单独压平某一根」**没有做到**，这条写进了 `term-recompute` 让用户看得见，
不埋在注释里 —— 与 `MOE_SHARD_MIN` / `fsdpPrefetch` / VPP 的 stage 画法同一种处理。

yaml 写出去的是 `recompute: [4, 4, 4, 4]`（框架本来的语法），**截断口径与容量栏共用一条** ——
两个视图不能各讲一套，这是行 9–12 治的那个病。默认档（full）仍是
`recompute: True` + `select_recompute: False`，与改动前逐字相同。

## 附：行 1 的推导（为什么说 EP 不该独占 rank）

现在页面把 EP 当正交维硬编码在两处：

- [js/config-relation-observer.js:10](js/config-relation-observer.js#L10) — `world = DP × PP × TP × CP × EP`，注释写「EP 不从 DP×TP 里切出来」
- [js/config-relation-yaml.js:109](js/config-relation-yaml.js#L109) — `expert_parallel: 64  # 即 EP，与 DP 正交`

但主流实现（Megatron / MindSpeed-LLM / MindFormers）都是切出式：world_size 只由 `DP × PP × TP × CP` 决定，EP **不进乘积**，而是把 DP 组再切一刀，约束是 `DP % EP == 0`（严格些是 `DP × TP % (EP × ETP) == 0`）。EP 不独占 rank —— 一张卡既是某个 DP 副本的成员，又是某个 EP rank 的持有者。

**关键点：参考配置在切出口径下其实是自洽的，只是 DP 被标错了。**

`dp=8, pp=4, tp=1, cp=1, ep=64 → 2048`，换成切出口径：

```
真 DP  = 2048 / (PP4 × TP1 × CP1) = 512
EDP    = 512 / EP64               = 8      ← 这就是配置里写的那个 "8"
```

两种口径算出来的 total rank 恰好都是 2048，所以一直没穿帮。

好消息是 `derive()` 里的 rank 编址
[js/config-relation-observer.js:342-346](js/config-relation-observer.js#L342-L346)
`r = s·(DP·EP·TP·CP) + d·(EP·TP·CP) + p·(TP·CP) + …`
在切出口径下**几何完全正确** —— 那 512 个 rank 本来就该按 `8 EDP × 64 EP` 排成网格。集群矩阵一个格子都不用改，错的只是命名和校验公式。

开关的联动面：

| | 正交（现状） | 切出（建议默认） |
|---|---|---|
| world | `DP×PP×TP×CP×EP` | `DP×PP×TP×CP` |
| 新增校验 | 无 | `DP % EP == 0` |
| 矩阵 d 轴 | DP | EDP（`DP/EP`） |
| yaml 注释 | 「与 DP 正交」 | 「从 DP 内切出，EDP=DP/EP」 |

[js/config-relation-capacity.js:574](js/config-relation-capacity.js#L574) 那句「EP 与 DP 是否正交的口径差异均未计入」说明这个洞已被意识到，只是没落成规则。

> ⚠ 未核实项：本仓内没有 MindFormers 具体版本的校验式证据，上述按 Megatron/MindSpeed 通行做法推得。
> 落地前建议拿实际使用的 MindFormers 版本核一下 `parallel_config` 的 device_num 校验。
