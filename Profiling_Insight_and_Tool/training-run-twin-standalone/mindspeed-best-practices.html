Drill-down 02 · Practice guide

最佳实践与排障

直接从仓库里的真实配置出发：32K 长序列怎么配 Ring、16K 场景怎么开 2D-TP、Llama2 OOM 怎么接 SmartSwap，以及 16 卡以上如何启动 Auto Settings。

Concrete playbooks

三个可以照着改的实例

每个实例都来自仓库脚本或特性文档，不是为了说明界面而虚构的参数。

CASE A · 32K LONG CONTEXT

8 卡 Llama2：Ring + Double Ring

目标是用 TP1 / PP2 / CP4 处理 32K 序列，并让通信与计算重叠。

TP=1
PP=2
CP=4

--seq-length 32768
--context-parallel-algo megatron_cp_algo
--cp-window-size 2
--use-cp-send-recv-overlap
--use-fused-ring-attention-update
--recompute-in-bubble
  • 仓库入口： feature_tests/ring_attention.sh
  • 关键判断： 32K / CP4 = 每卡 8K 序列块
  • 真实约束： cp-window-size 必须整除 CP；窗口增大不一定更快
CASE B · 16K LARGE TP

8 卡 Llama2：2D Tensor Parallel

把 TP4 拆成 2×2，并打开 AG / RS 与 MatMul 的通算重叠。

TP=4
PP=1

--seq-length 16384
--tp-2d
--tp-x 2
--tp-y 2
--enable-overlap-ag-with-matmul
--enable-overlap-matmul-with-rs
--overlap-grad-reduce
--overlap-param-gather
--swap-attention
  • 仓库入口： feature_tests/tp2d.sh
  • 当前实例： 4 层、MBS1、GBS4、BF16
  • 适用问题： TP 域较大、1D-TP 通信效率下降
CASE C · OOM RECOVERY

Llama2：用 SmartSwap 替代部分重计算

训练 OOM 时让系统采集张量生命周期、搜索换出策略，再进入稳定执行阶段。

# 训练脚本追加
--smart-swap

# 可选策略配置
policy_v2 = True
policy_pref = BETTER_PERFORMANCE
swap_bucket_size = -1
num_attn_layers_per_stage = 1
  • 文档实例 1： 8p / PP1 / 8K / 32 层，TP8→TP1，收益 25%
  • 文档实例 2： 8p / PP1 / 16K / 40 层，关闭全重计算，收益 28%
  • 代价： 每卡换出 30GB 时，8 卡主机至少需 240GB Host 内存
别机械复制：Ring 案例使用固定序列；SmartSwap 文档明确说明暂未适配动态序列 / MoE。这里展示的是仓库给出的起点和边界，不是任意模型都能直接套用的万能参数。

Case D · Auto settings

16 卡以上自动搜并行配置

Auto Settings 不是概念功能。把下面参数加到原训练脚本，它会多次拉起裁剪后的 Profiling，并在工作目录留下建模文件和日志，最后打印 Top-3。

仓库文档给出的真实启动参数
--auto-settings \
--auto-settings-type mixed \
--auto-settings-work-dir ./auto_settings_dir \
--auto-settings-ranks 16 \
--auto-settings-log-level debug \
--target-nnodes $NNODES \
--nproc-per-node $GPUS_PER_NODE \
--master-addr $MASTER_ADDR \
--master-port 6005 \
--node-rank $NODE_RANK
实际会发生：解析模型与硬件 → 生成多组 Profiling 配置 → torchrun 拉起短任务 → 解析算子、通信和内存 → 搜索候选 → 输出显存可行且预测性能靠前的三组配置。最低搜索规模在当前文档中标为 16 卡。

Five-step workflow

五步调优流程

这是用户指南明确给出的主流程。第一步必须运行一次带 Profile 的任务，后续分析可复用采集结果。

01 / COLLECT采集 Profiling选择最小 step 窗口、目标 ranks 与采集等级。
02 / COMPUTE分析算子耗时识别长耗时算子和计算利用率问题。
03 / COMM分析通信耗时判断未被计算掩盖的通信与扩展效率。
04 / MEMORY分析显存使用定位峰值、OOM 风险及各 stage 偏差。
05 / ACT选择优化策略按瓶颈类型选择并行、融合、Swap 或重计算。

Repository principles

五条最佳实践

这些原则比具体参数更稳定，适合作为调优工作流的默认护栏。

先诊断后优化先用 Profile 找瓶颈，再选择特性。
从简单开始先调整并行策略，再引入复杂机制。
逐步验证每次只改变一个变量并保留基线。
看整体吞吐不要只看单步或单个算子耗时。
结合硬件特性按昇腾拓扑和算力 / 带宽选择策略。

Minimal recipe

最小 Profile 配方

用户指南给出的采集入口，可作为诊断向导的默认模板。

仅采集第 5 个 step、Rank 0，并记录 CPU 与 shape
python your_train_script.py \
  --profile \
  --profile-step-start 5 \
  --profile-step-end 6 \
  --profile-ranks 0 \
  --profile-level level1 \
  --profile-with-cpu \
  --profile-record-shapes \
  --profile-save-path ./profile_dir
