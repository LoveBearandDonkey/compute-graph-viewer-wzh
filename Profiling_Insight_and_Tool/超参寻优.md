# 超参寻优(HPO)业界最佳实践 + 权威资料链接
> 术语：行业标准叫法：**超参数优化(HPO) / 超参寻优**；产品UI常用“超参寻优”，论文/技术文档用“超参数优化”。

## 一、核心最佳实践（工业界落地总结）
1. **算法选型**
    - 小算力、简单任务：**随机搜索 Random Search**（强基线，优于网格搜索）
    - 中等算力：**贝叶斯优化(TPE/BO)**，Optuna默认TPE；适合训练代价高
    - 大模型/深度学习：**多保真度HPO（Hyperband / BOHB）**，支持剪枝，提前丢弃差的trial，节省50‑70%算力
    - 不推荐网格搜索：高维超参空间下算力浪费巨大。
2. **搜索空间设计**
    - 学习率、weight‑decay：**对数均匀分布 log‑uniform**，不要线性；
    - 整数参数（epoch、n_head）：离散区间；
    - 类别参数（优化器、调度器）：类别搜索；
    - 先宽空间粗搜，再收缩范围做细搜；**不要把所有参数全部扔进搜索**，固定领域已知的稳定超参。
3. **剪枝Pruning（深度学习必备）**
    训练早期就终止性能差的试验，只保留有希望配置；Optuna、Ray Tune、BOHB都支持。
4. **实验与验证规范**
    - 先在**小数据集/子集**跑HPO，得到候选配置，再用完整数据集验证；
    - 必须记录全部trial：参数、指标、训练日志，保证可复现；
    - 多目标：同时优化精度、显存、推理延迟，输出帕累托前沿；
    - 设置最大trial数、超时，防止算力爆炸。
5. **大模型预训练/微调特殊实践**
    - 优先使用**µP(μ‑Transfer)**：小模型调参迁移到大模型；
    - 不要盲目对全部超参做HPO；优先调：学习率、warmup、weight‑decay、global batch size；
    - 预训练：优先参考缩放定律，再做小范围寻优，不做暴力全空间搜索。

## 四、`config-relation-observer` 与“配置寻优”的定位分析

### 1. 结论

业界有这类业务，但当前页面更准确地说是**训练配置分析与规划**，还不能完整称为“配置寻优”。它已经具备寻优系统很有价值的前置能力，却缺少“定义目标—搜索候选—运行评测—选出最优”这个闭环。

当前页面可以定义为：

> 面向大模型分布式训练的配置约束分析、资源预估、可行性校验与配置规划工具。

它比普通 YAML 编辑器强很多，也比单纯的显存计算器完整，但目前主要回答的是：

- 这份配置是否合法？
- 哪里会出问题？
- 改一个参数会影响什么？
- 预计能不能装下？
- 怎么改成一组可运行配置？

它尚未完整回答：

- 在所有合法配置里，哪一组吞吐最高？
- 给定 256 张卡，哪一组训练时间最短？
- 在显存余量不低于 10% 的条件下，最优 TP/PP/CP/EP 是什么？
- 推荐配置比当前配置快多少，证据来自估算还是实测？

后面这些问题才是“寻优”的核心。

### 2. 当前页面实际在做什么

#### 2.1 配置约束检查

页面会检查并行度乘积、模型结构整除关系、EP/DP 口径、TP/CP 与头数、层数与 PP/VPP 等硬约束。页面把问题总结成“配得通、切得开、跑得下”三关，这个定位非常准确，见 [config-relation-observer.html](training-run-twin-standalone/config-relation-observer.html#L584)。

#### 2.2 配置联动与修复

用户输入不兼容参数后，系统会保留输入锚点，计算一组兼容修改，展示字段变化并提供“一键应用”。这属于**约束求解/配置修复**，还不是全局寻优，见 [config-relation-observer.js](training-run-twin-standalone/js/config-relation-observer.js#L1865)。

#### 2.3 静态资源仿真

页面估算每个 PP Stage 的权重、梯度、优化器状态、激活、运行时预留和 OOM 风险，并按当前状态给出调大 EP、PP、重计算、ZeRO/FSDP2 等建议，见 [config-relation-capacity.js](training-run-twin-standalone/js/config-relation-capacity.js#L790)。

#### 2.4 配置解释与转换

页面支持关系视图、YAML 视图、配置文档、外部配置导入、样例配置解析和未映射键展示，见 [config-relation-observer.html](training-run-twin-standalone/config-relation-observer.html#L52)。

因此，当前页面的本质更接近：

> 约束求解器 + 配置数字孪生 + 资源预检器。

### 3. 能不能叫“配置寻优”

可以把“配置寻优”作为未来的上层业务名，但不建议现在直接用它命名当前页面。

| 名称 | 对当前页面是否准确 | 说明 |
|---|---:|---|
| 配置关系观测 | 准确但偏技术 | 强调联动关系，弱化了校验和建议能力 |
| 训练配置分析 | 很准确 | 包含导入、解释、校验、容量评估 |
| 并行配置规划 | 很准确 | 突出 TP/PP/CP/EP 和硬件资源规划 |
| 配置诊断与建议 | 准确 | 突出错误、预警和一键修复 |
| 配置寻优 | 目前偏大 | 暗示存在目标函数、搜索、试验和最优结果 |
| 分布式训练配置自动调优 | 完整形态最合适 | 适合真正形成自动闭环后使用 |

比较稳妥的产品结构是：

- 上层能力：**训练配置寻优**
- 当前页面：**配置分析**
- 后续页面：**自动寻优**
- 结果页面：**候选对比 / 试验记录**

另外，不建议把当前能力直接叫“超参寻优”。页面里大多数旋钮是系统与并行配置，例如 TP、PP、CP、EP、VPP、ZeRO/FSDP、重计算、精度和卡数；它们主要优化显存、吞吐和通信，并不直接优化模型收敛。学习率、warmup、weight decay 等传统 HPO 参数目前反而没有出现。

可以把参数明确分成三类：

- **模型与训练语义**：层数、序列长度、LoRA Rank、全局 Batch 等。
- **系统性能配置**：TP、PP、CP、EP、VPP、MBS、重计算、分片、精度。
- **资源与环境约束**：卡型、卡数、节点数、拓扑。

“配置寻优”主要面向后两类；“超参寻优”主要面向第一类以及学习率、优化器等收敛参数。把它们混在一起搜索，用户可能在不知情的情况下改变训练目标本身。

### 4. 业界是否有类似业务

有，而且最近似的是“大模型训练 Auto Configurator”，而不是传统 Optuna 式 HPO。

#### 4.1 NVIDIA NeMo Auto Configurator

这是最直接的对标产品。它能够：

- 推荐模型规模；
- 估算训练时间；
- 生成基础配置；
- 搜索 TP、PP、CP、EP、MBS、Activation Checkpointing；
- 对候选配置做短训练；
- 比较性能并输出最优配置；
- 单独记录 OOM 失败候选。

这几乎就是当前页面继续向前发展后的形态。尤其值得注意的是，它并不是只用公式宣布“最优”，而是“规则生成候选 + 短训练实测 + 选最优”。参考：[NVIDIA NeMo Auto Configurator 官方文档](https://docs.nvidia.com/nemo-framework/user-guide/25.02/usingautoconfigurator.html)。

#### 4.2 DeepSpeed Autotuner

DeepSpeed 会结合模型信息、系统信息和启发式规则，调节 ZeRO stage、单卡 micro-batch 及其他 ZeRO 参数，并用实际训练吞吐选择配置。官方示例明确展示了多次 experiment、best metric 和 best configuration。

当前页面中的 ZeRO-1/FSDP2、Micro Batch、OOM 判断、硬件相关建议，与 DeepSpeed Autotuner 的业务非常接近；区别是当前页面还是交互式单配置推演，没有批量试验执行。参考：[DeepSpeed Autotuning 官方文档](https://www.deepspeed.ai/tutorials/autotuning/)。

#### 4.3 SageMaker、Kubeflow Katib

这两类属于传统 HPO 平台：用户指定搜索范围和目标指标，平台运行多个训练任务，按目标指标选择最好的一组。SageMaker 对 HPO 的定义就是“运行多个训练作业，按指定指标寻找最佳模型”；Katib 则进一步提供贝叶斯优化、TPE、随机搜索、Hyperband、早停等算法。

它们是可借鉴的平台形态，但不如 NeMo Auto Configurator 与当前页面贴近。参考：[AWS SageMaker Automatic Model Tuning](https://docs.aws.amazon.com/sagemaker/latest/dg/automatic-model-tuning.html)、[Kubeflow Katib](https://www.kubeflow.org/docs/components/katib/overview/)。

### 5. 当前页面离“配置寻优”还缺什么

可以用一个简单判据：

> 寻优 = 搜索空间 + 约束 + 目标函数 + 候选评测 + 最优选择。

当前完成情况如下：

| 能力 | 当前状态 |
|---|---|
| 搜索空间 | 有参数及量程，但没有“哪些参数参与本次搜索”的定义 |
| 约束系统 | 已经比较强，是页面目前最成熟的部分 |
| 目标函数 | 没有 |
| 候选生成 | 没有批量生成，仅对当前输入做局部配平 |
| 候选评测 | 只有静态显存估算，没有批量短跑吞吐 |
| 结果选择 | 没有排名、最佳配置或帕累托前沿 |
| 试验管理 | 没有 trial、预算、早停和可复现记录 |

还要注意估算可信度。页面已经明确标注运行时开销系数“待实测标定”，昇腾 950 的 HBM 也是占位值，见 [config-relation-capacity.js](training-run-twin-standalone/js/config-relation-capacity.js#L153) 和 [config-relation-observer.js](training-run-twin-standalone/js/config-relation-observer.js#L170)。在这些数据未校准前，适合叫“估算、预检、建议”，不宜承诺“最优”。

运行事件目前也主要是静态案例数据，部分血缘明确使用 `buildMockLineage`，尚未形成真实 trial 数据回流，见 [config-relation-observer.js](training-run-twin-standalone/js/config-relation-observer.js#L5320)。

### 6. 当前页面可以向 HPO 学什么

最值得吸收的不是直接把 Random Search、TPE 按钮搬过来，而是把“单配置分析”升级为“有预算的候选实验闭环”。

#### 6.1 增加优化目标

允许用户先回答想优化什么，例如：

- 最大吞吐 tokens/s；
- 最短单 step 时间；
- 最短预计训练时间；
- 最低卡时成本；
- 最大显存余量；
- 在固定卡数下支持最大序列长度；
- 在吞吐损失不超过 5% 时最省显存。

没有目标函数，就只能给“合法建议”，不能给“最优建议”。

#### 6.2 建立搜索空间编辑器

让用户区分：

- 固定参数；
- 可搜索参数；
- 派生参数；
- 不允许改变训练语义的参数。

例如，一次“纯性能寻优”可以搜索 TP/PP/CP/EP、MBS、VPP、重计算、分片策略，但锁定层数、序列长度、模型结构和 LoRA 类型。

本文前面强调“不要把所有参数全部扔进搜索”，这个原则对当前页面尤其重要。

#### 6.3 把现有规则引擎用作候选剪枝器

推荐流程：

```text
用户目标与资源约束
→ 枚举候选配置
→ 当前规则引擎过滤非法配置
→ 静态容量模型过滤预计 OOM
→ 对剩余候选做少量 warmup/短跑
→ 提前淘汰低吞吐候选
→ 输出排名或帕累托前沿
→ 用完整训练配置复验 Top-K
```

这比直接对所有组合使用贝叶斯优化更适合当前参数空间，因为 TP/PP/CP/EP 多为有限离散值，而且存在大量严格整除约束。可以优先采用：

- 约束枚举或启发式生成候选；
- 静态估算做第一轮剪枝；
- Successive Halving/Hyperband 思想控制短跑预算；
- 候选空间仍很大时，再使用随机搜索、TPE 或贝叶斯优化。

#### 6.4 引入 trial 与对比视图

每个候选至少记录：

- 完整配置快照；
- 估算显存与实测峰值；
- 吞吐、step time、通信占比；
- 是否 OOM、失败阶段与原因；
- 运行卡型、框架版本、模型版本；
- 推荐分数和淘汰原因。

这对应本文前面提出的“记录全部 trial、指标和日志，保证可复现”。

#### 6.5 支持多目标，而不是只给一个“最佳”

训练系统配置通常没有唯一最优解。例如：

- 配置 A：吞吐最高，但显存占用 94%；
- 配置 B：吞吐低 3%，显存占用 78%；
- 配置 C：吞吐低 7%，但节点数减少一半。

因此更适合输出帕累托前沿，并提供“性能优先、稳健优先、成本优先”三个推荐档。

#### 6.6 让运行事件反向校准估算模型

当前页面最有潜力形成差异化的一点，是它同时有“配置关系”和“运行事件”。理想闭环可以是：

1. 配置阶段预计显存 52 GB；
2. 短跑实测 57 GB；
3. 系统把差异归因到 workspace、通信 buffer 或碎片；
4. 更新对应卡型、框架版本的校准系数；
5. 下一次候选评估展示“估算值、校准值、置信区间”。

这会比纯 HPO 平台更有解释力，也比只给结果的自动配置器更容易让工程师信任。

### 7. 最终建议

这项业务是成立的，而且业界已有明确需求和成熟参照。当前页面已经具备一个配置寻优系统里最难做好的部分之一：复杂约束建模、配置解释、显存分解和修改建议。

但当前阶段建议这样定性：

> 当前是“训练配置分析/并行配置规划器”，是配置寻优的前置引擎；加入搜索目标、候选批量生成、短跑评测、trial 管理和最优选择后，才适合正式叫“分布式训练配置寻优”或“训练配置自动调优”。

它不应该照搬传统 HPO，而应走一条更贴合自身优势的路线：

> **规则过滤 + 解析估算 + 短跑实测 + 多目标推荐 + 可解释回溯。**

## 五、面对 NeMo、DeepSpeed 与 MindSpeed Auto Tuning 的差异化竞争策略

### 1. 核心判断

不要把产品做成“另一个 TP/PP/CP/EP 搜索器”。这一层已经相当拥挤，而且 MindSpeed Auto Tuning 比 NVIDIA、DeepSpeed 更接近直接竞争面。

更有机会的定位是：

> **面向异构大模型训练的、跨框架、可解释、运行闭环的配置决策系统。**

它不只回答“推荐哪组参数”，还要回答：

- 为什么推荐？
- 为什么其他候选被淘汰？
- 估算依据是什么、可信度多高？
- 配置换一个框架后语义是否仍然相同？
- 实际运行为什么偏离预测？
- 这次运行能否让下一次推荐更准确？

### 2. 竞品已经占住的位置

| 产品 | 已有优势 | 留出的空间 |
|---|---|---|
| NeMo Auto Configurator | 启发式生成 TP/PP/CP/EP/MBS/重计算候选，短跑评测吞吐，输出成功和 OOM 结果 | 强绑定 NeMo；主要结果仍是配置和 CSV；官方当前支持范围集中于若干 GPT 类模型 |
| DeepSpeed Autotuner | 基于模型与系统信息调 ZeRO、MBS 等，以实测吞吐选最佳配置 | 重点是 DeepSpeed 自身参数；搜索维度和跨框架语义有限 |
| MindSpeed Auto Tuning | Profiling 黑盒建模、“以小仿大”、算子性能知识库、内存与性能预测、推荐 Top 3 | 已覆盖昇腾并行策略自动搜索，因此“支持昇腾”本身不是差异化 |
| 当前页面 | 配置关系解释、硬/软约束、显存分解、一键修复、YAML 导入、运行事件关系 | 缺少真实候选搜索、profiling、实测校准和 trial 闭环 |

NeMo 会先用启发式生成候选，再短跑、比较吞吐并记录 OOM；其当前文档还明确限制在若干 GPT 系模型范围内。参考：[NVIDIA NeMo Auto Configurator](https://docs.nvidia.com/nemo-framework/user-guide/25.02/usingautoconfigurator.html)。

DeepSpeed 已经可以自动调 ZeRO stage、单卡 micro-batch 和部分 ZeRO 配置，并按实际训练计时选择结果。参考：[DeepSpeed Autotuning](https://www.deepspeed.ai/tutorials/autotuning/)。

MindSpeed 更值得重视：它采用 profiling 黑盒建模、支持小规模推测大规模、维护算子性能知识库，并已覆盖 DP/TP/PP/VPP/CP/EP、ZeRO-1、MBS、重计算、MC2 等配置。参考：[MindSpeed Auto Tuning](https://gitee.com/ascend/MindSpeed/blob/7b8f3c19d0efea459c3b438063d81c0183ebdd8c/docs/features/auto_tuning.md)。

所以，单靠以下能力很难形成壁垒：

- 多支持几个搜索算法；
- 枚举更多 TP/PP/CP/EP 组合；
- 做一个更漂亮的候选配置列表；
- 给出一个“预计最优吞吐”；
- 只强调支持昇腾。

### 3. 最值得建立的五层差异化

#### 3.1 跨框架“配置语义中间层”

这是最现实、也最容易建立长期壁垒的一层。

NeMo、DeepSpeed、MindSpeed 的优化器主要服务自己的配置体系，而当前页面已经在处理：

- MindFormers YAML；
- MindSpeed/Megatron Shell 参数；
- DeepSpeed JSON；
- 不同 EP 口径；
- Ulysses、Ring 等 CP 算法；
- ZeRO-1、FSDP2；
- `full_batch`、MBS、GBS、微批数之间的语义差异。

应当把它正式发展成统一的 `Training Config IR`：

```text
外部配置
  ↓ 解析与来源追踪
统一配置语义 IR
  ↓
约束图 / 容量模型 / 性能模型
  ↓
MindFormers / MindSpeed / Megatron / DeepSpeed 原生配置
```

真正的产品价值不是“能读 YAML”，而是：

> 能判断两份字面不同的配置是否表达同一种并行语义，并指出转换过程中哪些参数等价、丢失、冲突或无法映射。

这对 CUDA→昇腾迁移、MindFormers↔MindSpeed 迁移、老配置升级特别有价值，也是单一框架调优器天然不擅长的领域。

可以逐步积累的专有资产包括：

- 配置字段语义字典；
- 跨版本映射规则；
- 框架口径差异库；
- 配置兼容性测试集；
- 真实项目中的错误映射案例库。

#### 3.2 从黑盒调优升级为“可解释配置因果图”

竞品通常能告诉用户哪组配置快，但较少完整回答为什么。

当前页面最应该强化的差异化，是把每条建议展开成因果链：

```text
TP 4 → 8
→ 每卡矩阵参数减半
→ SP 激活进一步下降
→ TP 通信组跨出单节点
→ HCCL all-reduce 延迟上升
→ 显存下降 11.2 GB
→ 吞吐预计只提升 3%，风险上升
```

推荐结果不只给一个分数，而应给：

- 变更了什么；
- 影响了哪些张量；
- 落在哪些 rank 和通信组；
- 改变了哪几段显存；
- 新增了什么通信；
- 为什么比当前配置好；
- 为什么没有选择排名第二的配置；
- 哪些结论来自公式，哪些来自 profiling，哪些只是经验规则。

尤其要提供反事实解释：

> 如果坚持 PP=4，最佳候选是 A；如果允许 PP=8，候选 B 吞吐高 6%，但跨机通信风险更高。

这会把产品从“调参脚本”提升为“性能工程师的决策工具”。

#### 3.3 白盒规则与黑盒 Profiling 的混合数字孪生

当前页面主要是白盒模型，MindSpeed Auto Tuning 则强调 profiling 黑盒建模。差异化不应在二者之间二选一，而应采用混合建模。

白盒层负责：

- 乘积与整除约束；
- rank 和通信组推导；
- 参数、梯度、优化器状态理论下界；
- 明显非法配置过滤；
- 推荐原因解释。

Profiling 层负责：

- 自定义模型结构变化；
- 实际 workspace；
- 算子融合与编译结果；
- HCCL 实际效率；
- 内存碎片；
- MoE 路由不均；
- 框架版本和 CANN 版本差异。

最终每个结果同时展示：

| 结果 | 数值 | 证据等级 |
|---|---:|---|
| 理论显存 | 51.8 GB | 公式 |
| 校准后显存 | 56.3 GB | 相似模型 profiling |
| 实测峰值 | 57.1 GB | 当前 trial |
| 预测误差 | 1.4% | 高置信度 |

关键不是只让预测更准，而是让用户知道“准到什么程度”。

建议建立置信度体系：

- A：相同模型、卡型、框架版本实测；
- B：相同算子形状和拓扑的历史数据；
- C：白盒公式加部分经验系数；
- D：存在未覆盖算子或硬件占位数据。

当置信度不足时，系统不应硬给“最优”，而应推荐最有信息价值的下一次 profiling。这实际上是主动学习，比盲目多跑 trial 更节省资源。

#### 3.4 打通“配置前—短跑—运行中—故障后”的闭环

这是当前页面最有潜力的方向，因为项目里已经同时存在配置关系、训练监控、运行事件、算子血缘和 profiling 分析。

建议形成完整闭环：

```text
配置导入
→ 开训前校验与估算
→ 候选生成
→ 小规模 Profiling/短跑
→ 推荐并启动正式训练
→ 监控预测与实测偏差
→ 定位性能下降/OOM/通信异常
→ 回写校准数据和失败知识
→ 下一次推荐更准确
```

NeMo 的流程主要终止于候选短跑与 CSV；DeepSpeed 主要终止于最佳配置；MindSpeed 已经有 profiling 建模，但这里的机会是把调优结果和运行期故障因果调查放在同一个配置关系模型里。

可以形成这些差异化体验：

- 从 OOM 事件一键回到触发它的配置字段；
- 显示“预计 56 GB，实际 61 GB，多出的 5 GB 来自哪个算子/workspace”；
- 某个 rank 超时后，反查它所属的 TP/EP/CP 通信组；
- 推荐配置上线后，自动验证预测吞吐；
- 软件版本升级后，发现同一配置性能回退并给出结构化差异；
- 把失败运行直接转化为以后禁止或降权的候选区域。

这会产生真正的数据飞轮：竞品算法可以复制，但真实运行中的“配置—拓扑—算子—事件—结果”数据很难复制。

#### 3.5 从单一吞吐目标升级为企业决策

“吞吐最高”通常不是企业用户真正的唯一目标。更有差异化的输出是受业务约束的多目标推荐：

- 性能优先：吞吐最高；
- 稳健优先：至少保留 15% HBM；
- 成本优先：最低 NPU 卡时；
- 交付优先：限定时间内训练完成；
- 资源适配：只使用当前空闲节点；
- 风险优先：避免 TP/EP 跨超节点；
- 迁移优先：尽量保持原 CUDA 配置语义；
- 变更最小：在当前配置基础上修改最少字段。

结果不要只给“Best”，而是给帕累托候选：

| 推荐档 | 吞吐 | HBM | 卡时成本 | 风险 | 说明 |
|---|---:|---:|---:|---|---|
| 性能优先 | 100% | 92% | 高 | 中 | TP 跨节点 |
| 稳健优先 | 96% | 77% | 中 | 低 | 建议生产使用 |
| 成本优先 | 89% | 81% | 最低 | 低 | 少用一半节点 |

企业用户更可能为“可审计、可复现、风险可控”付费，而不只是为搜索算法付费。

### 4. 建议选择的切入市场

不要一开始覆盖所有训练场景。更合适的突破口是：

> **昇腾大规模训练中的自定义 MoE、长序列以及跨框架迁移配置。**

这些场景同时具备：

- 配置维度最多；
- 框架语义差异最大；
- OOM 和通信故障成本最高；
- 单纯公式误差较大；
- 最需要解释；
- 最容易体现运行事件闭环价值。

特别是 CP 不只有 Ring 和 Ulysses，MindSpeed-LLM 还支持 hybrid、adaptive 等算法，不同算法与序列、头数和 mask 形态的关系很复杂。参考：[MindSpeed-LLM 长序列配置](https://gitee.com/ascend/MindSpeed-LLM/blob/1fd5df738726978b0099ed20f35e88b09be3f38f/docs/features/fine-tuning-with-context-parallel.md)。

这里比“普通 Llama TP/PP 搜索”更有差异化空间。

### 5. 产品演进路线

#### 5.1 阶段一：先做到“解释得对”

优先完善：

- 统一配置 IR；
- 跨框架导入与导出；
- 配置语义差异提示；
- 硬约束和软约束；
- 显存模型实测校准；
- 结论证据等级；
- 推荐前后配置对比；
- 预测误差展示。

这一阶段不要承诺“自动最优”，先成为工程师愿意信任的配置预检工具。

#### 5.2 阶段二：做到“推荐可验证”

增加：

- 搜索目标与约束编辑；
- 合法候选生成；
- 静态模型初筛；
- Top-K 短跑；
- trial 记录；
- 多目标帕累托前沿；
- 当前配置与推荐配置对比；
- “为什么选它/为什么不选另一个”。

这一阶段才正式使用“配置寻优”。

#### 5.3 阶段三：做到“越用越准”

增加：

- 预测与实测自动对齐；
- 按卡型、框架、CANN、模型版本建立校准档案；
- 未覆盖算子识别；
- 主动选择最有价值的 profiling；
- 失败配置知识库；
- 软件升级性能回归检测；
- 跨项目复用相似模型经验。

这时真正的壁垒是数据和知识，而不是搜索代码。

#### 5.4 阶段四：形成企业平台粘性

增加：

- 配置版本管理和审批；
- 调优预算；
- 集群队列与空闲资源约束；
- 推荐配置签名；
- 可复现实验包；
- 团队规则库；
- 配置基线和回归门禁；
- 私有化、离线环境支持。

### 6. 必须建立的核心指标

不能只展示“推荐吞吐提升 20%”，还要持续衡量：

- 非法配置开训前拦截率；
- OOM 预测准确率；
- 峰值显存预测误差；
- step time/吞吐预测误差；
- 推荐配置相对实际最优的 regret；
- 找到可用配置消耗的 NPU 小时；
- 首次获得可运行配置所需时间；
- 跨框架配置映射成功率；
- 未映射字段和语义错误率；
- 推荐被接受、一键应用和回滚的比例；
- 版本升级后的性能回归发现率。

这些指标比“支持多少种搜索算法”更能说明竞争力。

### 7. 最应避免的方向

- 不要先做学习率、weight decay 等通用 HPO，Optuna、Katib 已经足够成熟；
- 不要只做一个 MindSpeed Auto Tuning 的图形界面；
- 不要用当前静态公式直接宣传“全局最优”；
- 不要为了支持大量模型而堆预设，优先建立自定义模型的 profiling 校准能力；
- 不要把所有结论混成一个推荐分数，必须区分公式、规则、历史数据和当前实测；
- 不要只展示获胜候选，失败候选及其失败原因也是重要资产；
- 不要让优化器静默修改训练语义，例如层数、序列长度、GBS 或 LoRA 方式。

### 8. 最终竞争表达

最有竞争力的产品表达不是：

> “我们也能自动搜索 TP/PP/CP/EP。”

而是：

> “把任何训练配置导进来，我们先解释它在当前框架和集群上究竟意味着什么；再用最少的 profiling 预算生成并验证候选；正式运行后持续核对预测、定位偏差，并把每次成功和失败变成下一次寻优的知识。”

候选产品命名：

- **可解释训练配置寻优**；
- **训练配置数字孪生**；
- **训练配置智能决策平台**；
- 英文可用 **Training Configuration Intelligence**。

其中最值得守住的三条护城河是：

1. **跨框架配置语义 IR**；
2. **配置—张量—算子—通信—事件的可解释因果图**；
3. **预测、短跑和生产运行共同驱动的校准数据飞轮**。

搜索算法会越来越商品化；这三层才可能形成真正的长期差异化。
