# 故障故事线 · 无限画布（`incident-canvas`）

**主视图永远是并行拓扑 pattern 本体**——就是你打开 [`/combo-workbench/`](../combo-workbench/)
在舞台上看到的那张「模型分片与训练设备映射」，不是另画一份像它的图。画布围着它长。

## 「无限画布」是字面意思：下钻 = 在画布上展开一格

主视图钉在原点、永远在，不提供收起——它是这一页的主语。别的格子按需展开，各自落在画布上
自己那个位置，用一条贝塞尔连回主视图。**展开得越多，画布越大**；收起就是那一格的 ×。

**四个方位各管一件事，方位内部的顺序有含义**——这是这张编排表唯一的规矩：

```
        ╭ 上 · 告警（悬浮居中，不占画布的地）╮
        ╰────────────────────────────────────╯

   ←──────── 左 · 结构，由粗到细一路往外 ────────      ┌─ 右 · 事件下钻 ─┐

 ┌─ 卡内解剖 ─┐  ┌─ 单维切分 ─┐  ┌─ 整网 ─┐  ┌───────┐  ┌ 传播 ┐ ┌ 证据 ┐   ← 点事件时一起来
 │ 一张卡里面 │  │ 五级粒度轴 │  │ 真图展开│  │ 主视图 │  └──────┘ └──────┘
 └────────────┘  └────────────┘  └─────────┘  │ 并行拓扑│  ┌ 机制 ┐ ┌ 单卡 ┐   ← 再从传播点出来
                                              └───┬────┘  └──────┘ └──────┘
                              ┌── 泳道 · 微批次生命周期 ──┐
                              └───────────────────────────┘
                              ┌──── 计算血缘 ────┐   下 · 时序   ┌─ 训推大盘 ─┐
                              └──────────────────┘              └────────────┘  右下 · 读数
```

- **上 归告警，别的格子不进去**。试过把大盘摆到主视图正上方（告警挪成悬浮之后那一带
  看着是空的），行不通：画布顶上那一条是**悬浮告警的地盘**，告警一摊开就压住大盘的格头——
  切换问题之后大盘明明更新了，人却看不见自己在看哪条问题、数据变成了什么。
  这不是时机问题，绕不开：悬浮层盖住底下的东西是它的定义。所以大盘回到右下角。
- **左**：整网 → 单维切分 → 卡内解剖。越往外粒度越细，方向单一。中间那格是**连接两端的
  那根粒度轴**，所以它就该在中间。
- **右**：分两行，分法就是「怎么来的」——上行是点一枚事件时**一起**摊开的（传播关系 +
  支撑它的那张图），下行是再从传播那一格里点出来的分支（看机制 ▸ / 点一个 rank 对象）。
- **下**：两条横带，都是「展开成一条线」的形状，所以并排叠在主视图脚下。
- `Esc` 也按这套顺序收：**先退下钻，再从最外圈拆常备格**。原先那张表按纯几何排，
  最靠外的卡内解剖排在最前——结果刚点完一个事件按 Esc，收掉的是画布最左边那一格，
  而不是刚刚点出来的下钻。

## 开场镜头停在主视图，不是「适配全部」

适配全部要把五格常备面全框进来，落在 **26%** 上。那一屏好看，但主视图小到读不出一张卡，
而并行拓扑恰恰是这一页的主语。所以开场就把镜头钉在它身上（**约 85%**），四周各格只露一条
边当路标——读者一进来就知道「外面还有」，而不用先缩小一次才发现。要看全貌按「适配全部」
或双击空白，一次点击的事。

镜头记着自己停在哪一档（`main` / `all` / `free`）。改窗口大小时按那一档重新落位；
读者自己滚过、拖过之后就是 `free`，那时不动它——那一屏是他自己摆的。

## 告警是悬浮的一块，不是画布上的一格

故事线**不占画布的地**，它钉在视口上，不跟着缩放平移。理由是它压根不是一个「视图」：
别的格子都在答「这件事落在结构的哪儿」，它答的是「出了什么事、怎么一步步推过来的」。
绑进画布的代价是双份的——读者每次想回头看一眼时间线都得先把镜头挪回去；而镜头一缩到
26%，它自己也跟着糊成一条看不清的细带。

默认是**收起的一条告警**，钉在画布**正上方居中**：

```
( ● 问题2 · Router 溢出与通信死锁 [6] ⌄  │  ● 问题1 · 显存峰值与碎片 OOM [5] )
```

**问题即告警，是同一件东西**：每一条问题自己带严重度点和事件数，不是「一枚计数按钮 ＋
一组页签」拼在一起。拼的那版读起来是两样东西——那颗 `● 6` 说的到底是哪条问题的 6，
得想一下才知道。现在每条自己说自己的，active 那条就是你正在看的这条告警。

**两种点击，一个对象**：点已经在看的那条 = 开合它的事件链；点另一条 = 换过去看。
所以旁边不需要再摆一枚「打开」按钮。折叠角标只长在正在看的那条上（另一条点了是「切过去」，
没有开合可言，给了角标反而像在说它也能开），朝向跟着抽屉走。
只有 active 那条的点会呼吸——两颗一起跳是噪音，而「你在这条上、它还活着」才是这颗点要说
的话；没在看的那条留一颗静止的点：它有告警，但此刻不是主语。

也可以点右上角那枚「告警」筹码摊开。默认不铺开是因为铺开要占掉三分之一
视口，把主视图从 85% 压到 54%——主语让位给旁白，次序反了。

**居中而不是靠左**：它是这一页唯一的入口，居中才是入口该在的地方；靠左会被读成「角落里的
一个附件」。**缩到最小**：不写当前选中的那件事——那是抽屉里的内容，写在这条上只会把它撑成
半屏（早先那版就是 `Router FP8 溢出，E193 吸收 98% token · 问题2 · Router 溢出与通信死锁`）。
现在条宽约 466，不随选中的事件变长。

**问题段控从顶栏挪了进来**：它选的是「哪一条告警」，本来就属于告警这一块。长在顶栏时，
告警收起之后顶栏还替它留着一排按钮，同一件事两处各说各的。段控**只此一份，在两个宿主之间
搬家**而不是各建一套：收起时挂在这条上，摊开时挂进抽屉的格头——两套的话「哪个是真的」
这个问题就永远得回答一次。

**格子筹码挪进了顶栏**（挨着「适配全部 / 回主视图」——这三样管的是同一件事：镜头与画布的
整体状态，本来就该待在一处），所以画布顶上那一带整条归告警：收起态与摊开态都直接居中贴顶
（`top:12`），不再有任何让位规则。顶栏里那组不给底色也不给边框——顶栏本来就是一条底，
再套一层白底会变成「条里又有一条」。

**告警一开一关，画布要交代一下被它盖住的那一带**：镜头还停在 `main` / `all` 档就按那一档
重新落位；读者自己摊过拖过（`free`）就只平移让出的那点差值，不动他的缩放和构图——
`refit` 在 `free` 档上什么都不做（故意的，不能把读者摆好的那一屏抢走），所以这里用更轻的
手法，只把原本会被盖住的东西挪出来。

**摊开态也居中**，和收起那条对齐——两个形态是同一块东西，不该一个居中一个靠左。
它固定落在右上角那排筹码**底下**（`top:60`）：居中之后右缘会伸进筹码那一带，与其按宽度
分档避让，不如干脆常驻下面一行，一个规则所有宽度都成立。

尺寸 **1000 × 144 是两条问题线一起量出来的下限**。紧约束在**问题1**而不是问题2：
问题2 有六张卡（卡宽 144），880 就开始截「Router FP8 溢出，E193 吸收 98% token」；
问题1 只有五张卡、卡反而更宽（191），却卡在更长的那条标题上——
「EP rank 17（global rank 1553）触顶并发生碎片 OOM」要到 **1000** 才不被 `line-clamp` 截。
高度 144 是下限，138 会一次截掉 5 条标题。

> 第一版只扫了问题2 就写下「920 是下限」，漏了问题1——两条线卡片数不同、卡宽不同、
> 最长标题也不同，只量一条不足以定尺寸。

原先是 1180 × 238——卡片在行里是 `stretch` 撑满的，多出来的高度全变成卡片下半截的空白，
看着像留白，其实只是没人要的那截。

摊开时它是不透明的，所以镜头落位会把它盖住的那一带让出来（按元素实测位置算，不写死）。
一开一关都重新落位一次，否则让出的带子和镜头对不上。

## 并行拓扑的另外两屏，也是从四周展开的格子

并行拓扑本身有七个视图。这一页**不把它们做成页签**——页签会成为第二套并行机制，
同页摆两套，人就分不清「哪些屏是画布上的格子、哪些屏是某一格里的页签」。
所以要用到的那两屏各自成格，和整网 / 泳道 / 大盘一样从四周点开：

| 格子 | 钉在哪一屏 | 答的是 |
|---|---|---|
| **单维切分 · 五级粒度轴** | `view=dim&l5=1` | 一次只看一把刀，它在五个粒度上各切成什么：整网 → 层 → 算子 → kernel → 卡 |
| **卡内解剖** | `view=anatomy` | 主视图答「落到哪张卡」，它答「那张卡里面长什么样」：层段 → 算子片 → kernel → 流 |

`l5=1` 是必须的：不带它，单维切分那一屏只剩卡一级，读不出五个粒度的对照——
而那正是这一屏的题面。

连同主视图与整网，画布上一共有**四份同一个 pattern 本体**，各钉在不同的 `view` 上。
它们共用一个文件，浏览器只下一次，所以多开两格几乎不额外花钱（实测五格 iframe
全部就位约 2.6 s）。

## 走带：把泳道和拓扑接起来的那条线

泳道是一张**静态**甘特图，上游那份没有游标、没有播放。而「这一步走到此刻，每张卡
手上压着多少激活」正是它和拓扑之间还没接上的那条线：泳道画的是什么时候在算什么，
拓扑画的是那一刻显存里装着什么，本来就是同一件事的两面。

进度 t（0–1）推给两格 pattern（`pto:state` 的 `step`），它们按 1F1B 的形状把逐卡的
激活体算到那一刻；游标是叠在泳道 iframe 上的一层 div，**不改上游那个逐字节拷贝来的
文件**。收回走带回到峰值——那才是「一张卡要多少显存」的默认答案。

游标坐标必须**读**而不是假定（缩放与横向滚动都是实时状态）：
`内容坐标 = gutter + t · (width − 16 − gutter)`，`屏幕坐标 = 内容坐标 − scrollLeft`。
width 写在 `#timelineSurface` 的内联宽度里（已经吃了 zoom），和
`#timelineScroll.scrollLeft` 一样都是同源可读的渲染结果，不是要猜的内部状态。

## 计算血缘：同一个算子在五层里各叫什么名字

一次故障报在 Kernel 层（比如 `HCCL AllToAll executor`），而人能改的东西在模型语义层
（Router 的 Top-2 gate）。中间隔着 FX 捕获、GE 融合、Runtime 下发三道转换，名字每过
一道就换一次——不把这条链摆出来，「报错点」和「震中」就永远对不上号。

五层轨：模型语义 → FX Graph → GE Graph → Runtime → Kernel / Executor，层间标出这一步
发生了什么（捕获 / Lowering / 融合 / 任务下发 / Kernel 选择）。事件采到的那几层是实底，
没采到的灰掉并写明「不是不存在，是这一跑没留下记录」。`originNode` / `victimStage`
在对应节点上标「传播源」「受影响」。降级口径与 11 条 `lineage` 记录逐字取自原页的
`LINEAGE_LOWERING`。

**画布上那五格常备面一进来就是摊开的**——大盘给读数，整网 / 单维切分 / 卡内解剖给结构的
三个粒度，泳道给时序。不该让人先去点一遍才看得见。告警是第六枚筹码，但它默认是
**收起的一枚牌子**（理由见上一节）。事件相关的那几格（传播 / 机制 / 证据 / 血缘 / 单卡）
也按需展开，因为它们得先有一个选中的事件才有内容。

把格子全关掉时 URL 写的是 `open=none` 而不是把参数删掉：删掉的话下次打开这条链接会被
当成「没指定」，默认那几格又全长回来——读者刚一个个关掉、刷新一下全回来，那是 bug 不是
默认值。

那排筹码钉在**画布右上角**，不长在主视图的格头里：它管的是「这张画布上摊开了哪几格」，
是页面级的开关。长在格头上它会跟着画布一起缩放平移，镜头一挪开主视图就够不着了——
而这恰恰是你想收起某一格时最需要它的时候。
点告警里的事件会一并摊开「事件传播 + 证据」，事件里再点「看机制 ▸」摊开机制舞台。
`Esc` 先退下钻，再从最外圈拆常备格。

## 联动搭在**层号**上，不是 rank

这是一处必须说清的口径差异：

- 故事线讲的是一个 **2048 卡的实跑**（PP4 × EDP8 × EP64，`rank 1559` / `1553` 是那个集群里的门牌）；
- 被嵌的 pattern 画的是它自己那个 **128 卡的演示集群**（`world 128 · TP2 × PP4 × DP16 · EP8`，与组合工作台同一套缺省）。

两边卡数不同，**rank 号天然对不上**。把 1559 推过去要么无声无息（它那儿只有 R0–R127），
要么照亮一张根本不是那张的卡——后者比不亮更坏。也试过让 pattern 直接画 2048 卡：
DP 512 行会退化成一条看不清的斜线，还要 12 秒才画完，那不是「更真」，是把主视图毁了。

**层号则是两边都成立的主键**：L38 在故事线里落在 PP3（L34–L45），在 pattern 的 48 层口径里
也落在 PP3（L36–L47）——同一段流水线。所以选中一个事件，主视图点亮**承载这一层的那些卡**，
pattern 自己会在角上报「L38 · 32 张卡 · 各持 1/16，无一张完整」，并注明这是
「来自另一个视图的联动高亮，不是这一屏的选中」。rank 只从 pattern 流回来
（读者在整网那格点算子 → 主视图照亮那一层），不往它那儿推。

两格之间的层联动是**双向**的：读的是那一格自己的**搜索标签**，推出去的是**高亮**。
两者不同源，所以不会回声——高亮不产生标签，下一轮读到的还是读者自己那枚。

**`lineage.layer` 也算一路来源。** 层号原先只从 `focus.kind==='layer'` /
`origin.layers` / `scope.layers` 里取，于是像「PP3 断裂，2048 NPU hang」这种
（`focus` 写的是 stage、`scope` 写的是 all，层号只在血缘里的 L38 Router）就一路取空——
点中它时主视图和整网都不会亮，而它恰恰是故事线最后一枚、最该看清震中在哪儿的那一枚。

### 泳道接的是 `hl.rank`，桥仍旧搭在层上

泳道那一格认的主键是「哪一行」，不是层。而它同样对不上号：那份 mock 只模拟 32 卡里的
**一个 DP 副本**（`dp2 × pp4 × tp2 × ep2`，`activeDp=1` → Rank 16–31），故事线的
`rank 1559` 在它那儿不存在。直接推过去不会报错——泳道自己会在状态行里写
「Rank 1559 不在这份 32 Rank 模拟拓扑里，泳道未移动」——诚实，但点了等于没点。

所以这条桥和主视图那条**同一个主键**：先拿到事件的 PP 段（事件自己写明 stage 就直接用，
否则从层号反推），再取那一段在 `activeDp=1` 下的头一张（tp0 / ep0）。于是「点一枚事件」
这一下同时落到三个地方：主视图点亮承载这层的那些卡、整网点亮这一层、泳道展开父链把那一段
滚进视野。

> 要说清的是：落到「**哪一段流水线**」是真的，落到「具体哪一张卡」不是——那一行只是这段的
> 代表。所以泳道格头的副标题写的是 `已随 L38 定位到 PP3（这一段的代表行）`，不写 rank 号。
轮询而不是监听点击：一格里改「看哪一层」的路子不止一条（点侧视命中区、手填搜索框、
摘标签、正视换层步进），盯住**结果**比盯住每一条入口可靠。

## 五种机制

`router-collapse`（路由塌缩）· `barrier-wait`（barrier 语义）· `pp-cascade`（依赖链回压）·
`activation-lifetime`（存活区间叠加）· `fragmented-oom`（碎片）。

没有共用一张「通用示意图」：五条机制本来就不是同一件事。比如 `pp-cascade` 把
「2048 卡停摆」拆成一条可验算的乘法链 `1 →×EP64→ 64 →×EDP8→ 512 →×PP4→ 2048`，
每一步都是一个已知的并行度，而不是一句「故障扩散」。

## 训推大盘：十条关键少数 + 五个钩子

口径来自 `pangu_sophon_pytorch`——真正会在每个 `log_interval` 被打印、写进
TensorBoard / Prometheus 的就这几条：

| 指标 | 期望 | 出处 |
|---|---|---|
| `lm loss` | ↓ | `loss_func()` → `training_log()` |
| `grad_norm` | 稳定 | `training_log()` |
| `loss_scale` | 不触发 | `logger_and_track_metrics_callback.py:74` |
| `num_zeros_in_grad` | ↓ | `training_log()` |
| `throughput`（TFLOP/s/GPU） | ↑ | `PretrainMetricConfig._compute_throughput` |
| `MFU`（%） | ↑ | `PretrainMetricConfig._compute_mfu` |
| `throughput_per_day`（B tokens/day） | ↑ | `_build_log_dict:1505` |
| `elapsed time / iter`（ms） | ↓ | `_build_log_dict:1491` |
| `learning_rate` | 按计划 | lr scheduler（cosine / WSD） |
| `mem_reserved_bytes`（GB） | 平稳 | NPU 保留显存 / `theoretical_memory` |

五个早停钩子：`check_for_nan_in_loss_and_grad`、`loss_spike_monitor_callback`、
`init_heartbeat_monitor_pid`、`_warn_data_production_speed`、`mem_reserved_bytes` 增长趋势。
每个钩子下面一排小点是本条故事线的事件序列，在哪个事件上触发就点亮哪一颗——
**一颗都不亮也是信息**：这两条线里「数据生产速度告警」一次都没响过。

> **只取口径，不取值。** 大盘上每一个数都能在故事线的同一个事件里找到原文；
> 没采到的格子一律写「—」，不替它编一个。代码里这两份也是分开放的：
> `GROUPS` 是照搬的故事线，`BOARD` 只是这一层的口径映射。

### 「为什么有的有、有的没有」要在格子上就说清

十格里通常只有两三格有值——这是**规则的结果**，不是页面没加载：那一刻的日志只打印了
那几条。但这句话原先只写在最底下那行小字里，而人是在盯着一片发灰的「—」时才产生疑问的，
那时视线根本不在页脚。

所以栅格上方加了一行，先回答「这一刻哪几格有读数」再回答「为什么别的没有」：

```
这一刻  [4 / 10 有读数]  throughput、MFU、throughput_per_day、elapsed time / iter
        · 1 个钩子会触发   [其余 6 格写「—」] ＝这一事件没采到，不是 0，也不是没加载
```

顺带把「哪几格动了」做成一眼能看见的事：有读数的格子除了顶边那条色条，再加一层同色的
极淡底与描边；没采到的从 `.62` 压到 `.44`。原先十格里挑出两格全靠扫——而「这一刻动了
哪几格」恰恰是这一屏最该第一眼看见的东西，不该要人找。
