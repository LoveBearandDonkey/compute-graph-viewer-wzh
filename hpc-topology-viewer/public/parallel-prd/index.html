Product Requirements

并行拓扑可视化工具

范围假设 本文按「为 HPC topology viewer 写产品需求」来写。若你要的是别的对象（例如体验治理平台、或「配置→图」的 AI 技能），结构可复用，内容需替换——告诉我即可。

版本 v0.1 · 2026-07依据 《分布式训练参照系 —— 五根轴 · 两个对象 · 三组坐标》（下称「参照系」）
配套阅读 · 分布式训练参照系 —— 五根轴 · 两个对象 · 三组坐标
00

一句话

让工具的信息架构与概念本体同构：五类对象各有各的视觉语法，三组坐标各有各的视图，基数关系一律不压平。

01

背景与问题定义

1.1 现状

并行训练的配置空间是六维的（TP / SP / CP / PP / DP / EP），而人只能在三维里看东西。现有的拓扑可视化普遍采取「硬塞」策略，由此产生四类结构性错误——它们不是美观问题，是信息编码错误，会直接导致用户误判。

# 现象 本质 后果 依据
P1 把并行维度与通信原语一一绑定 把 N:M 关系编码成 1:1 看到 All-to-All 就以为是 MoE，而它同样可能是 Ulysses CP 参照系 §09、§13 勘误 K/L
P2 把 CP 硬加成卡网格的一根轴 混淆了两种「第四维」——切分维与时间轴 CP 与 DP 在卡网格上长得一样，用户分不清 §05、§12
P3 把 rank 画成容器 地址被当成了形状 让人以为 rank「装着」东西，一卡多 device 时彻底对不上 §15
P4 只呈现单卡时间线 丢掉了跨 rank 的相对关系 把「等待」误判为「链路慢」，归因方向完全反了 §12 诊断陷阱

1.2 机会

参照系已经把这套概念梳理成一个可直接映射到 IA 的框架：

  • 五根轴（ℓ h e b s）—— 决定有哪些可切维度
  • 两个对象（权重体 / 激活体）—— 决定被切的是什么
  • 三组坐标（空间 4 维 · 时间 · 粒度）—— 决定需要几个视图族
  • 五类对象（结构 / 内容 / 容器 / 地址 / 动作）—— 决定视觉语法

产品主张：把这四层直接落成 IA，而不是先画图再补概念。

02

目标与非目标

2.1 目标

优先级 目标 可判定的成功标志
G1 让配置可见 —— 给定一份并行配置，看清每张卡持有什么 用户能在 30 秒内答出「第 37 层在哪几张卡上、单卡权重 shape 是多少」
G2 让通信可见 —— 看清什么时候、谁跟谁、用什么原语通信 用户能区分「同步」与「转发」两类通信，且不把原语与维度绑死
G3 不制造错误认知 —— 宁可不画，不可画错 上表 P1–P4 四类结构性错误一条都不出现
G4 可用于诊断 —— 从图能导向可行动的判断 用户能据图区分 OOM 类与利用率类问题，并定位到具体 rank

2.2 非目标

  • 不做性能预测。 参照系只给了「计算密集 / 访存密集」的定性判据，没有 roofline 这类可算模型（§16）。工具不承诺吞吐数字。
  • 不做配置推荐。 §11 只给了决策顺序，没给数值方法。工具做校验（这配置合不合法）与诊断（哪里可能有问题），不做「你应该配 TP=8」。
  • 不覆盖推理。 全文是训练视角，推理的并行语义相当不同（§16）。
  • 不绑定具体框架。 概念中立；框架差异只体现在导入配置的适配层。
03

目标用户与场景

用户 场景 核心诉求 对应目标
U1 训练工程师 调一版新配置，想确认切分是否如预期 「我以为 TP 在机内，实际是不是」 G1、G4
U2 性能分析师 profiling 显示某卡 AllReduce 40ms，判断根因 「这是链路慢，还是它在等别人」 G4
U3 框架 / 算子开发者 排查某个算子在切分后行为异常 「这个算子被切成了什么样，通信插在哪」 G1、G2
U4 新人 / 跨团队沟通 理解一套并行配置在讲什么 「TP 和 DP 到底差在哪」 G2、G3

主场景（P0）：U1 输入一份配置 → 看到卡网格 → 点某张卡 → 读出它的多重 rank 坐标与持有内容 → 切换通信图层确认原语与落位。

04

设计原则

以下五条全部从参照系直接推出，是后面所有需求的裁决依据。当需求与原则冲突时，以原则为准。

DP-1 · 基数不压平

任何 N:M 的关系，界面上不得呈现为 1:1。

最典型的是「并行维度 → 通信原语」。压平会制造 P1 类错误。（§01、§09）

DP-2 · 五类对象，五种语法

结构画成拓扑、内容画成体积、容器画成边界、地址只标不画、动作画成连线。

地址不画成形状是这条里最硬的一款——它直接否决「把 rank 画成柱子/盒子」。（§15）

DP-3 · 有序维优先上轴，对称维可折叠

pp_rank 的大小有意义，必须占一根轴；tp_rank / dp_rank 只是标签，折叠了不丢信息（看一个组等于看全部）；CP 视实现而定。

这把「画哪三根轴」从主观选择变成由配置决定的推导。（§12）

已有可交互原型验证这条原则：PP 的两张脸 · 用 rank 看流水线。它把 PP 留在轴上、把 TP×DP×CP 折成每格一个 Stage 截面，于是斜线（一个 micro-batch 的因果链）、重叠（并行）、两角空白（气泡） 三件事同时可读；点开任一 Stage 又能把折叠的卡摊回来，逐格画出它的 PP 链（每跳一次 P2P、global_rank 加一个 Stage 的卡数）。折与不折的代价与收益，在这一张图里是同时看得见的。

DP-4 · 视图按坐标组划分，图层按对象类别划分，二者正交

任一视图上都能独立开关任一图层。

这是 DP-1 在交互上的落地：维度决定哪些卡在一组，原语决定组内怎么连线，两者不得耦合。（§14 推论 4）

DP-5 · 宁缺毋误

画不下的东西就不画，并明确告知为什么画不下，而不是找个近似塞进去。

三维只有三根空间轴而坐标系有三组，轴不够是硬约束。（§15）

05

信息架构

5.1 视图族（对应三组坐标）

视图 展开的轴 冻结/折叠的轴 回答什么问题 对应参照系
V1 卡网格（空间） TP × PP × DP 时间冻结；CP 分面；粒度固定在「卡」 谁和谁在一个通信域 FIG 06
V2 时间线（时间） 时间 × rank 空间折叠到只剩 PP 什么时候谁在算什么 FIG 15
V3 粒度链（粒度） 整网 → 层 → 算子 → kernel 空间折叠 某个东西被切在哪一级 FIG 01、04
V4 单卡容器（内容） 显存构成 折叠为一张卡 容器里装了什么、还剩多少 FIG 11
V5 输入分布（正交） DP × CP —— 输入怎么分布（与 V1 分开） §05

V5 单独立出来是 P2 类错误的解法：卡网格回答「模型怎么分布」，CP 属于另一个问题——「输入怎么分布」。两个问题各配一张图，比塞进同一张更清楚。

5.2 图层（对应五类对象）

图层 内容 默认 可开关
L1 结构层 图 / 层 / 算子的拓扑 V3 开，其余关 ✔
L2 内容层 权重体 / 激活体的体积 V4 开 ✔
L3 容器层 卡边界、流 常开 ✔
L4 地址层 rank 标注 常开 可切换显示哪一组坐标
L5 动作层 通信连线 按需 ✔ 且与维度选择解耦

L5 与维度选择解耦是 DP-4 的硬性落地，也是修正 P1 的关键。

5.3 坐标读出规范（修正 P3）

  • global_rank 常驻显示，任何视图任何时候都不变
  • 域内 rank（tp_rank / pp_rank / …）随当前 axis 高亮，不替换全局号
  • rank 一律以标注形式贴在卡（容器）上，不得渲染为独立的几何体

编号不变、只是当前生效的那一维被点亮。这样跨 axis 切换时用户不会觉得「卡的编号变了」。（§14 推论 5）

功能需求

P0 —— 不做就不成立

ID 需求 验收要点 依据
FR-1 配置输入与合法性校验 校验 heads % TP、experts % EP、layers % PP、seq % (2·CP)；DP 由 world_size/(TP·CP·PP) 自动算出，不可手填；MoE 最小卡数按 PP × max(TP·CP, EP·ETP) 校验，禁止用各维连乘 §11

ID 需求 验收要点 依据

07

关键交互

7.1 主流程

输入配置 ──▶ 合法性校验 ──▶ V1 卡网格
                 │              │
                 │              ├─ 点卡 ──▶ 坐标读出 + 持有内容
                 │              ├─ 开 L5 ─▶ 选维度 ⊗ 选原语（正交）
                 │              └─ 切视图 ─▶ V2 / V3 / V4 / V5
                 │
                 └─ 不合法 ──▶ 指出违反了哪条整除约束 + 给出最近的合法值

7.2 交互细则

  • 视图切换保持选中状态：在 V1 选中 rank 5，切到 V2 后仍高亮 rank 5 的时间线
  • CP 切换是视图开关，不是 axis 值：axis= 参数的取值域只含 tp|pp|dp|ep，CP 走独立入口（§05）
  • 默认视角可复位：三维视角允许旋转，但必须有「回到标准等轴测」
  • 遮挡处理：连线在三维中易被遮挡，需支持「只看连线」的抽离模式（对应 FIG 12 单独画拓扑形态的做法）
08

视觉编码规范

对象类别 几何 禁止
结构 节点 + 边，无厚度 画成实心块（会被误读为占显存）
内容 实心块，体积 ∝ 字节数 体积与实际量级脱钩
容器 线框盒，有明确容量边界 与内容用同一种填充
地址 文字标注 任何几何体
动作 连线 / 箭头 赋予体积

通道色彩：TP / PP / DP / CP / EP 各占一个固定色相，全局一致，跨视图不变。

线型语义：

  • 有方向 → 实线 + 箭头（P2P）
  • 无方向对称 → 实线闭合，无箭头（AllReduce）
  • 多对多且各边载荷不同 → 细线全连接（All-to-All）
09

验收标准

以下每条都可以直接测：

# 验收项 判定
A1 选 CP 维度时，能显示三种不同原语中的任一种 通过 = 不被固定为 Ring
A2 在任一视图中，找不到任何一个代表 rank 的几何体 通过 = 地址只以标注出现
A3 把 DP 从 2 调到 8，V4 容器视图无任何变化 通过 = 正确表达了「加 DP 不买余量」
A4 卡网格的 axis 取值域不含 CP 通过 = 未混淆两种「第四维」
A5 通信耗时不均场景下，工具提示指向耗时短的 rank 通过 = 归因方向正确
A6 输入 heads=33, TP=16 时报错并指出具体约束 通过 = 校验有效
A7 MoE 配置的最小卡数提示等于 PP × max(TP·CP, EP·ETP) 通过 = 未用连乘式
A8 切换视图后选中的 rank 保持高亮 通过 = 状态连续
10

分期

阶段 内容 产出
M1 骨架 FR-1 ~ FR-5（P0 全部） 能正确表达一份配置的空间结构与通信，且不犯 P1–P4 四类错误
M2 诊断 FR-6 ~ FR-10 从「看得懂」升级到「查得出」
M3 深化 FR-11 ~ FR-14 配置诊断与排布可视化

M1 的完成定义：验收项 A1、A2、A4、A6、A7 全部通过。这五条恰好对应四类结构性错误加配置校验——它们是这个产品与现有方案的全部差别所在。

11

度量

指标 定义 为什么选它
任务完成率 目标用户在无指导下完成主场景的比例 直接对应 G1
误判率 给定一组带陷阱的配置（如 Ulysses CP），用户判断错误的比例 直接对应 G3，是本产品的核心差异点
首次正确归因时长 U2 场景下从打开到给出正确根因的时间 直接对应 G4
满意度 常规主观评分 辅助

建议把误判率作为北极星指标。它是唯一能证明「结构正确」有价值的量化证据——否则「不犯 P1–P4」这件事在评审里很难被看见。

12

风险与开放问题

# 风险 影响 应对
R1 配置空间过大，UI 失控 参数一多，界面变成表单地狱 按 §11 的五步决策顺序组织输入（TP→PP→CP→EP→DP 自动），而非平铺所有参数
R2 三维遮挡 连线与块互相遮挡，信息读不出 提供连线抽离模式；等轴测固定视角作为默认
R3 定位摇摆：教学工具还是诊断工具 两者对精度与简化的要求相反 建议先定位教学 / 沟通（G1–G3），诊断（G4）作为 M2 目标；不要在 M1 同时追
R4 EP 语义随框架版本变动大 经典 EP / ETP / MoE Parallel Folding 三种语义并存 配置里显式要求版本；不同版本走不同渲染分支（§13 勘误 M）
R5 与真实 profiling 数据对接的成本 FR-7、FR-8 依赖真实时间线数据 M1 先用合成数据验证视觉编码，M2 再接真实数据

开放问题

  1. 数据来源：配置是手输，还是从训练脚本 / 框架配置文件导入？后者需要适配层，且要处理版本差异。
  2. 是否需要多配置对比？（FR-14）——如果主要场景是「调参时确认」，对比价值很高；如果是教学，价值低。
  3. ETP 是否进入 M1？它让 EP 的表达完整，但也让配置空间又多一维。
  4. 时间线数据的粒度：到 kernel 还是到层？到 kernel 数据量大但能定位算子；到层足够做 PP 诊断。
