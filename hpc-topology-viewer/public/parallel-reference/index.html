表 D · 卡 / device / 进程 / rank

全文的「卡」是刻意选的中性词——指一块独立的加速设备。并行切分、rank 排布、通信原语这些机制与具体厂商无关，这一层结论不受平台影响。平台差异分两类，只有第一类是称呼：① 命名差异——互联名、集合通信库、算子栈的叫法不同，不影响任何结论；② 高带宽域大小的差异——它同样不改变任何机制，但会改变所有以「机内」为界的数值约束（TP ≤ 高带宽域内卡数、EP 组是否必然换挡、order 字符串把哪几个组按进高带宽域）。灵衢超节点把高带宽域从 8 卡扩到 384 卡，正是第二类的一个实例：机制一个字不变，约束的边界挪了 48 倍。本文凡出现「高带宽域」处，读者应代入自己平台的实际尺寸；见 §01「七」。

「一张卡 = 一个 rank」对不对

对一半。准确说是两条：

  • device → global_rank 是 1:1（默认一进程绑一卡时）——这一半对。
  • device → rank 编号总数是 1:N——一张卡同时持有 global / tp / pp / dp / ep / cp / local 一整组编号。所以「一张卡一个 rank」只在 global 这一个域内成立，见 §10。

还有一层容易略过的精确性：rank 绑的是 device，不是物理卡。主流训练形态下二者重合——一块物理卡 = 一个 device = 一个 rank，日常混说没问题。但有的形态一块卡上带两个独立设备，那时「一张卡」就对应两个 rank。灵衢的物理链就是一个具体例子——本文物理链最底一级写作「卡（die / NPU）」，一个 node 的 perNode = 8 指的是 8 个 device，不是 8 块板子（见 §01「七」与表 B「node」行）。拿不准时以设备查询工具的实际列举为准——本文其余部分默认「一卡一 device 一 rank」的训练形态。

为什么 SP 值得单独强调

它的二义在中文语境里尤其容易翻车——「序列并行」四个字同时指向两个不同的并行维度、不同的通信原语、不同的嵌套位置。看到 SP 先问一句「是 Megatron 的还是 Ulysses 的」，能省掉一半的沟通成本。

基数：每种关系是几对几

后面所有关系里，最容易出错的不是「A 和 B 有关系」，而是「这个关系是几对几」。而且相当一部分关系的基数不是固定的——它随配置变化，而配置有两类：并行配置（TP/CP/PP/DP/EP 各维大小，决定切分映射类的基数）与拓扑配置（每 node 几卡 / 每机柜几 node / 每超节点几卡，决定物理位置类的基数）。两类互相独立：换一套并行配置，物理位置类的基数一个不动；换一台机器，切分映射类的基数一个不动。唯一把两者绑起来的是约束（TP 组要不要留在同一个高带宽域内），不是基数。本节先把记号钉死，再给出全景基数表；后文每处关系都会带上标记。

记号约定

1:1一一对应
1:N一对多
N:1多对一
N:M多对多
※基数随配置变化，见「取决于」列
  • 方向敏感。A → B 是 1:N 时，B → A 就是 N:1。本文一律按表头写的方向读，不省略箭头。
  • 区分类型与实例。「层」既可以指第 37 层这个实例，也可以指所有层共用的那份子图模板。两者对同一个 B 的基数往往不同，表里会写明。
  • N:M 不等于「说不清」。它是一个明确结论：两侧都能一对多，因此不存在归属关系，只能建索引。文中所有 N:M 都是这个意思。
第三格的陷阱

纯 TP 与纯 DP 在这张图上基数完全相同（都是层 → 卡 1:N），但语义相反：TP 的每张卡拿到的是碎片（单卡算不出这层的正确输出），DP 的每张卡拿到的是完整副本（单卡能独立算出）。基数相同不代表关系相同——判据在 §06 的那一列「能否独立算出这一层的输出」。

02

静态结构：整网怎么一路拆到硬件

整网是文章，层是句子，算子是词，kernel 是这个词在这块硬件上的发音。四级粒度，一条链。

算子：计算的最小语义单元

MatMul、Softmax、LayerNorm、Add、GeLU、Conv 这些。每个算子做一件明确的数学运算，输入张量、输出张量。它规定"要算什么"，不规定"怎么算"。

层：算子的固定组合模式 层 → 算子 1:N

一个 Transformer 的 Attention 层拆开就是：QKV 三个 MatMul → 转置 / reshape → QKᵀ MatMul → Scale → Softmax → 与 V 的 MatMul → 输出投影 MatMul。硬件眼里不存在"层"，只有一串算子。

但层不是纯粹的人为分组，它有一个硬性质：层与层之间的数据依赖极窄。上一层传给下一层的，只有一个 [batch, seq, hidden] 的激活张量；而层内部的中间张量又多又大——attention score 是 [batch, heads, seq, seq]，量级是 s² 对 s·h，长序列下差出一两个数量级。层间窄、层内宽，这才是层这个概念真正的物理基础，也是后面所有切分都以层为单位的原因。

整网：所有算子按数据依赖连成的那张图 整网 → 层 1:N

模型代码经框架（PyTorch / MindSpore）解析后，本质就是整网：节点是算子，边是张量的流动。训练时框架再自动补上每个算子对应的反向算子，整网规模翻倍。

结构上整网高度重复：embedding → Layer × N → lm_head。所谓 70 层、80 层就是这个 N。一层是整网的层子图模板，整网只是把同一份模板复制 N 份再串起来——权重不同，拓扑相同。

算子 ↔ kernel：接口与实现 N:M

算子 MatMul 规定输入两个张量、做矩阵乘、输出 shape 怎么推导；kernel 是这段语义在具体硬件上的一份实现代码——怎么分块、数据怎么在显存与片上 buffer 之间逐级搬运、计算单元怎么排流水。换硬件、换 dtype、换 shape，算子不变，kernel 要换。

关系基数成因后果
一算子 → 多 kernel1:Nfp16 / bf16、不同数据排布格式、大 shape / 小 shape 各有一份实现，编译期由算子选择挑一份同一算子改个 shape 性能就掉一截——选中的是另一份 kernel，或 tiling 不适配
多算子 → 一 kernelN:1算子融合：Add + LayerNorm + Cast 这类连续访存密集型算子合并中间结果留在片上不落 HBM，整网上节点变少但语义等价
一算子 → 多段 kernel1:N需要 workspace 的规约类算子必须分段执行profiling 的 kernel 计数与整网的节点数对不上，属正常

中间还隔着一层：tiling

kernel 不是拿到张量就能跑。执行前要先算 tiling——把大张量切成能塞进片上 buffer 的小块，决定循环怎么嵌套、搬运和计算怎么流水重叠。同一份 kernel 代码配不同 tiling 参数，性能能差几倍。静态 shape 可以编译期算好，动态 shape 得运行期算，这是动态 shape 性能往往不如静态的原因之一。

先厘清 b：一个词，三个 batch

batch 的字面意思是「一次喂进网络的一组样本」。但在分布式训练里这个词至少指三个不同的量，混用会直接算错显存和吞吐：

名字是什么谁的视角
global batch size
GBS		一次参数更新（一个 step）总共用掉的样本数优化器视角——决定梯度的统计性质，学习率要跟着它调
micro-batch size
MBS		一张卡一次 forward 实际处理的样本数显存视角——激活体大小直接由它决定
gradient accumulation
GA		一张卡累加多少个 micro-batch 的梯度才更新一次调度视角——PP 靠这些 micro-batch 填流水线
 
GBS = MBS × GA × DP

b 这根轴被切了两刀，不是一刀。轴的全长是 GBS；DP 把它切成 DP 段，每段 GBS/DP；GA 再把每段切成 GA 份，每份才是 MBS。所以单卡在任一时刻手里的激活体，对应的是 MBS 个样本，不是 GBS/DP 个。

这解释了容器模型里那条最反直觉的结论

§08 会看到：把 DP 从 2 调到 8，卡数翻四倍，单卡容器却纹丝不动。原因就在这里——DP 动的是 GBS 那一刀，MBS 那一刀没动。激活体只认 MBS。所以「显存不够就加卡」只有在加的是 TP 或 PP 时才成立；加 DP 买的是吞吐，不是余量。

PP 的 micro-batch 与 GA 的 micro-batch 是同一批东西。流水线用来填气泡的那些 micro-batch，正是梯度累积的那些。由此得到一条 §11 依赖链里没单列的隐含约束：用 PP 时必须 GA ≥ PP，否则流水线根本填不满，气泡会占掉大半时间。

一条样本 = 一条序列。[B, S, H] 里 B 是样本数、S 是每条样本的 token 数。注意有些实现用 packing 把多条短文本拼进一条定长序列，这时 B 与「文档数」就不再一一对应了。

「输入」到底是什么：token 只在入口是 token

位置shape是什么

所以「输入」这个词有两个所指：网络的输入（入口的 token id）与某一层 / 算子的输入（上一层的激活）。二者只在第一层重合。

b 索引第几条序列、s 索引这条序列里的第几个位置，所以 token 总数 T = B × S；h 是这个 token 被表示成向量后的宽度。前面说的「CP 切 s」「SP 切 s」「router 逐 token」，切的与数的是同一样东西——只是一个从张量维度说、一个从语义单元说。

这条对应关系解释了一件常被误读的事：MoE 的 top-k 是「每个 token 的扇出」，不是「每层选 K 个 expert」。router 对每个 (b,s) 各做一次 top-k，所以一层的路由边数是 T·K——见 §01 基数表「MoE 层 → 路由边」那一行。

batch size 数的是序列，不是 token。「batch size = 256」不是 256 个 token，是 256 条序列，每条 S 个 token。这是最常见的一处量级误算：S=8192 时那是 200 万个 token，差三个数量级。

batch ── B 条序列
          └ 序列 ── S 个 token 位置
                    └ token ── 一个 H 维向量

token 总数 = B × S      （[B, S, H] 里：B 数序列 · S 数 token · H 是每个 token 的宽度）
token 集合是个矩形，不是一条长队

这一点决定了并行怎么切：token 不是「batch 的元素」，而是 B × S 这个二维网格的格点。

                s 方向（序列内位置，长 S）　←  CP 在这个方向切
        ┌────────────────────────────────┐
   b    │                                │
   方   │        全局 token 矩形          │
   向   │        GBS × S 个 token         │
        └────────────────────────────────┘
        ↑ DP 在这个方向切（空间）＋ GA 再切一刀（时间）

一张卡在任一时刻，手里是这个矩形的一个子矩形。这把前面几条串成一句话：DP 切 b、CP 切 s——两刀切的是同一个 token 集合的两个不同方向；GA 也切 b，只是切在时间上（本节前面那句「b 被切了两刀」）。

micro-batch 与整网 / 算子 / 卡是什么关系

这三者容易被摆成同一排来比，但按 §18 的五类对象一归类就会发现它们不是同一种东西：整网是结构＋内容（图 ＋ 权重体），算子是结构（图上一个节点），卡是容器，而 micro-batch 是地址——b 轴上的一段区间。它既不占体积也没有容量，只用来指认「哪一批样本」。所以它与另外三者的关系一律是「一次执行」，而不是「一部分」。

关系micro-batch 在其中是什么它改变什么 / 不改变什么
× 整网一次完整的穿行。整网是管道，micro-batch 是一次放水整网一个字节都不变——同一份图、同一份权重被 GA 批数据先后穿过；变的只有激活体
× 算子决定执行次数与 shape 第一维：图上一个算子节点，一个 step 内前向执行 GA 次、反向再 GA 次；它看到的第一维是 MBS不改变算子的定义与选中的 kernel；只改变它被调用几次
× 卡决定显存里压着几批中间结果：显存 = 权重体分片（与 mb 无关，常驻）＋「在飞」的那几个 micro-batch 的激活体不改变权重体那一侧；「在飞几个」由调度定——1F1B 是 PP 个，GPipe 是 GA 个（§12）
两条直接可用的推论

一 · mb 号 不是门牌号的第五位。门牌号 (pp,dp,cp,tp) 四位全是空间——划分卡；mb 号 是时间——同一张卡按顺序把全部 GA 批都处理掉。两者正交：空间决定「哪张卡」，时间决定「第几批」。这也是 §12 里 PP 时间线横向宽度的唯一来源——把 GA 调到 1，横轴就塌成一条阶梯。

二 · profiling 时间线上有两级周期。层级的波形（一个 micro-batch 内 L/PP 层重复）套在 micro-batch 级的波形里（GA 批重复）。§12 说「层在时间线上是周期性重复的波形」时讲的是内层；把外层误当成内层，就会把「一批」数成「一层」，整网基线直接算错一个数量级。

一句话收口：micro-batch 不改变「有什么」（图、权重、卡都不动），只决定「这一刻在算谁，以及显存里压着几批的中间结果」。可交互版见 PP 的两张脸——那里的 F0 / B0 里的数字就是 mb 号。

为什么 b 是五根轴里最便宜的一根

样本之间彼此完全独立——这是 DP 能成立的全部理由，也是 DP 通信最稀（整个 step 末才一次）的原因。对比另外四根：s 有 attention 的跨位置依赖、h 有矩阵乘的规约依赖、ℓ 有前后层的因果依赖、e 有路由依赖。b 是唯一一根「切开就不用管」的轴，所以 DP 是最省事、也总是最先被用满的并行。

先把两个对象说透：权重体与激活体

它们各自装的是什么

一个常见的近似说法是「权重体就是整网，激活体就是输入数据」。两处都差一点，而这两处恰好最容易出错。准确说是三样东西，不是两样：

是什么占多少显存被并行切吗
图结构：有哪些算子、怎么连、张量什么 shape。就是 §02 那条粒度链本身几乎不占不切——每张卡都持有完整的图定义
权重体状态：挂在图上的那些数值大头PP 切 ℓ · TP 切 h · EP 切 e

差的第一处：整网 ≠ 权重体。整网 = 图 ＋ 权重体。图说的是「怎么算」，权重体说的是「用什么数算」。图本身几乎不占显存，却决定了一切结构；而且图上很多节点根本没有权重——Softmax、Add、GeLU、Dropout 都是纯计算，一个参数也不带。

差的第二处（更要命）：输入数据 ≠ 激活体。输入只是入口：token id 是 [B, S] 的整数，256×8192 条 int32 也就 8 MB 量级。激活体是这些数据流过整网之后留下的全部中间结果，逐层堆积，量级是输入的几千倍。把「激活体」读成「输入数据」，会低估显存好几个数量级。

一个够用的类比

图是管道网络的图纸，权重体是每个阀门的开度设置，激活体是此刻正在管道里流动的水。图纸不占体积；阀门设置持久存在、每步被微调；水流过就没了，但流的时候整条管道里到处都是水——这正是激活体「按层累积」的由来。

四条直接推论

一 · 共享轴决定了「谁能减什么」。ℓ 与 h 同时属于两个对象，b 与 s 只属于激活体。所以切 ℓ（PP）、切 h（TP）两边都减，切 b（DP）、切 s（CP）只动激活体。§08 容器模型那张表的四行，就是这句话的展开——不必另记。

二 · 生命周期决定了只有激活体能重算。权重体是状态，丢了就真没了；激活体是流量，有确定的生成规则（上一层的输出 ＋ 这一层的权重），丢了可以重跑一遍 forward 再造出来。这就是 activation checkpointing 全部的依据，也解释了它换来的为什么恰好是「算力换显存」——重算花的是算力，省下的是本来要留着等反向的那部分流量。

三 · 权重体在显存里是「×8 出现」的。bf16 参数每个 2 字节，但它带着同样大小的梯度和 6 倍大的优化器状态一起进显存，合计 16 B/参数。所以「参数量 × 2 字节」这个心算永远严重低估显存——它只算了那 16 分之 2。§12 里 7B 模型静态部分约 112 GB 的算法，就是这么来的。

四 · 通信搬的主要是激活体，不是权重体。除了 DP 的梯度规约和 ZeRO 的参数聚合，其余所有通信原语——PP 传层间激活、TP 传层内部分和、CP 传 KV、EP 传 token——搬的都是激活体。由此得到一条不太直观但很有用的推论：通信量主要随 batch 与 seq 增长，而不随参数量增长。换句话说，把模型改大不一定让通信变重，把 batch 或序列拉长却一定会。

两处边界

梯度与优化器状态严格说属于权重体。它们与参数同 shape、被同一组并行维度以同样方式切分，所以本文说「权重体」时默认含这三样；只在讨论字节数时才拆开算。

KV cache 是个混血，本文不展开。它的形状像激活体（随 b、s 增长），生命周期却像权重体（跨多步持续）——本质是被冻结成状态的激活体。这只在推理场景出现，本文是训练视角。

拆开算：梯度与优化器状态各是什么

上面的对照表写了「权重体在显存里出现 3–4 份，合计 16 B/参数」。下面把每一份拆开，说清楚它是什么、为什么必须存在、为什么用这个精度。

梯度：每个参数该往哪个方向调

前向跑完后，算出一个标量 loss（"模型预测得有多差"）。梯度就是 loss 对每一个参数的偏导数 ∂L/∂W——"如果把这个参数往某个方向动一点点，loss 会变多少"。

反向传播从 loss 出发，沿计算图逆向走一遍，用链式法则逐算子往回推，最终给每个参数算出一个梯度值。梯度和参数同 shape——参数矩阵是 [H, 4H]，梯度矩阵也是 [H, 4H]，每个位置告诉优化器"这个位置该怎么调"。

梯度算出来后不能立刻用，因为 DP 下每张卡只看了自己那份数据，算出来的梯度是局部的。必须先做一次 AllReduce（梯度同步），把所有 DP 副本的梯度平均之后，才能交给优化器去更新权重。所以梯度必须在显存里存着——从反向传播算出来，到梯度同步做完，这段时间它不能丢。

环：一个 step 内，权重 · 激活 · 梯度 · 优化器状态谁先谁后

把上面拆开的三份（梯度、m、v、master weight）和权重、激活放回同一张卡上看，它们不是四类互不相干的内存，而是同一份参数切片沿一条环形因果链上的四个瞬时快照。次序是硬约束，不能打乱、也不能反着来：

前向  权重 W(t) × 激活 A         →  out，A 暂存
反向  ∂L/∂out × 激活 A         →  梯度 ∇W，A 释放
同步  DP 组 AllReduce(∇W)       →  全局梯度
更新  优化器态(m,v,master) + ∇W  →  权重 W(t+1)，∇W 释放
              └──────────────────────────┘
                     回到前向，循环

三处次序上的硬约束，每一处都对应显存里"谁跟谁同时压着"的真实窗口：

  1. 激活必须活到反向，用完立即释放。它是算出这份梯度唯一需要的原料（上一层输出 ＋ 本层权重）。这正是前面推论二"只有激活体能重算"的另一半：它不仅丢了能重算，生命周期还被反向传播这一刻硬性框定——过了这一刻就是废料，没有理由继续占显存。
  2. 梯度从算出到被优化器吃掉之前，必须和权重同时驻留显存。这段窗口从反向传播产出 ∇W 开始，到 DP AllReduce 完成、优化器 step 跑完为止；一过这个窗口梯度立刻释放。峰值显存正好落在这段窗口内，不是巧合。
  3. 权重永远是"旧的算出新的"，不能反过来。拿 W(t+1) 去算这一步的梯度在因果上不成立。优化器状态同样在环上——这一步更新完的 m、v 是下一步的输入，不是本地终点。
和"状态 vs 流量"框架的关系

这条环不是新结论，是把前面"状态 vs 流量"的区分落到时间轴上：权重、梯度、优化器状态都属于状态一侧，常驻显存、被逐步更新；激活属于流量一侧，一个 step 内生灭。区别在于——状态一侧这三样虽然都算"常驻"，常驻的时间窗口并不对齐：权重和优化器状态全程都在，梯度只在"算出"到"被优化器吃掉"这一小段窗口内才和它们叠在一起。

唯一不在这条链上的是显存里的碎片 / workspace 预留——它是分配器与算子实现的副产品，不对应任何一份具体参数，编不进这条因果链。

对 viewer 的推论：一个 rank 里这几档该怎么摆

这条环不只是解释显存为什么这样长，还回答一个具体的界面问题：如果要在一张卡的面板里把权重、梯度、优化器状态、激活画成并排/堆叠的几块，摆放顺序该听谁的？两条规则叠加使用：

  1. 先按生命周期分组。权重、梯度、优化器状态是「常驻组」——16 B/参数那个恒定地板，全程都在；激活是唯一的「流量」，随在途微批数脉动；碎片/预留什么刀都没挨，不参与这条因果链。三组之间要有清楚的视觉断点：常驻地板 → 会脉动的部分 → 无归属的余量。
  2. 组内再按"谁跟谁共存的时间最长"决定相邻关系。权重放最前，当基准（它是链首也是链尾）；梯度紧挨着权重——梯度存在的窗口（算出到被优化器吃掉）完全叠在权重常驻的时间线内；优化器状态放梯度之后，收尾常驻组，因为它是"更新"那一步唯一同时读梯度、写新权重的一方。

由此得到的顺序：权重 → 梯度 → 优化器状态 → 激活 → 碎片。

这条顺序验证到什么程度——分三层说，不能笼统打勾

因果链本身与 16 B/参数的拆法，有外部文献支撑，不是这个代码库自证的。ZeRO 论文（Rajbhandari et al., 2020，ZeRO: Memory Optimizations Toward Training Trillion Parameter Models）给出的正是同一套拆分：bf16/fp16 参数 2 B ＋ 梯度 2 B ＋ fp32 master weight 4 B ＋ Adam 的 m、v 各 4 B，合计 16 B/参数。fp32 master weight、以及"梯度先在 fp16/bf16 下算出、转成 fp32 才用来更新 master weight"这条机制，出自 Micikevicius et al., 2017《Mixed Precision Training》——原文明确写着梯度需要从 fp16 转换到 fp32 才能拿去更新 fp32 的权重副本。激活"用完即焚、可以靠重算换回来"这条，出自 Chen et al., 2016《Training Deep Nets with Sublinear Memory Cost》，是 activation checkpointing 的原始出处。三篇论文相互独立、也独立于这个代码库存在，结论一致——因果链和字节数不是靠一份实现自证的。

宏观分组（常驻三档在前、激活单独、碎片垫底）与现有实现一致，但这只说明"至少有一份实现这么摆"，不构成理论证明。上面三篇论文回答的是"这几样东西有没有、多大、什么时候存在"，不回答"面板上该摆在哪个位置"——视觉排布本身不是它们关心的问题。

组内一处细节，仍只是本文的推理，没有外部依据。Micikevicius et al. 证实了"fp32 梯度转换缓冲"这个机制确实存在、且是梯度到 master weight 转换路径上的一步；但由此推出"它在面板上该紧贴着梯度摆、不该贴优化器状态"，是本文自己做的界面设计延伸——论文不讨论可视化布局，现有实现也没有这样摆（它排在优化器状态后面），也没有可用性测试支持"贴得更近＝更容易看出衍生关系"。这一层继续如实标为推理，不升级为已验证的结论。

推论一：为什么恰好是四个乘数

ℓ、h、b、s 四根轴全网每一层都存在，各自能贡献一个独立乘数：

world_size = TP × CP × PP × DP

e 这根轴只在 MoE 层存在，非 MoE 层根本没有 expert 编号可切。一根时有时无的轴撑不起一个全局并行维度，所以 EP 只能借用已有平面上的卡重新分组。这才是「EP 不是第五个并行维度」的根本原因——「它是对 DP×TP 平面的重新解释」只是这个原因在旧版实现上的表现形式；新版换成了两套独立分解 + 中间重排，结论不变，见 §13 勘误 M。

切分：五种并行各切哪一维

每种并行都是在对某一个维度做切分。切的维度不同，作用的粒度就不同——这是理解整套策略最省力的入口。

逐个说清楚

DP 每张卡持有完整整网，各算各的数据，反向后 AllReduce 梯度。ZeRO / FSDP 是 DP 的变体——只是把参数 / 梯度 / 优化器状态的存储也切了，计算时仍临时聚合成完整整网。

PP 把整网按层切成若干 stage，每个 stage 内的层和算子都是完整的，stage 之间只传激活值，用 micro-batch 填流水线来掩盖气泡。

TP 一个 Linear 的权重被按列 / 行切开，单个 matmul 被分解到多卡上。它是唯一把算子的参数分片、需要改写算子本身的并行。

SP TP 只切了 matmul，LayerNorm / Dropout 这些区域的激活值仍是完整的；SP 把这些区域的激活值沿 seq 维也切开，顺势省下显存。所以 SP 与 TP 同域同大小，不占独立的并行维度。

CP 为长序列服务。逐 token 独立的算子（Linear、LayerNorm）天然不用通信；只有 Attention 需要看到全序列，所以通信集中在 attention 处。

EP 不同 expert 放不同卡，token 经 All-to-All 路由过去再回来。只作用于 MoE 层，非 MoE 层不受影响。每个 expert 在它那张卡上是完整的——算子没被改写，这一点与 TP 有本质区别。

嵌套顺序：由通信频率和通信量决定

TP / SP 通信最频繁（每层两次集合通信、量大），必须放最内层，绑在机内高带宽互联上。CP 次之，也尽量留在机内。PP 单次通信量最小（只传 stage 边界的激活），放外层、可以跨机。DP 每个 step 才通信一次且可与计算 overlap，放最外层。

world_size = TP × CP × PP × DP

64 卡示例：TP=4 · CP=2 · PP=2 · DP=4
  4 卡捆成一个 TP 组  →  相当于一个不可再分的调度单元
  2 个 TP 组拼成 CP 组
  纵向切成 2 个 pipeline stage
  这样的"整网副本"复制 4 份跑 DP

每往外一层，就是把内层的整体当作一个单元再复制或切分——这就是嵌套关系的本质。

TP 具体怎么切：列切与行切必须配对

前面只说了「TP 沿 h 切权重矩阵」。但一个 Transformer 层里是两个连续的矩阵乘，怎么切才不会在中间也要通信？答案是：第一个列切、第二个行切，配成一对——这是 TP 全部机制所在。

MLP 块：列切 → 行切

X [B,S,H] ──W1 [H,4H]──▶ Z [B,S,4H] ──GeLU──▶ ──W2 [4H,H]──▶ Y [B,S,H]

TP=2 切法：
  W1 按列切   [H, 4H] → 每卡 [H, 4H/2]      每卡算 X @ W1ᵢ → Zᵢ [B,S,4H/2]
                                                   ← X 每卡都要完整的
  GeLU            逐元素，直接在分片上做       ← 列切的关键理由
  W2 按行切   [4H, H] → 每卡 [4H/2, H]      每卡算 Zᵢ @ W2ᵢ → 部分和 [B,S,H]
  AllReduce       把各卡的部分和加起来 → 完整 Y     ← 全层唯一一次通信

为什么必须列-行配对？若 W1 也按行切，算完 Z 就是「按 4H 维分片的完整值」，而 W2 行切需要的正是这种分片——看似也行；但 GeLU 之前若 W1 按行切，每卡拿到的是部分和而非真值，非线性函数不能作用在部分和上（GeLU(a+b) ≠ GeLU(a)+GeLU(b)），就必须先 AllReduce 一次。列切 → 行切是唯一能让中间那步免通信的组合：列切让每卡拿到「一部分神经元的真值」，非线性可以逐元素照做；行切再把它们规约回来。

Attention 块：按 head 切 → 行切

W_Q / W_K / W_V   按 attention head 切：每卡拿 num_heads/TP 个完整的 head
                    ← head 之间本来就互不依赖，所以按 head 切不需要任何通信
attention          在本卡的局部 head 上完整算完（含 softmax）
W_O                按行切 → 部分和 → AllReduce

所以一层两次 AllReduce：attention 块一次、MLP 块一次；反向同样两次。这就是 §01「MoE 层 → All-to-All 次数」旁边那条「TP 每层两次」的由来，也是 TP 必须绑机内高带宽域的全部理由——频率最高。

这解释了 TP 的三条约束
  • num_attention_heads % TP == 0（§11）——因为切的粒度是整个 head，不能把一个 head 劈开。GQA / MQA 下还要 num_query_groups % TP == 0。
  • TP ≤ 高带宽域卡数——每层两次集合通信，频率碾压其他所有维度。高带宽域的半径由载体决定：传统平台上等于一台机（典型 8 卡），灵衢超节点上等于整个超节点（384 卡），见 §19 与 §16 勘误 Q。
  • TP 是「分片」不是「划分」（§01）——它把单个权重矩阵拆开，算子本身被改写成分片算子，各卡算的是同一个 matmul 的不同部分；PP / EP 则是把完整单元分开放。这正是 TP 的归属边界被推到 kernel 那么深的原因（§02）。

SP：TP 的省显存伴侣

列切-行切这套只覆盖两个 matmul 之间那段——LayerNorm / Dropout 那些区域 TP 切不到（它们要的是完整的 h）。没有 SP 时，这些区域每卡存一份完整激活 [B, S, H]，浪费。

SP 补的正是这一段——在非 TP 区域沿 s 再切一刀，复用 TP 的通信域。SP 不是一个独立的并行维度——它不产生新的通信组、不改门牌号，只是在 TP 组内部把激活"转着存"：

一层内部的布局切换（TP = 2 为例）

 SP 区（LayerNorm / Dropout）      TP 区（matmul）
 每卡持有 [B, S/2, H]             每卡持有 [B, S, H/2]
       ↓ 切 s，完整 h                   ↓ 完整 s，切 h

 进 TP 区：AllGather 沿 s 拼回 → 列切 matmul 自然沿 h 分开
 出 TP 区：ReduceScatter（= AllReduce + 沿 s 切开）→ 回到 SP 布局

关键：ReduceScatter 取代了原来的 AllReduce，通信量相同；但出来的激活从 [B, S, H] 变成 [B, S/TP, H]——省了 TP 倍激活显存。所以 SP 不加通信、不加新卡，纯粹是在 TP 组内部把激活"转着存"。实际项目里 SP 几乎总是跟 TP 一起开——开了没有代价，不开白浪费显存。

SP 为什么几乎总是开

SP 是极少数纯赚不赔的优化——它不加通信、不加卡、不改算子，唯一的效果是激活显存省 TP 倍。只要 TP > 1，就该开 SP。Megatron-LM 中 TP > 1 时 SP 默认启用。

为什么是"免费"的？纯 TP 在每个 matmul 之后做 AllReduce（通信量 = 2×数据量）。SP 把 AllReduce 拆成两半：出 TP 区做 ReduceScatter（通信量 = 数据量），进 TP 区做 AllGather（通信量 = 数据量），加起来总通信量完全一样——只是把一次集合操作拆成两次更小的，分别放在 TP 区的两端。

省下来的显存能干什么？

  • 加大 micro-batch → 每步处理更多样本，提高 GPU 利用率
  • 加长序列 → 支持更长上下文（激活量随 S 线性增长）
  • 减少 activation checkpointing → checkpointing 是拿计算换显存的，显存够了就不用换，省下重算的时间

Router 值得单独看一眼

它是 MoE 层里唯一两个维度都不切的权重（[H, E]，每卡一份完整副本）。原因很实际：它必须为本卡的每个 token 算出完整的 E 个门控分数才能取 top-k，切了就得先聚合。它很小（H×E 对比 expert 的 E×H×4H），复制的代价可以忽略。

勘误 A · EP 不是第五个并行维度

先前写作"总卡数 = TP × CP × PP × DP，EP 通常复用 DP 组的卡，或单独成维"，后半句不准确。EP 不是独立于这四个并行维度之外的额外乘数——它是对 MoE 层重新解释已有的 DP × TP 平面上的那批卡：非 MoE 层按 TP/DP 走，MoE 层把同一批卡重新分组成 EP 组。实现上通常要求 EP 组大小能整除对应平面的大小。所以世界大小仍是 TP × CP × PP × DP，EP 是这个网格上的一个视图，不是一条新的边。FIG 06 里选「EP 组」时高亮的正是同一 stage 的整个 TP×DP 平面，而不是新增一个轴。

勘误 B · "TP 是唯一切进算子内部的并行"说得太满

准确的说法是：TP 切分算子的参数（权重矩阵被拆开，matmul 本身被分解重写）；CP 切分算子的输入，但它同样要求 attention 算子改写——Ring Attention 需要 flash-attention 式的分块 online softmax 累加，逐块更新 running max 与 running sum，才能在只看到部分 KV 的情况下算出正确结果。所以"需要算子级改写"的有两个：TP 和 CP，只是改写的对象一个是参数、一个是规约方式。EP 和 PP 则完全不动算子。

样本之间彼此独立，token 之间不独立。

DP 能成立正是因为 batch 里的样本互不相干，副本可以各跑各的一路到 step 末。CP 如果 token 也独立，就会和 DP 一模一样——事实上对 Linear、LayerNorm、激活函数这些逐 token 的算子，它确实就是那样，一次通信都不用。只有 attention 需要看到全序列，所以 CP 每撞上一次 attention 就得对一次账。

CP 就是「会漏的 DP」，漏点只有一个，就是 attention。

佐证

CP 域在 step 末同样要参与梯度规约——各卡看到的序列片段不同，算出的梯度自然不同，必须求和。实现上通常直接把 CP 域和 DP 域合并成同一个规约域。这是它属于 DP 一族最直接的证据。

Ring Attention：CP 怎么对账

CP 的代价全落在 attention 上。每张卡只有 S/CP 段的 Q 和 KV，但 attention 要求每个 query 位置看到所有 key/value 位置。Ring Attention 的做法：

  1. 初始状态：CP=4，4 张卡排成环。卡 i 持有 Q_i（本地 query）和 KV_i（本地 key/value）。
  2. Step 0：各卡用 Q_i 对本地 KV_i 算 partial attention，记录 running max 和 running sum。
  3. Step 1：KV 块沿环传递一步（卡 0→1, 1→2, 2→3, 3→0）。各卡用 Q_i 对收到的 KV 块再算一次 partial attention，用online softmax 累加到之前的结果上。
  4. Step 2–3：继续传，直到传完一圈。每卡看过了所有 KV，attention 结果完整。

关键约束：必须用 online softmax（flash-attention 式的 running max + running sum 逐块累加）。普通 softmax 需要先看到所有 score 才能算分母，做不了分块。这就是 §04 勘误 B 说的"CP 也需要算子级改写"——改写的对象是 softmax 的规约方式，不是参数。

CP 贯穿全部 stage，不只在入口

一个常见的误解是"CP 在第一个 stage 把序列切开，后面就拼回去了"。事实上CP 的切分从入口一直贯穿到最后一个 stage：

  1. 入口：Token IDs / Position IDs / Attention Context 的序列维被切成 S/CP 份，每张卡只拿到自己那一段。
  2. PP 传递：stage 边界传递的是激活 [B, S/CP, H]——不会拼回完整序列。PP 的 P2P 只负责"本卡的那份激活往下传"，跟 CP 正交。
  3. 每个 stage 内部：所有 layer 都只处理 S/CP 个 token。Linear / LayerNorm / GeLU 不需要看全序列，直接算。只有 Attention 要看全序列，所以每个 stage 的每层 attention 都要做 Ring Attention。
  4. 输出：只有在最终算 loss 时才需要把各 CP 卡的结果汇总。

为什么不在 stage 之间拼回去再切开？因为没有好处——PP 的 P2P 通信只需要发送本卡那份激活，拼回去反而要一次 AllGather，白白加通信。CP 的切分是全程常驻的状态，不是一次性操作。

SP 的原理：AllReduce 换成 ReduceScatter

SP 的核心改动只有一处：把纯 TP 的 AllReduce 替换成 ReduceScatter。理解这一步，SP 就全明白了。

先看纯 TP（没有 SP）的通信：行切 matmul 之后每张卡持有 partial sum，需要 AllReduce 求和。AllReduce = ReduceScatter + AllGather，通信完成后每卡都持有完整结果 [B, S, H]。但接下来的 LayerNorm / Dropout 是逐 token 独立的——不需要完整 S，只要自己分到的那几个 token 就够了。

SP 的改动：

  • 出 TP 区：只做 ReduceScatter（AllReduce 的前半）→ 每卡得到 [B, S/TP, H]，只占 1/TP 的显存
  • 进 TP 区：做 AllGather（AllReduce 的后半）→ 拼回 [B, S, H]，送进列切 matmul

把 AllReduce 拆成两半，分别放在 TP 区的两端——通信总量完全相同，但 TP 区外的激活从 [B, S, H] 缩到 [B, S/TP, H]，省 TP 倍。这就是 SP"不加通信、纯省显存"的原因。

布局切换的实质

TP 区：每卡持有完整 S、切 H → 形状 [B, S, H/TP]
SP 区：每卡持有完整 H、切 S → 形状 [B, S/TP, H]
AllGather 和 ReduceScatter 就是这两种布局之间的转换器——沿 s 拼回 / 沿 s 切开。SP 没有自己的通信组，复用 TP 组。

CP × SP：两者同时开启时发生什么

CP 和 SP 都涉及序列维 s，但它们在不同的通信组、不同的嵌套层次上各切一刀，互不冲突。

对 viewer 的推论

CP 需要一个正交的视图，而不是在卡网格上硬加一根轴。卡网格回答「模型怎么分布」，CP 属于另一个问题——「输入怎么分布」。两个问题各配一张图，比塞进同一张更清楚：卡网格视图放 TP × PP（＋ EP 作为 MoE 层的重解释），输入分布视图放 DP × CP。这也界定了 axis= 这类参数的语义边界：CP 不属于卡网格的 axis 集合，它该是个独立的视图开关。

ZeRO-3 / FSDP 为什么不在这张表里

它们是 DP 维度内部的显存优化：把权重在 DP 组内再切一刀，用的时候临时 AllGather 拼回来。不产生新通信组、不改门牌号、不改并行拓扑——只改变了每张卡"平时常驻什么"。对拓扑视图来说，一条脚注足矣。

CP=1 是默认选择——决定它的是序列长度，不是卡数

128 卡、256 卡、1024 卡——卡数不影响 CP 的取值。CP 回答的唯一问题是：一条序列的中间激活在一张卡上放不放得下？

激活显存 ∝ mb × s × h（§08）。序列长度 s ≤ 32K 且开了梯度重计算时，激活体在 64 GB 卡上通常不构成瓶颈，CP=1 足矣。只有当 s 进入 128K+ 区间、单卡激活显存即使重计算仍然放不下时，才需要 CP≥2 把序列切开——每多一路 CP，每张卡上的 attention 就要多做一轮 Ring 通信。

经验阈值（仅参考量级）：H=8192 · bf16 · 开重计算 · 64 GB 卡：s ≤ 32K → CP=1；s ∈ [64K, 128K] → CP=2；s ≥ 128K → CP=4+。实际阈值取决于 H、MBS、重计算策略和框架开销。不要因为"卡多"就开 CP——那是 DP 的事。

06

映射：层与卡是多对多

三处说到"层"，指的都是整网定义里的同一种逻辑单元。层数永远是 N，不会因为并行策略而变多变少。变的不是层本身，是"层 → 卡上实例"的映射方式。

涉及的层单卡持有的映射性质层 → 卡能否独立算出这一层的正确输出
PP不同的层完整的层划分（沿深度切开一串层）N:1能
TP同一层层的分片分片（把层内的权重矩阵拆开）1:N不能（算出的是部分和）
DP同一层完整的层复制（同一层的多个副本）1:N能
EP同一层层内部分 expert（各自完整）划分（沿宽度分开放）1:N不能（token 需路由）

注意第 5 列：TP、DP、EP 三者的基数完全相同（都是 1:N），但映射性质三不相同。基数只回答「几对几」，不回答「是什么关系」——第 6 列那个判据才是区分它们的东西。这是 §01 那条提醒的具体落点。

这个判据和通信位置完全对应：PP 的通信在层的边界，DP 的在层之外（step 末），TP / EP 的在层的内部。所以"这一层在物理上不属于任何单卡"这句话，只对 TP 和 EP 成立，而且成立的理由不同。

勘误 C · EP 不该和 TP 并成"一层多卡"

先前把 TP 与 EP 一起归为"一层多卡的常态"，混了两件事。TP 是把单个权重矩阵拆开，算子本身被改写成分片，各卡算的是同一个 matmul 的不同部分。EP 是把层内并列的多个 expert 分开放，每个 expert 在它那张卡上是完整的，算子没被改写；层不完整是因为 expert 集合不全 + 需要路由。
从这个角度看，EP 更像 PP 的兄弟——都是把完整单元分开放，只是 PP 沿深度、EP 沿宽度；TP 才是那个真正把算子分片的。

为什么切分几乎总以层为单位 层 → stage N:1 stage → 卡 1:N

因为层间那条窄依赖是天然的低成本切口。PP 沿层边界切，卡间只需传一个激活值；如果切在层中间（比如 softmax 和后面那个 matmul 之间），要传的中间张量往往大一个数量级。

这带来一个实际约束：PP 的最小切分粒度就是层，层数除不尽 stage 数就会负载不均。

勘误 D · PP 负载不均不止"除不尽"

先前只提到"80 层切 6 个 stage 必然有卡多扛"。补充：即使整除也不均——第一个 stage 还要背 embedding，最后一个 stage 要背 lm_head 和 loss 计算（词表大时这部分显存和算力都很可观）。所以实践中常见的做法是首尾 stage 少分几层，做非均匀切分。把"层数 ÷ stage 数"当成唯一的均衡判据会漏掉这一项。

PP 决定层去哪几张卡，TP / EP 决定层在那几张卡里怎么碎，DP 决定这套安排复制几遍。层作为概念自始至终没变，变的只是它被映射到硬件上的方式——这正是讨论并行时层始终是最省力参照单位的原因。

07

逻辑侧 ↔ 物理侧：两条链不是逐级对齐的

逻辑侧五级、物理侧七级——连级数都对不上，更不用说逐级对齐。级数变多，落点没变。最关键的一点：所有并行切分都收在物理侧的同一级上。

上四级、下两级都不参与切分

  • 集群、超节点、机柜、node：不参与切分，只决定拓扑与带宽。上四级的存在只影响「TP 域必须在高带宽域内、PP 域可以跨高带宽域」这类约束，不改变切法——高带宽域的边界由硬件给定：传统单机上它等于机（8 卡），灵衢超节点上它等于超节点（384 卡 · 48 node · 16 机柜）。
  • 计算单元、片上 buffer：与并行完全无关。tiling 也是切，但不跨卡、不通信、不改语义。

物理侧不是五级：机以上还有三级

以灵衢 UnifiedBus / CloudMatrix384 为例，机（node）往上还有三级：集群 → 超节点 → 机柜 → node → 卡 → 计算单元 → 片上 buffer，物理侧从五级变成七级。✅ 已核实-原文 arXiv:2506.12708 §3.3.2–3.3.3 给出的默认尺寸是：perNode=8（每 node 8 张 NPU）、nodeRack=4（每机柜 4 node）、podCards=384（每超节点 384 卡）——一个超节点 ＝ 48 node ＝ 384 卡 ＝ 16 机柜（12 计算柜 + 4 通信柜）。这三个数字在 viewer 里是 URL 可配参数（?perNode=&nodeRack=&podCards=），不是写死的硬件常量，本文按 CloudMatrix384 的公开规格举例作为默认值，不代表所有灵衢部署都是这个尺寸。

互联侧有三张平面，各管一件事：UB 平面——超节点内非阻塞全互联，承载 TP / EP 并行与显存池化 ✅ 已核实-原文 arXiv:2506.12708 §3.2；RDMA（RoCE）平面——跨超节点 scale-out，训练场景下论文只给了一句无数字的泛述（支持分布式训练框架间通信），推理场景下论文验证过用于 PD 分离间的 KV cache 传输；VPC 平面——管理面与持久化存储，训练数据面不走这张网。一句话结论：七级链里只有一处是换挡点，在超节点边界，不在 node（机）边界——下面的判据表要坐实这一点；寻址粒度、板内/板间/机架间是否同档、平面选择由哪一层决定这三个仍待灵衢团队确认的口径问题，见 §20 留白。

为什么偏偏是卡：一个判据，三个身份

「都落在卡上」不是约定俗成，是可以推出来的。先把「并行切分」这个词说严：

判据

一刀算不算并行切分，看它是否改变状态的归属——切开之后，索引空间的不同子块分属不同的持有者，且按 §02 的通则，切口处必须插入通信算子来补齐。这句话预设了持有者必须具备三种能力：私有地址空间（归属才有边界）、通信端点（补齐才有收发方）、独立执行流（分片才能同时被算）。

把这说到底就是一句话：地址空间的边界在哪里，并行的落点就在哪里。并行切分本质是「把索引空间的子块分派给不同的地址空间」（§10：rank 元组是地址）；物理七级里，归属的粒度恰好就是卡——往上即使有更大的统一寻址（灵衢 UB 让超节点内 384 卡互相直接读写对端显存），那也只是可达性扩大，不是归属合并：peer 访问与 UB 都是搬运手段，框架的归属记账仍以卡为界；往下没有更小的独立地址空间。

UB 统一寻址会不会推翻这句话

不会。灵衢 UnifiedBus 在硬件层给出的是全局统一寻址与路由——UB 交换芯片能把一张 NPU 发起的访问请求直接路由到超节点内任意一台 MP Server 的显存 ✅ 已核实-原文 arXiv:2506.12708 §3.6.2。但判据是三种能力的合取，不是一项：超节点即使有统一寻址，它仍然不是通信端点（是端点的集合），也没有独立执行流（384 张 NPU 各有各的流）——三缺二，进不了 (pp,ep,dp,cp,tp)→global_rank 的值域，因为没有一个执行流去算「分给超节点」的那个分片，也没有一个端点去收发它。

更根本的是：统一寻址扩大的是可达性（谁能读到谁的字节），判据要的是归属（这些字节记在谁名下）。这与 peer 访问、offload 是同一种形状——peer 访问早让 A 卡直读 B 卡显存，offload 早让 rank 把状态暂存到 host DRAM，量级和路径都不同，但都没有把落点挪走。UB 只是把这个「搬运手段」的半径从 8 卡的机扩到 384 卡的超节点。代码这一侧也自证：FusedDispatch/FusedCombine 里 AIV 核直接写对端 NPU 显存，「对端」这个词本身就预设归属边界还在 ✅ 已核实-原文 arXiv:2506.12708 §3.5.2；viewer 的 fabricOf / commLoad9 全部以 rank 为索引，没有一处以 pod（超节点）为持有者。

真正会推翻这句话的情形是：384 卡上只跑一个执行流、rank 数从 384 降到 1，框架的分片记账不再以卡为单位——那时超节点才被改造成「卡等价物」，落点才会上移，这与本节 MIG 那条压力测试互为镜像。CloudMatrix384 不是这样：每张 NPU 各绑一个 rank，HCCL 成员表仍是 global rank 列表。也不必等灵衢团队回答寻址粒度是统一虚拟地址空间还是 rank → 预注册 buffer 的静态映射（§20 留白）——两种候选答案都不改变这个结论，因为归属记账在框架侧，不在 MMU / 寻址层。

还可以换一个函数视角：整个并行配置就是一个映射 (ℓ, e, b, s, h) → (pp, ep, dp, cp, tp) → global_rank → 卡，值域是卡的集合。集群 / 超节点 / 机柜 / node 从不出现在这个函数里，只影响「哪个函数是好主意」（§11 的 order 与整除约束）；计算单元与 buffer 只在函数求值之后出现——卡拿到自己那块之后怎么算，已经与「分给谁」无关。卡是「分派」与「执行」的交接面：以上决定哪张卡算，以下决定这张卡怎么算。级数从五变七，这个函数的定义域与值域一个字没变。

与 §02 的对偶

§02 说两条链在 kernel 处汇合——那是逻辑侧的唯一交点；本节说四条并行映射在卡处汇合——这是物理侧的唯一落点。两者是同一事实的两面：kernel 按定义是一张卡上的一次执行（「不可再跨卡的那一级」），卡按定义是 kernel 排队执行的地方。TP 把归属边界推到最深（kernel）时落点仍是卡——因为「归属」这个概念本身就是以卡为单位定义的。

口径核对

与实现对得上：Megatron / torch.distributed 里 world_size ＝ 进程数（标准排布一进程绑一卡，§10），所有并行组（TP / CP / PP / DP / EP 组）的成员都是 global rank 的列表；initialize_model_parallel 的输入只有各维大小与 order 字符串——「机」「机柜」「超节点」这些概念在切分语义里都没有入口，它们只通过两条侧门进入：① rank 排布约定——stride 1 的组落在同一个 node 上（§11）；灵衢之后真正要看的不是它落不落在一个 node，而是整组在不在同一个超节点内（跨了才换挡）。② 配置约束——TP ≤ 高带宽域卡数：传统机上是机内卡数（典型 8），灵衢超节点上是 384。

所以「整网怎么在卡上切分」这个问题，答案的全部信息都在卡这一级。这也解释了为什么单卡视角（显存里放了什么 / 流上排了什么）能撑起那么多诊断——并行的一切后果都在那里落地。

机制：切分是怎么真的落到卡上的

上面说的都是「对应关系」。但实际跑起来，配置写在整网上、执行发生在卡上，中间那段过程是什么？这里有一个反直觉的事实值得先摆出来：

「切整网」从来没有真的发生过

没有哪一刻存在一个完整的整网、然后被切开分发。每张卡从一开始就只构造自己那一份——PP 只实例化本 stage 的那几层，TP 只分配权重矩阵的那一条，EP 只建自己那几个 expert。切分是「按 rank 各自少建」，不是「建好再分」。

这正是 SPMD 成立的样子（§10）：所有卡跑同一份代码，各自按自己的门牌号取自己那一片。「整网被切开」是一句逻辑描述，不是物理过程。

三处最容易搞反的地方

常见说法实际是怎么验证
「卡一开始就有门牌号」 一开始只有一维的 global_rank（启动器分配）。四位门牌号是 initialize_model_parallel 算出来的，方向是 global_rank → (pp,dp,cp,tp) 换个 order 字符串，同一张物理卡的门牌号就变了（§11）——若门牌号是卡固有的，这不可能发生

完整的故事链条：跟住一张卡走完一个 step

把上面五步讲成一个能复述的故事。配置 TP2·CP1·PP4·DP16 = 128 卡，整网 48 层、H=8192，GBS=512 · S=8192 · GA=8 → MBS=4。我们跟住 global_rank = 41 这一张。

第 0 幕 · 开机：128 个一模一样的进程

启动器拉起 128 个进程、各绑一张卡。此刻它们唯一的差别是一个数字 global_rank（0…127），代码完全相同，谁也还不知道自己该干什么。

第 1 幕 · 报到：一维编号变成四位门牌

配置到位：order = tp-cp-ep-dp-pp。每个进程各自算了一遍同样的除法，41 号解出 (pp=1, dp=4, cp=0, tp=1)——我是第 1 号 stage、第 4 个副本、权重矩阵的第 1 条。顺带它也算出自己在哪些组里：TP 组 {40, 41}、PP 链 {9, 41, 73, 105}、DP 组 {33, 35, …, 63}。

没有人告诉它这些，是它按同一份公式自己算出来的——换个 order，它算出的就是另一组。

第 2 幕 · 备料：只建自己那一份（只做一次）

整网 48 层。41 号看自己的 pp=1，只实例化 L12–23 这 12 层——其余 36 层的权重它连显存都没申请。再看 tp=1，每个权重矩阵只建右半边 [8192, 16384]。

整网从头到尾只存在于代码里，物理上从来没有在任何一处被完整实例化过。最后它在切口插好通信算子：层内两处 AllReduce（和 40 号一起）、stage 边界的 Send/Recv（收 9 号的、发给 73 号）。这一幕做完就冻结，整个训练不再变。

第 3 幕 · 进料：token 每步换一批

数据集 512 条序列 × 8192 token ＝ 420 万个 token。41 号按 dp=4 取第 4 份的 32 条，再按 GA=8 切成 8 批、每批 4 条（MBS）。它此刻手里是 [4, 8192] 个 token id，过 embedding 成 [4, 8192, 8192] 的激活。

留意谁跟它拿到一样的东西：40 号（同 TP 组）拿到逐字节相同的 token（TP 切的是权重不是数据）；9 号 / 73 号（同 PP 链）也是同一批（它们是流水线的前后站）。真正拿到不同数据的，只有 dp 不同的那些卡。

第 4 幕 · 开算：算子落成 kernel

两样都齐了：权重片 [8192, 16384] ＋ token 片 [4, 8192]。41 号开始跑 L12–23 的算子，每个算子看到的 shape 都已被除小。

但算子还不能直接跑：编译器按 shape + dtype + 硬件 挑一份 kernel 实现、把访存密集的几个融合掉、算好 tiling，再把 kernel 逐个排进流。这里正是两条链唯一的交点——算子（逻辑侧末级）与 kernel 队列（物理侧末级）在 kernel 处碰头（§02 · FIG 03）。

第 5 幕 · 接力与收束

前向算完，41 号把激活 P2P 发给 73 号，转身去接 9 号送来的下一个 micro-batch——这就是流水线。8 批的前向与反向都走完之后，它才和 DP 组的其他 15 张卡做这个 step 唯一的一次梯度 AllReduce。参数更新，回到第 3 幕重来。

从这段能直接读出三件事

  • 对单个算子实例而言，PP 是筛子，其余三个是除号。PP 决定这一层在不在这张卡上（有 / 没有），TP / CP / DP 决定在的话剩多大。注意这个说法只在「盯着一个算子」时成立——对整张卡而言，PP 同时也是层数的除号（L/PP）。

四刀有没有先后：地址的四个数位，不是四道工序

FIG 10 从上到下一刀接一刀，容易读成流水工序。其实那是叙述顺序：四刀作用在四根互不相干的轴上（层号、隐藏维、token 位置、样本号，§03），构成笛卡尔积，先切哪刀得到的分块完全相同（§11 层面一，三处例外也在那里）。更准确的读法是：卡坐标 (pp, dp, cp, tp) 是一个四位数的门牌号，四刀是这个门牌号的四个数位——数位之间没有「先写哪一位」的时间概念。图里把 PP 放在第一刀有个真实的理由，但那不是时间，是求值：PP 是筛子、其余是除号，筛掉了，除号无意义——这只是「读这张图」的顺序，不是「切」的顺序。

但拆是躲不掉的第二步，因为处方跟着轴走、轴属于体（§03）：两个体的增长规律不同（权重体只随模型结构，激活体随 batch × seq）、旋钮不同（权重体超 → TP / PP / ZeRO；激活体超 → CP / MBS / 重计算）。合着看只能说「满了」，拆开才知道拧哪个。

就算不拆帐，时间轴也会替你拆

「状态 vs 流量」（§03）在监控曲线上有直接投影：显存占用一开始就高、全程平直——权重体问题，它在第一个 token 之前就已分配；随层数爬升、随 step 锯齿——激活体问题，它逐层堆积、每 step 生灭。两个体的生命周期差异大到曲线形状本身就能分体，不需要先拆帐。

结论：两个体不是可以绕开的实现细节，而是诊断树的第一个分叉。定位流程天然是「合进、分出」：症状层合着看（卡坐标 ＋ 容器总量 ＋ 时间线），归因层拆开走（哪个体 → 哪根轴 → 哪个并行维 → 哪个旋钮）。

08

卡作为容器：谁能减什么

全局只有两个被切的对象：权重体和激活体。四个并行维度是落在它们身上的四刀——两刀切权重，两刀切激活。卡是接住碎块的容器，容器满了就是 OOM。

调大它权重 · 梯度 · 优化器状态激活值为什么
TP全减减（开 SP 时）切的是权重体的 h 轴，参数量真的少了
PP全减减切的是权重体的 ℓ 轴，这张卡少背几层
CP不变减只切激活体的 s 轴，权重一份不少
DP不变不变只切全局 batch，单卡的 micro-batch 没变小
DP 那一行值得单独说

把 DP 从 2 调到 8，卡数从 128 涨到 512，容器里一点变化都没有——这是容器视角最反直觉、也最有用的一条。DP 增加的是吞吐和总卡数，不是单卡的余量。所以「显存不够就加卡」这句话，只有在加的是 TP 或 PP 时才成立；加 DP 是买吞吐，不是买余量。

例外是 ZeRO / FSDP：它们把优化器状态（乃至梯度、参数）沿 DP 域切开，这时 DP 才开始减容器里的东西。但那是给 DP 打的补丁，不是 DP 本身的性质。

09

通信：切口处插入的算子

并行切分之后，框架会在切口处往整网里插入通信原语。关键认知：通信算子对卡来说也是算子，也排在同一条流上占时间。

AllReduce（集合通信） N:1 → 1:N

域内每张卡都持有一份同 shape 的数据，做一次全局规约（通常是求和），结束后每张卡都拿到相同的完整结果。两个高频场景：DP 的梯度同步（每 step 一次）；TP 的层内激活值求和（每层两次，因为权重被切开后各卡算出的是部分和，必须加起来才等于原 matmul 的结果）。

Ring 实现下每卡的通信量约为 2(N−1)/N × S，S 是数据量——注意它不随卡数线性增长，这是 Ring 算法的核心价值。

All-to-All（集合通信） N:N 各不相同

每张卡把自己的数据按目标 rank 切成 N 份，各发各的、各收各的——本质是一次分布式转置，每张卡收到的内容都不同（这是它和 AllReduce 最大的区别）。

最典型的用途是 EP：token 被 router 判定该去哪个 expert，dispatch 一次 All-to-All 送过去，算完 combine 再一次送回来。所以一个 MoE 层前向就有两次，反向同样两次，是 EP 的主要开销来源。但它不为 EP 专有——Ulysses 语义的 CP 同样以 All-to-All 为核心原语（把 seq 维切分转成 head 维切分）。

P2P / Send-Recv（点对点，不是集合通信） 1:1

只有两张卡参与，一发一收。PP 专用：stage N 算完把边界激活发给 stage N+1，反向时梯度沿反方向传回。

勘误 E · "PP 通信量最小"要加限定

准确说是单次通信量最小（一个 [b, s, h] 激活张量，不是整份权重）。但通信次数是 micro-batch 数 × stage 边界数，micro-batch 开得多时总量并不小。"PP 可以跨机"成立的理由是单次通信量小、且能与计算 overlap，不是总量小。

AllReduce 与 SP 的关系：两处描述并不矛盾

这里有一个看起来打架、实则不冲突的点，值得写清楚：

  • Ring 实现下 AllReduce = ReduceScatter → AllGather（先规约散开，再聚齐）。
  • Megatron SP 的前向里，进入 TP 区用 AllGather（把 seq 切分的激活值聚成完整），离开 TP 区用 ReduceScatter（把部分和规约并沿 seq 重新切开）——顺序是反的。

两者不矛盾，因为站的位置不同：前者是拆解一次 AllReduce 的内部实现，后者是描述一层前后两个通信算子各用什么。SP 的实际效果是把原本一次完整 AllReduce 的两半拆到层的两端，中间那段激活值顺势保持 seq 切分状态。通信总量与纯 TP 相同，省下的是激活值显存。

解绑：切分维度并不决定通信原语

先承认一个表述问题

本文此前（包括 FIG 06 的交互按钮、FIG 12 的图例、以及各处「TP → AllReduce、PP → P2P、EP → All-to-All」的写法）把并行维度和通信原语讲成了一一对应。这是典型实现的对应，不是本质对应。§01 的基数表里写的 并行策略 → 原语 N:M 才是对的，正文与图没跟上。这一小节补齐。

真正决定原语的，是切口两侧的数学关系

并行的名字（TP / PP / DP / EP / CP）描述的是切哪一维；而通信原语由切开之后各卡手里的东西和完整结果之间差了什么决定。这是两件事：

切口性质各卡手里是什么需要的动作可选原语
切在求和 / 归约维部分和加起来AllReduce、ReduceScatter（+ 后续 AllGather）
切在拼接维完整张量的一片拼齐AllGather、Broadcast
切在归属维归属错位的数据重新分配All-to-All
只有前后依赖上一段的输出递给下一个P2P Send / Recv

所以链条是两层，不是一层：

   (名字)        (真正的约束)        (多选一)              (工程权衡)

后两步是多选一，不是唯一确定。这就是 N:M 的来源。

同一个并行维度，三种主流实现用三种完全不同的原语——P2P、All-to-All、AllGather 各占一种。如果「维度决定原语」成立，这种情况根本不该存在。

反过来同样成立：一个原语服务多个维度。All-to-All 既是 EP 的核心，也是 Ulysses CP 的核心；AllReduce 既服务 DP 也服务 TP，而这两者的相似之处仅在于「切的都是求和维」，与它们本身像不像毫无关系。所以在 profiling 里看到 All-to-All 就断定「这是 MoE」，是把 N:M 当成了 1:1。

那最初为什么会这么讲

因为用典型实现建立直觉最省力，而 Megatron-LM 的默认配置事实上就是那一套对应。作为入门脚手架没问题，但把脚手架讲成结构就越界了。这个越界在治理场景里有实际代价：一旦用户的性能问题来自非标准实现，按并行的名字反查原语会直接把定位方向带偏。

前面的图都是「选一个维度，高亮整组卡」。但真实的诊断场景往往是反过来的：你选中的是一张卡、或一张卡上的某个切分块——然后问：这个块的「兄弟」在哪？它们之间怎么通信？走的什么物理链路？

第二层 · 选中一个切分块 → 亮出它的「同源兄弟」

进到卡内部，能看到这张卡持有的具体分片（§08 容器）。选中其中一个——比如「第 3 层的 W_Q 权重分片 [H, H/TP]」——问题变成：这个分片的其他碎片在谁手里？

  • TP 分片的兄弟：同一 TP 组的其他卡上各有一片，合起来才是完整的 [H, H]。它们之间每层两次通信（AllReduce 或 AG+RS）。
  • DP 副本的兄弟：同一 DP 组的其他卡持有完全相同的分片（副本），step 末做一次梯度 AllReduce。
  • PP 没有兄弟：PP 切的是层号，不同 stage 持有的是不同的层，不存在「同一层的碎片分散在不同 stage 上」的情况。PP 方向的连线是激活值的传递，不是同一张量的聚合。
  • CP 的兄弟在激活体上：CP 只切激活（seq 维），权重不受影响——所以选中权重分片时 CP 没有兄弟；选中激活分片时，CP 组内的其他卡持有同一 token 序列的不同段。

NCCL / HCCL / RCCL 是同一层

三者的角色完全一样——都是集合通信库，封装 AllReduce / AllGather / ReduceScatter / All-to-All 等原语，只是分别对接不同厂商的硬件互联：

  • NCCL（NVIDIA Collective Communications Library）—— 对接 NVLink / NVSwitch / IB / RoCE
  • HCCL（Huawei Collective Communication Library）—— 对接 HCCS（机内）+ UB / RoCE（跨机）
  • RCCL（ROCm Communication Collectives Library）—— 对接 xGMI / IB

训练框架（Megatron / DeepSpeed / FSDP）从来不直接调用硬件互联，它们只调用集合通信库的 API（all_reduce(tensor, group)）。集合通信库负责决定这次 AllReduce 走哪条物理路、用什么算法（Ring / Tree / Mesh）。所以本文前面所有关于通信原语的讨论都不受硬件影响——AllReduce 在 NCCL 和 HCCL 上语义完全一样，只是底层走的线不同。

勘误 P · UB 是 UnifiedBus（互联总线），不是 Unified Buffer（主机侧共享 buffer）

上一版这里把两个同名缩写混成了一个。昇腾 DaVinci AI Core 片内确实有一块叫 Unified Buffer 的统一缓冲（AIV / vector 单元直接读写的片内 SRAM，与 L0A/L0B/L0C/L1 同级）——但那是卡内的东西，与本节讨论的物理互联无关。这里真正该出现的是灵衢 UnifiedBus（缩写也是 UB）：一种卡级互联总线 / 协议，把超节点（SuperPoD）内的全部 NPU、CPU 接成一张非阻塞全互联平面✅ 已核实-原文 arXiv:2506.12708 §3.2 / §3.3.3，属于硬件互联层，是 NVLink / HCCS / xGMI 的同侪——不在 HCCL 内部。两个 UB 一个在卡内、一个在机房里，隔了三级，此前的整块论述建立在错的那一个上，需要逐句纠正：

① 「UB 是 HCCL 在跨机场景下使用的通信加速机制」——错。UB 位于 HCCL 之下的硬件互联层，是 HCCL 可选的载体之一，不是 HCCL 内部的机制；它服务的场景也不是"跨机"，而是超节点内（scale-up）。
② 「核心思路是在主机侧开辟共享 buffer，把跨机通信汇聚后再经 RDMA 发出」——这段机制是虚构的。灵衢 UnifiedBus 提供的是卡到卡的内存语义直连（Load/Store 与 URMA 单边读写）🔍 第三方分析 公开二手手册对灵衢规范的整理，非官方原文逐字，走的恰恰是绕开主机内存中转的路径。
③ 「跨机时 HCCL 自动走 UB + RDMA 通道」——方向反了。UB 与 RDMA / RoCE 是互斥的两张平面，不是串联的一条通道：超节点内走 UB，跨出超节点边界才换挡到 RoCE（或 UBoE）。
④ 「诊断时要关注 UB 的 buffer 大小、RDMA 连接数」——这个旋钮不存在。真正该查的是这组卡有没有跨出超节点边界、平面接线是否一致（接错平面时链路层可以全 Up，但集合通信带宽会塌陷）。

正面重述一句话：UnifiedBus 把总线级的低时延内存语义从主板内延伸到了整个机房，扩大的是高带宽域的半径，不是给跨机通信加了一层缓存。原块里说对的那句精神依然成立，只是要把主语换回来：从应用层看不到这层选择——调的还是 hccl.all_reduce(tensor, group)，HCCL 拿到 group 后自己判断这组卡落在哪张平面上；UB 影响的是走哪条路、性能如何，不影响通信语义，也不改变可选原语集合。超节点这一档具体如何接入本文的参照系（口径假设、带宽单位、与 §07 / §11 的接口），见 §19；一手细节见仓库内 public/ub-reference/index.html（灵衢 UnifiedBus 参考手册）。

PP 链路不是兄弟关系

在联动显示中，TP 和 DP 的连线连接的是同一张量的不同碎片（TP）或同一张量的完全相同副本（DP），通信的目的是聚合或同步。PP 方向的连线则完全不同——它传的是「上一个 stage 的输出激活」交给「下一个 stage 的输入」，两端拿的根本不是同一层的东西。PP 的连线该画但不该和兄弟块混在一起——它是数据流方向上的依赖，不是切分产生的聚合需求。

反过来，DP 的 AllReduce 只在一个完整的前向 + 反向传播结束后做一次梯度同步，频率低很多，即使落在 RoCE 上也可以接受。这就是 FIG 12D 最底行"物理链路"那一层真正决定的事——不是"走不走网线"而是"带宽够不够用"。

编号：卡与 rank 不是一回事

物理上通常一张卡对应一个 rank，但一张卡同时持有多个 rank 编号。All-to-All 里说的"目标 rank"，指的是通信域内的编号，不是全局卡号。

rank 是"在某个通信域里的编号"，不是卡的身份证 卡 → rank 编号 1:N

严格定义：rank 是一个进程在某个通信域（communicator / process group）内的序号，范围 0…N−1。训练默认配置是一进程绑一卡，所以 global rank ↔ 卡确实是 1:1，日常混着说没问题。

混淆的根源正是基数：卡 → global_rank 是 1:1，但卡 → rank 编号总数是 1:N。前者让人以为「卡就是 rank」，后者才是实际情况——一张卡同时挂在多个通信域上，每个域给它一个不同的号。

但并行切分会同时建立好几个通信域，每个域各自从 0 开始重新编号。于是同一张卡会有一整组坐标：

global_rank = 21   ← 全局唯一，对应物理卡
  ├ tp_rank = 1    ← 在它的 TP 组（4 卡）里排第 1
  ├ ep_rank = 5    ← 在它的 EP 组（8 卡）里排第 5
  ├ pp_rank = 2    ← 它属于第 2 个 stage
  └ dp_rank = 0    ← 它是第 0 个整网副本

具体算一遍：32 卡、TP=4、EP=8、排布按 [ep][tp]（TP 在最内层，且此例简化为 PP=DP=1）。

global_rank = 21
  ep_rank = 21 // 4 = 5
  tp_rank = 21 %  4 = 1

卡 21 发出的第 3 份数据 → 给 ep_rank = 3 的那张卡
  它的 global_rank = 4 × 3 + 1 = 13

所以 All-to-All 里的"目标 rank"是 EP 域内 0–7 那个编号，"切成 N 份"的 N = 8（EP 组大小），不是 32。

rank 与图 / 权重体 / 激活体：rank 是地址

把 §03 的三样东西接到这里，rank 的作用就一句话：rank 元组是这张卡在五维索引空间里的地址，它唯一决定这张卡从每根轴上取走哪一片。

rank 是地址，不是身份

rank 本身不携带任何「这张卡与众不同」的含义，它纯粹是个索引。所有卡跑的是同一份程序，只是各自按自己的 rank 去取对应的那一片——这就是 SPMD（single program, multiple data）能够成立的全部条件：图不被切（§03）＋ rank 是纯地址（本节）。少了任何一条，各卡就得跑不同的代码。

还有一层双重身份值得留意：域内 rank 既是「取哪一片」的索引，也是「跟谁通信」的收发地址。框架保证这两者一致；order 字符串（§11）改变的只是这些逻辑组到物理卡的映射，不改变索引与通信对象的对应关系。

为什么必须说 rank 而不能说卡

因为通信原语永远发生在某一个通信域内部，它对全局卡号一无所知。集合通信库的 API 拿到的就是域内 rank。同一张卡在 TP 域里是 rank 1、在 EP 域里是 rank 5——说"发给卡 13"没有歧义但没有意义，底层要的是"发给本域的 rank 3"。

1:1 也不是铁律 ※ 随部署方式变

  • 一进程多卡（一个 rank 管多张卡，少见）
  • 一卡多进程（推理多实例、MPS）
  • CPU 进程也占 rank（某些混合部署）

另外还有个容易混的 local_rank——那是机内编号（0–7），用来 set_device 绑卡的，和通信域 rank 是两回事。

切分的先后顺序：四种不同的「先后」

「各种切分有没有先后顺序」这个问题，问的其实是四件不同的事。分开看，答案分别是：基本没有、有且是性能关键、有且形成依赖链、只有一个维度有。混在一起问，就会得到自相矛盾的答案。

数学 · 可交换性基本没有切的是相互正交的轴（§03 的五根轴），构成笛卡尔积，与应用顺序无关。三处例外见下

一 · 数学层面：基本可交换，但有三处例外

五根轴彼此独立，所以「先按 batch 分再按层分」与反过来得到的分组集合完全一样。抽象结构与应用顺序无关——这是「切分对称」这个直觉的合理内核。但有三处真实的依附与不可交换：

  • SP 必须依附 TP，不能独立存在。它切的正是 TP 切不到的那部分激活值（LayerNorm / Dropout 区域）的 seq 维，且严格复用 TP 的通信域。Megatron 里 --sequence-parallel 要求 tensor_model_parallel_size > 1。这印证了 §00 表 A 与 §03 的判断。
  • TP 与 EP 在 MoE 层是两套不同的分解。attention 走 TP×CP×DP×PP，expert 走 ETP×EP×EDP×PP，两套 mesh 形状不同，边界上必须做 token permutation + All-to-All-V 重排，算完再逆向送回。Megatron-Core 称之为 MoE Parallel Folding。「先按 expert 分再切权重」与「先切权重再分 expert」对应完全不同的通信拓扑——这里的先后是实质性的。
  • EP 与 CP 不能进同一个 RankGenerator。源码里有断言把二者隔开。注意别误读：这不是说 EP 和 CP 不能同时启用，而是它们分属两个不同的 RankGenerator 实例——attention 部分才有 seq 维（CP），expert 部分 token 已被打散，用 DP 取代 CP。

二 · rank 排布：order 字符串决定物理落位

§04 说过嵌套顺序是「TP 最内、DP/PP 最外」，但那是约定的说法。真正的机制在 Megatron 的 RankGenerator 里：

megatron/core/parallel_state.py
initialize_model_parallel(..., order: str = "tp-cp-ep-dp-pp")

# RankGenerator 用前缀积算 stride
prefix_product([tp, cp, ep, dp, pp]) → [1, tp, tp·cp, tp·cp·ep, ...]
                                        ↑
                        order 最左那个维度 stride = 1

global_rank = tp_rank + dp_rank·tp_size + pp_rank·tp_size·dp_size

最左 = stride 1 = 组内 global_rank 连续 = 落在同一台机内。这就是 TP 必须放最左的全部理由——它每层两次集合通信，频率最高，必须走机内高带宽互联；DP 每 step 才一次，放最右、成员跨机也无妨。

改 order 不改变抽象分组，只改变物理落位。同样是「谁和谁在一个 TP 组」，换个顺序字符串，这些通信就从机内挪到了跨机。

源码里一处真实的自相矛盾

initialize_model_parallel 的函数签名默认值是 order="tp-cp-ep-dp-pp"，但同一文件的 docstring 仍写着过时的 default=tp-dp-pp，并声称只支持 tp-dp-pp 和 tp-pp-dp。早期版本（支持 CP / EP 之前）确实是后者，加入 CP 和 EP 后签名更新了、注释没跟上。以签名为准。

有 MoE 时会建两个独立的 RankGenerator：一个给 attention（带 cp、ep=1），一个给 expert（带 ep、cp=1）。两者的 PP 组必须一致。这也让 §04 勘误 A 的说法需要更新——见下方勘误 M。

一个广泛流传的错误算法

估算 MoE 配置的最小卡数时，不能用 PP · TP · CP · EP · ETP 连乘——这会严重超配。正确的是：

最小卡数 = PP × max(TP·CP, EP·ETP)

因为 dense path 用 TP·CP mesh、MoE path 用 EP·ETP mesh，二者在每个 PP stage 内共享同一批卡（取 max，不相乘），只有 PP stage 之间才是相乘。NVIDIA 的调优文档专门把连乘式标为错误，并指出它出现在很多 README 和排期表里。

由此得到的五步决策顺序

  1. 先定 TP——受两个硬约束：head 数整除，且 TP ≤ 高带宽域卡数（传统平台典型 8；超节点平台上是 384，§19）。若此时单卡装得下，就停在 TP + DP，不引入 PP。
  2. 再定 PP——仅当 TP 已到机内上限仍 OOM 时引入。
  3. 长序列加 CP——经验法则：TP 随 KV head 数扩，CP 随序列长度扩。
  4. MoE 加 EP / ETP——EP 尽量留机内；ETP 通常设 1，避免 MLP GEMM 的 TP 通信开销。
  5. DP 最后自动定——它是剩余卡数，不是一个可选项。

实际配置评估：TP=2 · CP=1 · PP=4 · DP=16 · EP=8 → 128 卡

按上面五步倒推这份配置的设计逻辑，同时验证整除约束与物理落位。

这正是§09 部署原则的实例——把频率最高的通信（TP，每层 2 次）放在带宽最高的路径上（机内），把频率较低的通信（EP，仅 MoE 层）推到跨机。

总体判断：配置合理。CP=1 在标准序列长度下正确；TP=2 保守但安全（单卡显存够则不必加大）；PP=4 在模型规模需要时是必要的权衡；EP=8 在传统 8 卡机上必然跨机、是 EP 的已知代价，可通过通信 overlap 缓解；在灵衢超节点这类高带宽域里，EP=8 根本不跨出 UB 平面，这项代价不成立（§19）。唯一需要实测验证的是 PP 气泡率——MBS 偏小时 PP=4 的气泡可能成为吞吐瓶颈。

四 · 执行时序：只有 PP 有严格因果

这一层的完整展开在 §12，这里只补两条印证：

  • 各并行的通信按发生频率排序（TP 层内 → CP/SP 层内 → EP 的 MoE 层 → PP 的 stage 边界 → DP 的 step 末），恰好是 order 字符串从左到右的镜像。嵌套顺序、rank 排布、通信频率三者是同一件事的三种写法。
  • CP 的时序完全取决于实现：Ring Attention 的 KV 沿环轮转，CP 轴上有明确的循环时序（第 i 轮才拿到第 i 块 KV）；Ulysses 用两次 All-to-All 把「seq 切分」换成「head 切分」，轴上没有时序。这正是 §09 那条「维度不决定原语」的又一佐证。
与本文既有结论的关系

印证了：world_size = TP × CP × PP × DP（§04）、EP 不是独立乘数维（§04 勘误 A）、SP 与 TP 同域同大小（§00、§03）、维度与原语是 N:M（§09 解绑）、PP 负载不均不止「除不尽」（§06 勘误 D）、PP 是唯一有因果次序的维度（§12）。

需要更新的：见下方勘误 M。

勘误 M · EP 的机制说法需要按版本区分

§04 勘误 A 说 EP 是「对 DP×TP 平面的重新解释」。这在经典 EP（较早的 Megatron-Core）下成立，但在采用 MoE Parallel Folding 的新版里应更新为：attention 与 expert 各有一套独立的 RankGenerator 与并行 mesh，二者在同一 PP stage 上共享 GPU，靠 token 重排衔接。

结论方向不变——EP 仍然不是 world_size 公式里的第五个乘数——但机制描述从「重新分组」变成了「两套独立分解 + 中间重排」。而且这条约束本身随版本变动很大（经典 EP 要求 EP = DP·TP，ETP 模式要求 EP = DP，Folding 后完全解耦），引用时必须核对 Megatron-Core 版本号。

本节的可靠性边界

参数名、默认值与公式来自 Megatron-LM 源码与 NVIDIA 官方文档，属一手来源。但三点需要留意：其一，EP 相关约束在不同 Megatron-Core 版本间语义差异极大，务必核对版本；其二，「最左 = 机内」成立的前提是启动脚本把 rank 正确映射到物理卡，若 NUMA / 拓扑错配，TP 仍可能跨机。

运行时：单卡的空间与时间

一张卡本质上是一块 HBM + 一组计算单元 + 若干条执行流。它不认识"整网"，只认识两件事：显存里放着什么，和流上排着什么。

空间：HBM 里放了什么 卡 → HBM 1:1

占用项性质量级
权重静态，训练全程常驻bf16：2 字节 / 参数
梯度反向产生与权重同量级
优化器状态混合精度下常是大头Adam：fp32 master weight 4 + momentum 4 + variance 4 ≈ 12 字节 / 参数
激活值动态，前向逐层堆积、反向逐层释放≈ 层数 × 单层激活值量，随 batch × seq × hidden 增长
通信 buffer · workspace · 内存碎片随并行配置与算子实现变化常被低估

能不能单卡放下整网，取决于这五项之和——不是取决于整网有多少参数。算一遍 7B 全量训练：

权重 (bf16)      7B × 2  =  14 GB
梯度            7B × 2  =  14 GB
优化器状态       7B × 12 =  84 GB
                        ─────────
静态部分小计            ≈ 112 GB   ← 激活还没算

所以 64 GB 单卡训不动 7B，不是因为 14 GB 的权重放不下，而是优化器状态就是权重的 6 倍。激活值显存是按层累积的——前向走到第 k 层时前 k 层的激活值都得留着等反向用，这也是重计算（activation checkpointing）以层为粒度做的原因：丢掉中间激活，反向时重跑这一层的前向，用算力换显存。

时间：流上排了什么 流 → kernel 1:N

整网是并行的（有分支），但一张卡的执行流是串行的。框架把这张图按拓扑序摊平成一个 kernel 队列，卡上一次执行一个（或少数几个并发）算子：读输入张量 → 算 → 写输出张量 → 下一个。

所谓"整网在卡上运行"，物理真相就是一条几千到几万个 kernel 的执行序列被反复刷过去，中间穿插内存分配 / 释放。这是为什么 profiling 出来是一条时间线，而不是整网那样的一张图。

层在这条时间线上表现为周期性重复的波形——那段肉眼可见的重复 pattern 就是层。这也是性能分析的抓手：拿准一层的耗时乘以层数就是整网基线，某层异常凸起立刻可见。

而且一张卡上不止一条流 卡 → 流 1:N

至少是「计算流 + 通信流」双流：把 AllReduce 丢到独立流上，让它和后续算子的计算重叠，这就是 overlap。所以严格说，是 N 张卡 × 每卡若干条流，靠 event 做流间同步。

算子的两类瓶颈

  • 计算密集型（大 MatMul）：吃满矩阵计算单元，算力是瓶颈。
  • 访存密集型（LayerNorm、Add、激活函数、Softmax）：算得很快但反复读写 HBM，带宽是瓶颈，计算单元大量空转。

算子融合的价值就在这里——把连续的访存密集型算子合成一个 kernel，中间结果留在片上不落 HBM。

N 条时间线：卡与卡之间没有全局时钟 卡 → 时间线 1:1 线间 N:M

每张卡一条独立的执行流，各跑各的。它们之间唯一的耦合是通信算子：谁先到谁就等着，直到域内所有 rank 都到齐。所以"整网在跑"这件事，物理上是 N 条各自推进、被通信算子反复钉在一起的时间线。

维度时间线差异成因
TP几乎锁步，偏差以微秒计每层两次 AllReduce，且各卡算子完全对称（切的是权重，shape 一致）
DP同构但异步跑相同的整网、数据不同，中途互不干涉，直到 step 末一次梯度 AllReduce 才对齐；快慢来自变长序列、padding 比例
PP差异最大，阶梯状错开stage 0 跑 micro-batch 1 的前向时 stage 3 还在空转等激活；1F1B 下每个 stage 的 F/B 交错节奏都不同
EP节奏相同但负载不均router 把 token 分给各 expert，热门 expert 所在的卡多算好几倍；靠 capacity factor 与负载均衡 loss 压制
CP因果掩码天然不均持有靠后 seq 分片的 rank，attention 要看的历史更长；实现上用 zigzag / striped 分配把长短片段交叉配对
高频诊断陷阱

profiling 里看到某张卡的 AllReduce 耗时 40 ms，绝大多数情况不是链路慢，是这张卡先到了、在等别人。集合通信的耗时天然包含域内最慢者的等待。真正该看的是：

  • 通信耗时在各 rank 上不均——某几张特别短、其余特别长，说明短的那几张是慢的源头（它们晚到，几乎不用等）
  • 通信耗时普遍偏长且均匀——才更可能是带宽或拓扑问题

这个归因方向是反直觉的：等待时间长的卡是"受害者"，等待时间短的卡才是"嫌疑人"。工具如果只呈现单卡时间线，用户几乎必然会归错因；只有把多 rank 的时间轴叠在同一坐标上、并标出通信算子的进入 / 退出时刻，慢的那一张才会自己浮出来。

时间是第几维？

短答：时间不是那四个切分维之一，但 PP 已经是时间的空间化。

world_size = TP × CP × PP × DP 里的四个维度全是空间维——它们划分的是卡的集合，每张卡拿到一个四元坐标。时间不在其中。但这四个维度里，PP 是特殊的：

维度轴上有序吗表现
TP无序，完全对称tp_rank 0 和 3 在同一时刻做同样的事，锁步；交换编号不改变任何东西
DP无序，完全对称副本之间互不干涉，step 末才对齐
CP取决于实现Ring Attention：KV 沿环轮转，有循环时序；Ulysses：一次 All-to-All，无时序
PP严格有序、有方向对同一个 micro-batch，stage k 必须先于 k+1 —— 这就是时间

PP 的一切特征其实都是时间特征：气泡（纯时间产物——其他三个维度里根本没有「气泡」这个概念）、需要 micro-batch 去填（对时间的再细分）、通信是有方向的 P2P 而不是对称的 AllReduce、多 rank 时间线呈阶梯状。

pp_rank 本质是一个被空间化了的时间下标。这也是为什么它同时出现在 FIG 06（网格）和 FIG 15（时间线）里——它是唯一同时属于两边的轴。

配套可交互原型

PP 的两张脸 · 用 rank 看流水线——把 FIG 15 / 16 做成可动的：调 PP / micro-batch / 调度（1F1B ↔ GPipe），看斜线（一个 micro-batch 的因果链）、重叠（并行）、两角空白（气泡）怎么随配置变；再点任一 Stage，把折叠的 TP×DP×CP 张卡摊回来，逐格画出它的 PP 链。

那里顺手纠正了一个常见误解：1F1B 与 GPipe 的气泡占比完全相同（makespan 都是 2M+2(PP−1)），1F1B 省的是显存——峰值在飞 micro-batch 从 GA 降到 PP。本节上面那句「1F1B 调度的全部目的就是让稳态尽量长」应据此理解为显存约束下的调度，而非减少气泡。

不同 stage 是并列的，还是一个跑完再跑下一个？

都不是——是错开重叠。这个问题要分成两句话答，因为答案取决于问的是「同一个 micro-batch」还是「不同的 micro-batch」：

  • 对同一个 micro-batch：严格串行。它必须依次流过 stage 0 → 1 → 2，这是数据依赖强加的因果次序，无法并行。FIG 16 右图那条深色箭头链画的正是它——向右上走，每上一级都往后挪一格时间。
  • 对不同的 micro-batch：并行。micro-batch 1 在 stage 1 上算的同时，micro-batch 2 已经在 stage 0 上开工了。图上三行在横轴上互相重叠，重叠的部分就是这种并行。

所以「流水线」这个名字是准确的。类比装配线：一件产品必须依次经过每个工位（串行），但不同产品可以同时占着不同工位（并行）。PP 的全部效率来源，就是用后者去填前者留下的空。

阶段发生什么与气泡的关系
warmup 预热stage k 要等 k 个时间单位才拿到第一个 micro-batch，此前一直空转气泡的前半——图上左下角那片空白
steady 稳态所有 stage 同时都有活干，并行度最高无气泡。1F1B 调度的全部目的就是让这段尽量长
cooldown 排空最后几个 micro-batch 陆续走完，stage 0 先空下来气泡的后半——图上右上角那片空白
气泡占比 ≈ (PP−1) / GA

warmup 与 cooldown 合计约 PP−1 个时间单位，稳态约 GA 个，所以气泡占比大致是 (PP−1)/GA。这就是 §03 那条「GA ≥ PP」的量化版：GA 越大气泡越小。

但 GA 不能无限加——它受 GBS = MBS × GA × DP 约束，加 GA 要么抬高 GBS（影响收敛与学习率），要么压低 MBS（可能让单卡算不满）。这三者是一组联动的旋钮，不能只看其中一个。

那 stage 与 stage 之间到底是什么关系

一句话：stage 之间是「链」，不是「组」。TP 组、DP 组都是对称集合——组内成员可以互换编号而不改变任何东西；PP 是一条有向链，成员不可互换。这也是它用 P2P 而非集合通信的根本原因。展开看有七层：

关系维度stage 之间是什么关系
数据依赖单向链：stage k 的输出激活值就是 k+1 的输入；反向时梯度沿同一条链倒流。每个 stage 只有一个前驱、一个后继
通信只在相邻两个之间有 P2P。非相邻 stage 之间没有直接通信——stage 0 和 stage 3 不做任何集合操作（例外见下）
时间错开重叠。对同一 micro-batch 严格串行，对不同 micro-batch 并行
权重完全不同的层，零重叠。对比 DP（逐字节相同）与 TP（同一矩阵的不同分片），这是三种截然不同的关系（§10）
负载名义均分 L/PP 层，实际首尾偏重（§06 勘误 D）。关键是最慢的那个 stage 决定整条流水线的节拍——木桶效应
显存严重不对称，见下方专述

最容易被忽略的一层：靠前的 stage 显存压力更大

直觉上每个 stage 分同样多层、显存应该差不多。实际上在 1F1B 调度下，靠前的 stage 要同时压着更多在途 micro-batch 的激活值。

原因是因果次序：stage 0 前向完第 1 个 micro-batch 后不能立刻做它的反向——得等它一路走到最后一个 stage 再一路退回来。这段等待里 stage 0 已经又前向了好几个 micro-batch，而每一个的激活值都得留着。稳态下 stage k 手里压着约 PP − k 份：

stage 0     压 PP 份 micro-batch 的激活值   ← 显存压力最大
stage 1     压 PP−1 份
   ⋮
stage PP−1  压 1 份                          ← 最轻松

所以 PP 下的 OOM 几乎总是先发生在 stage 0，而它恰好还额外背着 embedding。首 stage 少分几层的非均匀切分，一半是为了算力均衡，另一半正是为了这个。

顺带说清 1F1B 的真正价值：朴素的 GPipe 调度是「先做完所有前向，再做所有反向」，那样每个 stage 都要压住 GA 份激活值。1F1B 把峰值从 GA 降到 PP——它让激活值显存不再随梯度累积步数增长。这才是 1F1B 相对 GPipe 的核心改进，压气泡反而是次要的。

「非相邻 stage 不通信」的一个例外

当 embedding 与 lm_head 共享权重（tied embedding，很常见）时，这份权重同时被首 stage 和末 stage 用到，它们的梯度必须相加。此时框架会额外建一个只含首尾两个 stage 的通信域做规约——这是 PP 链上唯一一处跨越非相邻 stage 的通信。不共享权重时则完全没有。

Rank 状态图：一张卡此刻持有什么

§12 把一张卡拆成两个正交视角：空间（HBM 里堆了什么）与时间（流上排了什么）。这一节补上第三个：状态——同样那五档东西，此刻各自归谁所有、是完整的还是一片、什么时候来、什么时候走。「rank 7 用了 72 GB」在诊断上几乎没有信息量；「这 72 GB 里优化器态占 19 GB、比这套配置应有的多 11 GB」才有。差别就在这一层。

这一节要回答的问题，和它不要回答的问题

要：这张卡此刻持有哪些权重 / 梯度 / 优化器状态 / 激活，它们分别对应模型的哪一段、区间是多少、处在生命周期的哪一相、占多少字节、正在被哪个通信原语搬。

常见误解：「ZeRO 把激活也切了」

✗ 错误直觉：ZeRO / FSDP 是省显存的机制，激活是显存大头，所以它应该也切激活。

✓ 正确机制：ZeRO 的三级与 FSDP 的分片策略，定义里都只有三样东西——参数、梯度、优化器状态。DeepSpeed 官方对三级的表述分别是「optimizer states … are partitioned across the processes」（stage 1）、「The reduced 16-bit gradients … are also partitioned」（stage 2）、「The 16-bit model parameters are partitioned across the processes」（stage 3）✅ 已核实-原文 deepspeed.ai/tutorials/zero；PyTorch FSDP 的 FULL_SHARD 一句话是「Parameters, gradients, and optimizer states are sharded.」✅ 已核实-原文 docs.pytorch.org/docs/stable/fsdp.html。激活不在其中。

DeepSpeed 确实另有一个切激活的开关，但它不属于 ZeRO 三级，而是挂在 activation checkpointing 配置下、默认关闭的 partition_activations：「Enables partition activation when used with model parallelism」✅ 已核实-原文 deepspeed.ai/docs/config-json §Activation Checkpointing。注意它的前提是已有模型并行——它切的是 TP 造成的那份重复激活，不是沿 DP 域切。所以正确说法是：激活的减少来自 TP+SP、CP、重计算、offload，不来自 ZeRO 的 DP 分片。

二 · ZeRO / FSDP 三级：DP 从「不减显存」变成「减显存」 级 → 被切的态 1:N

§08 那张容器表里 DP 那一行写的是「全不变」，并附了一句「例外是 ZeRO / FSDP」。这一节把那个例外展开——它是本文原来最大的一块留白（§20 二 · 第一行，本次据此填上），因为三级之间的差别不是程度差别，是状态形态的差别。

先把基线摆出来。§12 的口径是每参数 16 字节：

权重 W   bf16                    2 B
梯度 G   bf16                    2 B
优化器 O fp32 master 4 + m 4 + v 4  12 B
                              ──────
                                16 B / 参数     ← 每张 DP 卡各存一份完整的（DDP 语义）

DP=d 张卡，就是同一份东西存了 d 遍。ZeRO 做的事只有一句话：把这三样里的某几样，沿 DP 域切成 d 份，每卡只留自己那一份。

级别沿 DP 切谁单卡常驻（B/参数）新增通信权重在一步里的形态
基线（DDP / 无分布式优化器）都不切2 + 2 + 12 = 16梯度 AllReduce ×1全程完整
ZeRO-1（≈ Megatron 分布式优化器）优化器状态2 + 2 + 12/d梯度 ReduceScatter + 参数 AllGather全程完整
ZeRO-2（≈ FSDP SHARD_GRAD_OP）＋梯度2 + 2/d + 12/d同上全程完整
ZeRO-3（＝ FSDP FULL_SHARD）＋参数16/d ＋ AllGather 窗口前向 AllGather、反向再 AllGather、梯度 ReduceScatter只在用它的那一小段时间里完整

Megatron-Core 分布式优化器文档给了一张理论显存表（d = DP 数）✅ 已核实-原文 docs.nvidia.com/megatron-core … features/dist_optimizer.html。把它按上面的口径拆开，三行各自都能配平：

fp16 参数 · fp16 梯度   20 B → 4 + 16/d
   20 = W 2 + G 2 + O 16      （O = master 4 + m 4 + v 4 + fp32 梯度副本 4）
    4 = W 2 + G 2              ← 留在本地的

bf16 参数 · fp32 梯度   18 B → 6 + 12/d
   18 = W 2 + G 4 + O 12
    6 = W 2 + G 4
 12/d = O/d

fp32 参数 · fp32 梯度   16 B → 8 + 8/d
   16 = W 4 + G 4 + O 8       （fp32 训练不需要 master 副本，只剩 m、v）
    8 = W 4 + G 4

三行的「留在本地的部分」恰好都等于 W＋G，「被除以 d 的部分」恰好都等于 O。这就从官方数字这一侧独立验证了：Megatron 的分布式优化器切的正是、且仅是优化器状态——即 ZeRO-1 的语义。这也顺带验证了本文 §12 那套「16 B = 2＋2＋12」的拆法：换成 fp32 梯度就是 18、换成 fp16 全量就是 20，三种口径互相能推出来，不是凑的。

三 · 三级里真正的分水岭在 ZeRO-3：权重不再是常驻物 权重 → 完整态 1:N 次/步

前两级只改「存多少」，不改「什么时候在」——权重全程完整躺在 HBM 里，计算随时可以读。ZeRO-3 改的是后者，这是它和前两级的本质区别，也是把它画进 viewer 时唯一必须新增的一条时间线。PyTorch 官方对四种分片策略的措辞把这件事说得极准：

策略官方原文（节选）读法
FULL_SHARD 「this strategy unshards (via all-gather) before the forward, reshards after the forward, unshards before the backward computation, and reshards after the backward computation」 一步之内拼回来两次、丢掉两次
SHARD_GRAD_OP 「unshards before the forward, does not reshard them after the forward, and only reshards them after the backward computation」 拼一次、留到反向做完——拿驻留换掉一次 AllGather
NO_SHARD 「Parameters, gradients, and optimizer states are not sharded but instead replicated across ranks … For gradients, this strategy synchronizes them (via all-reduce)」 就是 DDP
HYBRID_SHARD 「Apply FULL_SHARD within a node, and replicate parameters across nodes」 机内切、机间复制——把昂贵的集合通信关在机内

✅ 已核实-原文 docs.pytorch.org/docs/stable/fsdp.html · ShardingStrategy

SHARD_GRAD_OP 的那句「does not reshard after the forward」是这张表最有信息量的一格：ZeRO-2 与 ZeRO-3 的差别，在实现上就是「前向做完要不要立刻丢掉」这一个布尔量。丢，省显存但反向要再拼一次；不丢，反向直接用但整个反向期间都占着完整参数。

推论：ZeRO-3 的显存账里必须有「AllGather 窗口」这一格，它常被漏掉

「参数被切成 1/d」很容易被读成「参数显存变成 1/d」。不对——计算的那一刻参数必须是完整的，所以卡上除了 2P/d 的常驻分片，还得随时腾得出一个分片单元的完整参数（FSDP 里就是一个 wrap 单元，通常一个 transformer block）。于是：

ZeRO-3 单卡权重显存 ≈ 2·P/d          （常驻分片）
                    + 2·P_unit        （AllGather 窗口，P_unit = 一个 wrap 单元的参数量）
                    + 预取深度 × 2·P_unit  （为了 overlap 通信与计算，通常预取下一单元）

这解释了一件实践上很反直觉的事：FSDP 的 wrap 粒度是一个显存 ↔ 通信的旋钮。包得太粗（整个模型一个单元）→ 窗口等于整份参数，等于没切；包得太细 → 窗口很小但 AllGather 次数暴涨、每次都太小打不满带宽。🔸 推断 窗口与预取的具体字节数取决于实现与 backward_prefetch 设置，本文只给结构，不给系数。

四 · 四类状态各自的生命周期 状态 → 相 1:N

§12 的「环形因果链」讲的是四档之间谁先谁后（权重 → 激活 → 梯度 → 优化器状态 → 新权重）。这里讲的是另一件事：每一档自己在一步之内经过哪几个相。两张图叠起来才是完整的一步。

状态相序列由什么驱动相变
权重（ZeRO-3） 分片 → AllGather → 完整 → 前向用毕丢弃 → AllGather → 完整 → 反向用毕丢弃 → 更新后的分片 进入 / 离开一个 wrap 单元的计算
权重（ZeRO-0/1/2）完整常驻 → 步末被就地更新只有优化器步一个相变
梯度 不存在 → 逐层生成 → 累积（GA 未走完时反复叠加） → ReduceScatter / AllReduce → 本卡那一片（已规约） → 清零 反向逐层推进；GA 走满；优化器步
优化器状态本地分片常驻 → 被读写更新 → 更新完只在步末那一下

只有梯度和激活是「会消失」的，另两档在非 ZeRO-3 下全程常驻。这一条直接决定了 viewer 上该给谁配时间轴：给常驻物配一条随时间起伏的曲线，画面在动、信息是零。

相位差：同一时刻，不同 stage 的卡不在同一相

§12 已经说过 N 条时间线之间没有全局时钟。叠上 PP 之后还要再进一层：1F1B 稳态里，stage 0 已经在做第 k+3 个微批的前向，stage 3 还在做第 k 个的反向。所以「此刻」这个词对整网无定义，只对「某张卡 + 某个微批」有定义。读一屏 Rank 状态图时，标题必须是「rank 37 · 微批 #7 · 反向中」，只写「rank 37」是读不出来的。

五 · 归属：shard 区间是框架里的一等数据结构，不是 UX 造出来的概念 参数 → rank N:M

「这张卡持有第 37 层 QKV 的哪一段」听起来像是为了做可视化才需要的说法。它不是——框架内部就是按这个结构组织的，而且给了它明确的名字。Megatron-Core 分布式优化器的原文：

Each grad buffer (padded to be an even multiple of DP-world-size) is conceptually
divided into DP-world-size contiguous regions, where each DP rank "owns" a
contiguous region. Ownership in this sense means DP rank is responsible for
reducing the relevant subset of grads, and updating the relevant subset of params.

✅ 已核实-原文 Megatron-LM megatron/core/optimizer/distrib_optimizer.py · _build_model_gbuf_param_range_map 文档串

同一处还定义了四种区间，它们是同一段数据在四个坐标系里的表示：

区间官方定义它回答的问题
gbuf_world「The param's range within the entire grad buffer (world index).」在整个梯度缓冲里的绝对位置
gbuf_world_in_bucket「The param's range within the relevant grad bucket's buffer.」在它所属那个通信桶里的位置
gbuf_local「The param's range within the DP rank's local view of the grad buffer.」在这张卡自己那一段里的位置
param「The param's range within itself (i.e., its shard).」相对参数自身的偏移，即「这是它的第几段」

「归属」在这里有一个精确定义：负责规约这一段梯度、并负责更新这一段参数。注意它不是「存着这一段的值」——ZeRO-1 下每张卡都还存着完整的权重副本，但只有一张卡负责更新其中某一段。存储与责任在这一层分开了。

FSDP 那一侧给出了同一件事的另一半，而且说得更狠：

An original parameter may have all, some, or none of its data present for a
given rank. In the none case, its data will be like a size-0 empty tensor.

对 viewer 的推论：rank ↔ 参数不是布尔关系，是区间关系

「rank 37 有没有第 36 层的 QKV.weight」这个问题，正确答案可以是「有其中的 [4096:6144]」，也可以是「一个字节都没有」。所以这条关系不能画成有 / 无两态的着色（那正是 §17 推论 5 说的编码类别错误），只能画成区间条：整条代表张量，高亮段代表本卡那一段。这也和 §07「归属边界」是同一个东西——ZeRO 只是把那条边界从「层」推到了「张量内部的字节区间」。

六 · 应有 vs 实有：让这一屏能诊断，而不只是能看 配置 → 应有量 1:1

前面五小节合起来给出一件很有用的东西：「这张卡应该持有多少」是可以先验算出来的——它只由配置决定（§11 的五步 ＋ 本节的 ZeRO 级别 ＋ §12 的字节口径），不需要跑起来。既然应有值可算，那么任何与实测的偏差都是信号。

档应有（由配置算）实有（由 runtime 报）差值意味着什么
权重2·P/(zero≥3 ? d : 1)allocator 分类统计偏大 → wrap 粒度过粗 / 预取过深；偏小 → 某些模块没被纳入分片

为什么「总量曲线」诊断不了，而这张对账表可以

总量是五档之和。五档里有两档是常驻的（不该变）、两档是周期性的（该在一步之内起伏）、一档是噪声。把它们加起来，等于把「不该变的变了」和「该变的变多了」这两种完全不同的故障压成同一条曲线。拆开之后，前者是一条水平线上的台阶，后者是波形幅度变化——形态就不一样，不需要阈值也能一眼看出。这与 §12「OOM 属空间问题、利用率低属时间问题」是同一种拆法的延伸：只有拆到「每一档各自应该是什么形态」，读数才带诊断力。

七 · 合成：Rank 状态图在这套参照系里的位置

把这一节接回全文：它不是新的一根轴，而是给 §07 的双链插了一级。原来的双链是「逻辑侧：整网 → 层 → 算子 → kernel」对「物理侧：集群 → 超节点 → 机柜 → node → 卡 → 计算单元」，两条链靠「卡」这一级咬合。现在中间多出一层：

逻辑侧      整网 → 层 → 算子 → 张量（参数 / 激活）
                                    │

                                    ↓
物理侧      集群 → 超节点 → 机柜 → node → 卡（rank）→ HBM 里的那几个字节区间

换句话说，「状态」是逻辑张量与物理字节之间那个一直被省略掉的中间层。§03 给了「能切的只有五样」，§07 给了「切到哪张卡」，§12 给了「卡上一共多少字节」——这一节回答的是剩下那半句：那些字节此刻分别是什么、归谁、处在哪一相。

这不是本文的抽象。Megatron-Core 把 TP 的每一个通信点都实现成一个 autograd 函数，而它们的官方文档串每一条都写成「前向做什么、反向做什么」的一对：

勘误 N：「列切要 AllGather 输入、行切要 ReduceScatter 输出」——只在开 SP 时成立

这条说法很常见，也很容易被当成 TP 的固有行为。按上表逐条对：

  • 不开 SP：列切线性层入口是 copy_to_tensor_model_parallel_region——前向不通信（输入本来就是各卡完整的一份），反向才 AllReduce；行切线性层出口是 reduce_from_tensor_model_parallel_region——前向 AllReduce，反向不通信。一层 TP 的前向只有一次 AllReduce。
  • 开 SP：入口换成 gather_from_sequence_parallel_region（前向 AG / 反向 RS），出口换成 reduce_scatter_to_sequence_parallel_region（前向 RS / 反向 AG）。这时才是「AllGather 进、ReduceScatter 出」。

所以准确的说法是：TP 的通信方向由「算子是列切还是行切」×「在前向还是反向」×「SP 开没开」三者共同决定，不是一个固定模式。这与 §04「SP 的原理：AllReduce 换成 ReduceScatter」是同一件事的两种说法——那里从通信量的角度讲，这里从 layout 的角度讲：AllReduce = ReduceScatter + AllGather，SP 做的是把这对拆开、让中间那段停在分片态上，顺带把激活也切了。🔍 第三方分析 「入口 f / 出口 g 分别对应列切与行切」这一对应关系出自 Megatron-LM 论文（Shoeybi et al., 2019）的经典结构，函数级证据见上表。

三 · 通信不是时间线上孤立的一根彩条：它和计算是绑定的 通信 ↔ 算子 1:1

两条独立证据说明「把通信单独摆在一条 timeline 上」这种呈现方式本身就丢了信息：

其一，通信被实现在 autograd 图里。上一小节那八个函数不是独立调用的库函数，是算子输入输出上的包装——它们在计算图里有位置。所以「这次 AllGather 属于哪个算子的哪个输入」在框架里是确定的，不是需要事后猜的。

其二，通信被设计成与计算重叠。Megatron-Core 的 tp_comm_overlap 让 Linear 层的执行与 TP 的 AllGather / ReduceScatter 重叠，命令行开关是 --tp-comm-overlap🔍 第三方分析 Megatron-Core model_parallel_config 与 NeMo/Megatron-Bridge 通信重叠文档。一旦重叠，「通信耗时 1.4 ms」这个数就不再等于「拖慢了 1.4 ms」——重叠之后真正该读的是「有没有被藏住」，而这只有把通信和它并行的那段计算画在一起才看得出来。

CP 那一侧给了同一件事最干净的例子。官方对 context parallel 的三句描述：

  • 「CP requires additional all-gather across GPUs to collect the full sequence of KV. Correspondingly, reduce-scatter should be applied to the activation gradients of KV in backward propagation.」——又是一对：前向 AG、反向 RS。
  • 「All modules except attention (e.g., Linear, LayerNorm, etc.) can work as usual without any changes, because they do not have inter-token operations.」——通信绑在哪个算子上是确定的：只有 attention。
  • 「The all-gather and reduce-scatter are transformed to point-to-point communications in ring topology under the hood.」——语义与实现是两层：语义上是 AG/RS，实现上跑成环形 P2P。

✅ 已核实-原文 Megatron-Core 用户指南 · Context Parallelism

第三句尤其值得记住：它印证了 §09 那条「训练框架不直接调用硬件互联」的分层——同一个语义原语在不同实现下可以是完全不同的物理通信模式。所以观测面上必须同时留出「语义原语」和「实际链路」两栏，把 Ring 实现的 AllGather 记成一堆 P2P，读者就再也拼不回「这是 CP 在取 KV」。

把两者混起来的代价是具体的：读者会以为可以用同一套原语去描述片上搬运（「这里做了一次 AllGather」），或者反过来以为跨卡通信也能靠调度隐藏掉。归属变不变，是这条界线的本质。片上存储层次的具体分级（各级缓冲的命名与容量）是厂商相关的实现细节，按 §20 的边界划在本文范围外。

压力测试：一张卡直接写另一张卡的显存，还算通信吗？——算
  1. 判据问的是归属，不是搬运机制。AIV 核把一批 token 写进对端 NPU 显存之后，那批 token 归对端的专家算、本卡不再是它的持有者——归属变了，所以是通信。判据一个字不用改。
  2. §07 已经预先答过，而且答得更根本：「往上没有更大的统一地址空间（peer 访问是搬运手段，框架的归属记账仍以卡为界）」。UB 直写就是一次 peer 访问。可寻址 ≠ 同一个持有者：UB 给了 A 一条能写到 B 显存的路，没有把 A、B 的地址空间合并成一个记账单位；§07 落点判据的三项（私有地址空间 / 通信端点 / 独立执行流）在卡这一级仍然三项全齐。
  3. 与「rank 内」那一行的差别恰恰是可检验的：rank 内的搬运只改驻留位置，前后都是同一个持有者；UB 直写改的是持有者。两者在硬件上都可以是「一次写」，在记账上完全不同。
  4. 证伪条件（这一条最要紧，别写成「肯定不会松」）：会动摇落点的不是「能不能直写」，而是归属记账的单位变没变。如果 UB 的统一寻址推到让一段张量的持有者是超节点而不是某张卡（池化内存里没有哪个 rank 是 holder），那么「私有地址空间」在卡这一级就不再成立，落点要上移，§07 整段论证需要重做。目前没有证据说它到了那一步——Megatron / HCCL 的组成员仍然是 global rank 的列表（§07 口径核对），归属记账仍以 rank 为界。所以正确的写法是：判据不动，但把「寻址粒度」列成这条判据的证伪条件，而不是一个无关的实现细节（见 §20）。

再往下分一层：跨 rank 那一侧其实有三种粒度

「rank 间 / rank 内」只是第一刀。跨 rank 这一侧再按被搬的两端是什么关系分开，四条边就各归其位——而且这三种粒度的诊断问法完全不同：

「形状变不变」这一列是这张表最有用的一列。它把四种边分成两类：改形状的（分块之间）问的是「这一片是哪一段」，不改形状的（副本之间 / 段与段之间 / rank 内）问的是「值对不对」「谁在等谁」「够不够快」。拿错问法，一条边的读数就全是噪声——比如盯着 PP 那条边问「本卡持有哪一片」，它压根没被切过。

五 · EP 是唯一一条按 token 路由的边 token → 专家 T:E

前面四维的通信边有一个共同点：它们连接的都是「同一个张量的不同分片」。TP 的两片是同一个矩阵的两半，PP 的两端是同一条激活流的前后段，CP 的各段是同一条序列的不同片，DP 的各份是同一份梯度的副本。EP 不是——

把这条链拆开，它需要四张互相关联的表才能记全，而另外四维只需要一张配置表：

#表由谁决定变不变
①token → 专家（top-k）router 的输出，即数据内容每个微批都在变
②专家 → rankEP 配置整个训练固定
③rank → rank 的 token 计数① ∘ ②每个微批都在变

第四张表最容易被忽略，但没有它整条链是断的：token 要先按目的专家重排成连续段才能发（否则 All-to-All 的 split 无法表达），算完还要按同一张表逆排回原位置，才能接上残差。Megatron-Core 的 dispatcher 层就是干这个的，并且给了三种实现✅ 已核实-原文 Megatron-Core 用户指南 · Mixture of Experts：

dispatcher官方描述什么时候用

注意第一种根本不搬 token——它把 token 全量收齐到每张卡上。所以「EP 就等于 All-to-All」是不成立的：EP 说的是专家怎么分布，dispatcher 才决定 token 怎么流动。这也是 §09 那条「切分维度不决定通信原语」的又一个实例，而且是最有说服力的一个。

不均衡的传导链：一条能一路走到 step 时长的因果链

router 输出偏斜（数据内容决定）
   → 某几个专家收到的 token 多
   → 那几个专家所在的 rank 收到的 token 多

   → 这些 rank 的专家 GEMM 计算量大

链条上每一环都是可观测的，而且越靠前的环越早暴露问题：等到看见 step 时长变长，中间五环已经全部发生过。这正是 §13「五类数据筛选器」里 MoE 那一类（Pmax / H / tok / balance）存在的理由——它们读的就是这条链的头两环。控制这条链的旋钮是容量因子（capacity factor，决定每个专家最多处理多少 token，超出部分丢弃或 padding）与均衡辅助损失，Megatron-Core 提供了微批级、序列级与全局级几种均衡策略✅ 已核实-原文 同上。这填上了§20 留白表里「MoE 的负载均衡：没展开 token drop」的一半——另一半（drop-less 实现的具体机制）仍然留白。

和 §17 推论 8 的关系：这一节没有推翻它，是给它补了正确的画法

§17 推论 8 判定「用动画精细呈现 token 选专家的过程」不可建，理由是基数错了——token → expert 一层就有上万条边，画出来信息量为零。那条结论仍然成立。本节新增的不是「把个体边画出来」，而是把这条链的四张表分别用适合各自基数的编码呈现：①④ 是万级，只能出统计（分布、熵、Top-k 集中度）；② 是配置级，几十条，画映射图；③ 是 EP × EP 的矩阵，几十到几千格，画热力图。同一条链上不同环节的基数差三个数量级，所以必须用三种不同的编码——这正是推论 8 想说的事，只是当时只说了它的否定面。

G 把算子开发层的两代工具并列表述 各家的算子开发工具通常是新旧两代并存，而非并列的两条技术路线。表述时要说明代际关系，否则读者会误以为需要在两者之间做选型。
H "优化器状态每参数约 12–16 字节" 给出构成：混合精度 Adam = fp32 master weight 4 + momentum 4 + variance 4 = 12 字节。狭义只算 momentum + variance 则为 8。区间的上下界来自口径差异，应说明口径。
I rank 换算例：32 卡 TP=4 EP=8 该例隐含 PP=DP=1。补上前提，否则 global = ep×4 + tp 的换算式不成立。
J "SP（序列并行）" 术语二义：Megatron SP（TP 的补丁，同域同大小）与 Ulysses / Ring 语义的序列并行（= CP）是两个不同维度。全文已统一，见 §00。
K 「TP → AllReduce、PP → P2P、EP → All-to-All」这类一一对应的写法（见 FIG 06 交互按钮、FIG 12 图例及 §09 各小节） 并行维度与通信原语是 N:M，不是 1:1。决定原语的是切口两侧的数学关系（部分和 / 分片待拼 / 归属待重排 / 前后依赖），不是并行的名字。§01 基数表原本写对了，正文与图未跟上，已在 §09 末补解绑小节并改写图例。
L 「All-to-All 专属于 EP」 错误。Ulysses 语义的 CP 同样以 All-to-All 为核心原语（把 seq 维切分转成 head 维切分）。且 CP 一个维度就有三种主流实现，分别用 P2P、All-to-All、AllGather——这是「维度不决定原语」最强的反证。
M EP 是「对 DP×TP 平面的重新解释」（§04 勘误 A 的说法） 在经典 EP（较早版本）下成立；采用 MoE Parallel Folding 的新版应更新为：attention 与 expert 各有一套独立的 RankGenerator 与并行 mesh，二者在同一 PP stage 上共享卡，靠 token 重排衔接。结论方向不变（EP 仍不是 world_size 的第五个乘数），但机制描述从「重新分组」变成「两套独立分解 + 中间重排」。该约束随版本变动极大（经典 EP 要求 EP = DP·TP，ETP 模式要求 EP = DP，Folding 后完全解耦），引用时必须核对版本号。详见 §11。
N 「TP 的列切要 AllGather 输入、行切要 ReduceScatter 输出」——一种很常见、也很容易被当成 TP 固有行为的写法 只在开 SP 时成立。不开 SP：列切层入口是 copy（前向不通信，反向才 AllReduce），行切层出口是 AllReduce（前向规约，反向不通信）——一层 TP 的前向只有一次 AllReduce。开 SP 后两处才分别换成 AllGather 与 ReduceScatter。方向由「列切/行切 × 前向/反向 × SP 开没开」三者共同决定，不是固定模式。函数级证据与完整对照见 §15 二、三。
O 「ZeRO / FSDP 是 DP 的变体，把存储也切了」（§04、§08、§09 的零散提法） 方向对，但把三级压成了一句话，掩盖了它们之间不是程度差别而是形态差别：ZeRO-1/2 只改「存多少」，权重全程完整常驻；ZeRO-3 / FSDP FULL_SHARD 改的是「什么时候在」——权重只在用它的那一小段时间里完整，一步之内拼回两次、丢弃两次，并因此多出一格常被漏算的 AllGather 窗口显存。另外「ZeRO 把激活也切了」是错的：三级的定义里只有参数、梯度、优化器状态。展开见 §14 二、三。
P "UB（Unified Buffer）不是独立通信原语，而是 HCCL 在跨机场景下使用的一种通信加速机制：在主机侧开辟一段共享 buffer，把多卡的跨机通信汇聚到这段 buffer 再经 RDMA 网络发出"（§09 两处 note、物理互联表"HCCL over UB（Unified Buffer）"一行、FIG 12C/12E 及其图注） 同名不同物，且位置放反。本文语境下的载体 UB 是灵衢 UnifiedBus——超节点内部的物理互联平面，与 NVLink / HCCS / xGMI 同属硬件互联层，不在 HCCL 内部；它是超节点内才用的平面，跨超节点时反而退场、换 RDMA / RoCE 平面接手，与原文"跨机才启用、经主机侧聚合"正好相反。"UB"这两个字母在昇腾语境里还指 AI Core 片上的统一缓冲区（Unified Buffer），属物理链最底的"片上 buffer"一级，与卡间互联无关——原文把这两者叠在了一起。唯一保留不变的结论：走哪张网不影响通信语义，训练框架仍只调用集合通信库的 API，不直接感知硬件互联。
Q "TP 必须机内"（散见于把通信频率最高的维度绑在"机内高带宽互联"上的各处表述：TP/SP 通信最频繁必须绑机内、TP ≤ 机内卡数、TP×EP 超过单机卡数即视为"跨机"代价） 不是被推翻，是被参数化。超节点把这条约束里"机"这个变量的实例从 8 卡换成了 384 卡：准确表述是「TP 必须在高带宽域内」，8 卡单机只是高带宽域在传统平台上的一个特例，与本文已有的TP ≤ 单节点高带宽域卡数、"超节点把高带宽域扩出单机"两处表述归一。判据、部署原则（把通信频率最高的维度放在带宽最高的路径上）与落点（仍是卡）一个字未变，变的只是这条约束里域的半径。
R （自检项）§00"平台差异只体现在互联名、集合通信库与算子栈的称呼上，不影响本文任何结论"——高带宽域从 8 卡扩到 384 卡，是否已经是这句话的反例？ 不是反例，与 F 同型：看似打架，实为两件不同的事。这句断言的是机制与语义不受平台影响——并行切分的落点、通信原语的选择逻辑、rank 排布的规则都没有变化；变化的只是"高带宽域"这个约束变量的取值（8→384）与档位名字（UB / RoCE 取代 NVLink / IB 之类具体叫法），这本就是这句话留给平台自行填的部分。真正会证伪这句话的是切分落点上移，或某条判据因换平台而成立/不成立——目前没有出现。
S "Rank 通信 ⊃ HCCL ⊃ UB：三层嵌套，不是三个场景"（§09 三层嵌套小节标题与配套表格） 包含关系写反了。UB 是硬件互联层的一种，HCCL 是架在硬件互联之上的软件集合通信库——二者是上下层，不是外层套内层；照此写法把 UB 换成 NVLink，"NCCL ⊃ NVLink" 立刻不成立。准确的三层是"Rank 通信 ⊃ HCCL ⊃ 载体（走哪张网）"，第三层取值是片内 / UB 平面 / RDMA 平面这一组分类，而不是某一个具体优化点；嵌套本身（逐层深入同一条路径）不变，变的只是最内层装的是什么。
T （自检项）UB 支持超节点内全局统一寻址，是否意味着并行切分的落点该从卡上移到超节点？ 不上移，但要分两层说，否则会把"可寻址"读成"同一个持有者"。硬件层：UnifiedBus 确实提供全局统一寻址与路由能力；软件层：具体实现出于时延考虑仍可能退回 rank 级别的静态预注册而不查全局地址表——两者是能力与实现的两个层次，不矛盾。判定切分落点的判据是归属（私有地址空间、通信端点、独立执行流三项全齐），不是可达性：不论走哪层实现，UB 扩大的都只是可达性，框架的归属记账仍以 rank 为界，落点不受影响。

核对过但确认无冲突的点

  • "硬件不认识层" 与 "层在时间线上是周期性波形" —— 不矛盾。前者说的是执行抽象（卡只见 kernel 队列），后者说的是可观测表征（重复的层子图产生重复波形）。
  • "TP 每层两次 AllReduce" —— 成立。Transformer 层前向中 attention 块一次、MLP 块一次；反向同样两次。
  • "一个 MoE 层前向两次 All-to-All" —— 成立（dispatch + combine），反向同样两次。
  • "激活值显存 ≈ 层数 × 单层激活值量" —— 作为一阶近似成立，未计入重计算与 SP 带来的折减。
  • "7B 单卡 64 GB 训不动" —— 成立，静态部分即约 112 GB。

对体验治理的推论

上面这套参照系的实用价值在于：它能把用户口中同一句抱怨，拆成责任方、周期、定位路径都不同的几类。

推论 1 · "算子不支持"其实是三类问题
  1. IR 层没这个算子 —— 需求是新增算子定义，周期最长
  2. 算子在，但缺这个 dtype / format / shape 组合的 kernel —— 落到某条分支上没实现，报错常表现为"不支持的输入"
  3. kernel 在，但精度对不上或性能不达标 —— 实现质量问题

三者响应路径、责任方、交付周期完全不同，但用户侧表征几乎相同（一条报错、一次跑不通）。在问题上报入口就把这三类区分开，比事后靠工程师逐个定位要省得多。

推论 2 · OOM 与利用率低是两条独立线索

"显存 OOM" 是空间侧的问题（五项占用之和 > HBM），"卡利用率低" 通常是时间侧的问题（气泡、通信没 overlap、访存密集型算子太碎）。两者在体验上的表征完全不同，定位路径也不一样，值得当作两条独立线索来拆——而不是笼统归入"性能问题"。

推论 3 · "每层都慢"与"某一层特别慢"是不同根因

前者通常是算子实现或并行配置问题，后者往往是某个特定结构（MoE 层的 All-to-All、长序列的 attention）。层这个粒度，恰好是这两类问题能被区分开的最小单位——性能报告如果不按层聚合，这条线索就丢了。

推论 4 · 维度与原语必须解耦成两个图层

如果 viewer 把「并行维度」和「连线样式」硬绑定，就是把一个 N:M 关系编码成了 1:1——用户看到 All-to-All 连线会默认「这是 MoE」，而它同样可能是 Ulysses CP。

正确做法是两者各自成层、可任意组合：维度决定哪些卡在一个组里，原语决定组内怎么连线。解耦后反而更简单，也更能暴露真实配置——当用户选了 CP 维度而连线显示的是 All-to-All 而非 P2P 环，他立刻就知道这套跑的是 Ulysses 而不是 Ring Attention。这个信息在绑定式设计里是丢失的。

推论 5 · viewer 的两个编码决策

rank 编号显示：只标 global rank，用户看 All-to-All 连线时得自己心算映射；按当前 axis 显示域内 rank，连线语义自洽但跨 axis 切换时会让人觉得"卡的编号变了"。较稳的做法是全局号常驻、域内号随 axis 高亮——编号不变，只是当前生效的那一维被点亮。

通信连线样式：三种原语的视觉语义本不相同——P2P 该画成有方向的链，AllReduce 该画成无方向的域内闭合，All-to-All 该画成多对多且各条载荷不同的流。若用同一种连线样式，用户很容易把"同步"和"转发"混为一谈。

多 rank 时间轴：只呈现单卡时间线会诱导用户把"等待"误判为"链路慢"。把多 rank 时间轴叠在同一坐标上并标出通信算子的进入 / 退出时刻，才能让真正的慢卡浮出来。

推论 6 · 三个设计判断，来自三个连环问题

「切分都落在哪」「切分有没有顺序、顺序保留吗」「诊断时能不能不分权重体激活体」——这三问连起来，其实是在替 viewer 做三个地基级的判断：

  1. 锚点唯一：界面的基本单元就是卡。并行的一切后果都落在卡上（§07），node / 机柜 / 超节点 / 集群只是卡的分组背景（用来画「谁和谁近」）——这四级只用来回答「这条边走哪张网」（UB / RoCE），不参与界面的基本单元；计算单元与 buffer 只在下钻单个 kernel 时才需要出现。不必让七级物理层级平权地占据界面。
  2. 切分是配置，不是事件。谁拿哪块在 run 开始时一次定死、全程冻结（§07），所以切分属于静态图层——画一次、常驻；需要动画的只有执行（时间线、通信脉冲）和 MoE 路由这一处例外。「静态的归属 ＋ 动态的执行」是天然的图层划分。
  3. 诊断流合进、分出。入口用三个不分体的柄（卡坐标、容器总量、shape 除号），第二步才拆成权重体 / 激活体去开处方（§07 末）——且显存曲线的形状能自动完成这一步分拣，界面可以代替用户判断。

五根轴（ℓ、h、e、b、s）在这套界面里不需要作为概念教给用户：它们只是卡的门牌号里的几位数字（§10），界面上表现为「这张卡管哪几层、哪段序列、哪批样本、矩阵的哪一条」——用户问的从来是后面这句话。

推论 8 · 元素数必须由配置界定，不能由数据量界定

以 MoE 路由为例。想「用动画精细呈现选专家的过程」是自然的念头，但它不可建——不是因为点太多，而是编码类别错了。§17 说关系画成连线；可 token → expert 的基数是 T:E 且 T ≫ E（§01：一层 T·K 条边，典型 16384 条），在这个基数下连线必须降级成密度／流量。画出一万多条边，观者能读到的信息量是零——真正的信号全是聚合量（哪个 expert 热、丢了多少 token、多少跨机），个体边只是统计现象的样本，不是被诊断的对象。

推论 7 · 讲解脚本：整网怎么切到卡、算子看到什么、通信从哪来

「一个整网怎么切分到卡、单卡算子看到什么维度、通信关系是什么」，有一套五句话讲完的叙述——骨架是定对象 → 发门牌 → 看除号 → 缝切口 → 验一致，每句对应本文一张图：

  1. 定对象（FIG 05）：整网里真正占地方、需要分的只有两样——权重（常驻的状态）和激活（流过的数据）。结构本身不切，每张卡都拿全份图纸。
  2. 发门牌（FIG 09）：world_size 张卡不是逐级分下去的，每张卡直接领一个四位门牌 (pp, dp, cp, tp)，四位数字回答四个问题：管哪一段层、喂哪一批样本、喂每条句子的哪一段、拿每个权重矩阵的哪一条。
  3. 看除号（FIG 10）：于是任何一张卡上的任何一个算子，看到的维度就是全局 shape 被除小的样子——权重 [H, 4H/TP]、激活 [B/DP, S/CP, H]、层数 L/PP。切分留在卡上的全部痕迹，就是 shape 上的几个除号。
  4. 缝切口（FIG 12）：凡是切开的地方都得缝，通信算子恰好插在切口上——TP 的切口在算子内部（每层两次，最频繁）、PP 的在层与层之间（stage 间 P2P 传激活）、CP 的在 attention 内部（token 要互相看）、DP 的在整个 step 之外（step 末一次梯度同步）。用哪种原语视实现而定（§09），讲故事只需要切口位置。
  5. 验一致（FIG 13）：故事自带检验——切口越深、缝得越勤，卡就必须靠得越近：TP 组永远机内、DP 组可以跨机。反过来，看一张卡的通信频谱，能反推它的门牌号。

MoE 模型补一句：门牌多一位 ep，切口在层内部的路由处——token 被 All-to-All 送到 expert 所在的卡，算完送回。

同样重要的是三条禁忌，各对应前文一个结论：别按物理层级逐级下钻讲（集群分给机、机分给卡——切分不经过机，两条链不逐级对齐，§07）；别讲成四道工序（先切谁再切谁——四刀是门牌的四个数位，同时成立，§07）；别从五个并行名词开讲（名词驱动会让人以为有五套机制——机制只有「分东西＋缝切口」一套，五个名词只是切的方向不同，§03）。

压缩到一句话：每张卡领一个门牌号，门牌决定它分到哪些碎片；shape 上的除号是切分的全部痕迹；切口在哪，通信就在哪；切得越深，缝得越勤。

推论 9 · 载体是第三个图层

推论 4 说维度和原语要解耦成两个图层：维度决定哪些卡在一个组里，原语决定组内怎么连线。这两层之外还有第三层——载体：决定这条线实际走哪张网、画多粗、什么颜色（片内 / 超节点内 UB / 跨超节点 RoCE，§19）。三层各自独立、可任意组合：同一条连线，维度层答它是 TP 还是 DP，原语层答它是环形还是树形，载体层答它落在 UB 还是 RoCE——三个问题互不蕴含，缺一层就会把三种不同性质的信息叠成一层，读错。

§09 末那张「兄弟块 + 通信连线 + 物理链路 = 三层叠加」的表其实已经在说这三层，只是把第三层叫「物理链路」、且只分粗细两档（粗线＝机内、细线＝跨机）。§19 做的事是把这个已有的第三层从两档扩成三档、从只能调粗细升级到可以着色：片内（通常不出卡，不必画）、超节点内 UB（一种颜色）、跨超节点 RoCE（另一种颜色，且更细）——分档轴不是机箱的铁皮在哪，是带宽域的边界在哪，换挡点在超节点而不在机（§07）。

回答两个具体问题

卡是容器吗？——是，而且不止它一个

是。卡是空间容器：装权重体分片与激活体分片，容量是显存，装满就是 OOM（§08 整节讲的就是它）。

但容器不止一种。流也是容器——它装 kernel，容量是时间。两者的区别很关键：

容器装什么容量装满会怎样
卡权重体 / 激活体的分片显存字节硬失败 —— OOM，程序崩
流kernel时间软退化 —— 排不下不会崩，只是变慢

这解释了 §17 推论 2 里那条判据的由来：OOM 与「利用率低」之所以是两条独立线索，正因为它们是两个不同容器满了。一个硬失败、一个软退化，连症状形态都不一样。

rank 是容器吗？——不是，它是地址

不是。容器有容量、装东西；rank 两样都没有。它是地址——§10 已经论证过：rank 元组唯一决定这张卡从每根轴上取走哪一片，但它本身不持有任何东西。

容易混淆是因为一种转喻：口语里说「这个 rank 上跑着什么」，实际说的是「这个 rank 所指向的那张卡上跑着什么」——用门牌号代指房子。日常无害，但一旦精确起来就必须分开，比如一张物理卡带两个 device 时（§00 表 D），「rank」和「卡」的数量就对不上了。

那什么才是装 rank 的容器？是通信域。它装的是成员（rank），但它的「容量」由配置决定而非物理限制，所以严格说它是逻辑分组而非真容器——本文把它归入结构一类。

可行性：每个对象都能具象化吗

能，但不能都画成同一种东西——这正是分五类的意义。逐类看：

三 · 换挡点在超节点边界，不在 node 边界

核心论断

超节点内部，node 边界不是降速点；换挡发生在超节点边界。UB 平面把 384 卡、48 个 node、16 个机柜连成一张非阻塞全互联网络；出了超节点才换到 RoCE，按前面两个口径换算，落差约四倍（196 GB/s vs. 50 GB/s）。

这条论断推翻的是老经验「TP 必须机内」——它默认高带宽域的半径等于一台 8 卡机。在灵衢超节点上这个半径被撑到 384 卡：TP 域可以横跨 48 个 node 而不换挡，§07 已经把这条老经验松弛成「TP 必须在高带宽域内」，本节把「高带宽域」这个变量坐实成「超节点」。

证据等级：「超节点内部不降速、换挡在超节点边界」这一定性判断是 ✅ 已核实-原文——论文两句原话直接支持：「inter-node bandwidth degradation is under 3% …, allowing CloudMatrix384 to function as a tightly-coupled, large-scale logical node」与「node's aggregate uplink bandwidth to the L2 fabric precisely matches its internal UB capacity, maintaining the non-blocking characteristic across the supernode」arXiv:2506.12708 §3.2 / §3.3.3。但论文没有给出跨超节点之后带宽 / 延迟具体掉到多少的量化对比数字——「落差约四倍」是拿 196 GB/s 与 50 GB/s 两个第三方口径相除得出的 🔸 推断，不是论文原文的对比实验。

适用边界：arXiv:2506.12708 的标题是「Serving Large Language Models on Huawei CloudMatrix384」——一篇推理论文，全部实验数据基于 DeepSeek-R1 推理场景。论文第 3.2–3.3 节的拓扑 / 硬件规格描述是训练推理通用的静态介绍，可以放心引用；但 FusedDispatch/Combine 的吞吐提升、PD 分离、KV cache 池化这类具体机制与数字，都是在推理管线里验证的——训练场景下 MoE 通信能否同样用 send-recv + AIV-Direct 替代 all-to-all，论文没有直接实验支持，本文只把它当作「架构能力上可推广，但未被这篇论文验证」的 🔸 推断，不写成训练侧的既有结论。

四 · 载体是通信五元组的第六元

§15 把一条通信边记全需要五样东西：源、张量、并行域、原语、宿；效果是这五元的函数——效果 = layout 变换 + 归属再分配。载体是第六元，答的是「这条边走哪张网」——1:1（一条边只落在唯一一张平面上），但这一元不进「效果」那个函数。

载体进的是「代价」，不是「效果」

换网不改前后态，只改从前态走到后态要多久。把 UB 换成 RoCE，哪张卡持有哪一段、形状是什么，逐字不变——所以：

效果 = f(源, 张量, 并行域, 原语, 宿)        ← 前五元的函数，不变
代价 ≥ g(载荷, 载体)                        ← 载体只进这一个，新增

把载体写进效果，等于说「走 RoCE 的 AllGather 拼出来的张量和走 UB 的不一样」——那是错的。这与 §09「UB 影响的是性能和带宽利用率，不影响通信语义」、§15「同一个语义原语在不同实现下可以是完全不同的物理通信模式」是同一件事：载体决定这条边多快到，不决定它到了之后是什么。

五 · 传输下界：字节 ÷ 平面带宽

知道了载荷（§15 第六行）与载体（本节），可以给出一个数：下界 = 载荷字节 ÷ 载体带宽。这是下界，不是耗时——它不含：

  • 拓扑跳数（同一张平面内部，卡到卡还要经过几级交换）；
  • 集合通信的算法系数（环形 AllReduce 要搬 2(N−1)/N 份数据，不是一份）；
  • 争用（同一张平面上还有别的边在抢带宽）；
  • 协议开销（RDMA / RoCE 的包头与握手）；
  • 与计算的重叠（overlap 掉的部分不体现在这条边的独立传输时间上）。

即便如此，这个下界仍有诊断价值：下界与实测之差，就是没被藏住的开销。一条边算出来「至少要 2 ms」，实测跑了 20 ms，差的 18 ms 不会凭空消失——它一定落在跳数、算法系数、争用、协议开销、串行等待里的某一项上，缩小范围本身就是诊断的一半。

宁缺毋误

下界公式对 TP / PP / DP 能给数，因为它们的载荷字节可以从并行配置直接算出（§15）。CP / EP 算不出就不给数：CP 的载荷取决于环上每一跳传的 KV 块大小，块大小又取决于 kv 头数与切法，不是一个能从配置直接读出的常量；EP 的载荷取决于 top-k 路由在运行时的实际去向，各条边不等。硬凑一个数就是把示意值当成算出来的——这条纪律与 viewer 的 commLoad9 一致：CP / EP 两项直接留空，不给示意字节。

六 · 口径假设与待确认

假设：超节点内不分板内 / 板间 / 机架间

假设：本节与 viewer 对超节点内部一律按 UB 同一档带宽计算，不区分板内（同 node）/ 板间（同机柜跨 node）/ 机架间（跨机柜同超节点）——三档当前全部取 196 GB/s。公开资料只给了「非阻塞全互联」这类定性描述和「inter-node bandwidth degradation < 3%」这一个笼统数字，没有按分层给出具体 GB/s 对比表；这是口径假设，不是事实。

三个待灵衢团队确认的问题：

  1. 寻址粒度——UB 是统一虚拟地址空间，还是 rank → 预注册 buffer 的静态映射？每条消息的数据路径上有没有一次地址翻译？这一问不是实现细节：只要归属记账仍以 rank 为单位，§07 落点判据与 §15 归属判据都不动；若答案是「持有者变成了超节点」，两条判据都要重做（见 §07 压力测试、§15 四）。
  2. 板内 / 板间 / 机架间的 UB 是否同一带宽档——上面已写成假设，真实是否降速待确认。
  3. 平面选择是否严格「超节点内 = UB / 跨超节点 = RoCE」，HCCL 在哪一层做这个选择？若不是严格按边界、而是按 group 大小或算法自适应，本节表二的「训练数据面走不走」这一列就不能只由物理坐标推出来。
对 viewer 的推论：载体是图层，不是新的并行轴

载体（片内 / UB / RoCE）不应该成为界面上与 TP / PP / DP / CP / EP 并列的第六个可选维度——它不是切分维度，一条边落在哪张平面上，是这组 rank 的物理坐标决定的，不是哪根轴决定的（§07：node / 机柜 / 超节点从不出现在切分函数里）。它该做的是图层 / 着色维度：同一张连线图，切换到载体图层时按 UB / RoCE 分色，回答的是「这条边多快到」，不是「这条边为什么存在」。这与 §17 推论 4 是同一条纪律的另一个实例——推论 4 说维度与原语要解耦成两个图层，本节说载体要解耦成第三个图层：维度决定哪些卡在一个组里，原语决定组内怎么连线，载体决定这条线画多粗、多快。三者各自成层、可任意组合，任何一层都不该被硬绑定到另一层上。

一 · 本文做过的简化

最需要说明的一处：「TP 切 h」其实合并了两根不同的轴

为了让「五根轴」这个框架成立，本文把 TP 的切分统一写成「切 h 隐藏维」。实际上 TP 在一层里切的是两个不同的东西：

  • Attention 部分按 head 切。W_Q/W_K/W_V 名义上是 [H, H]，实为 [H, num_heads × head_dim]，TP 沿 num_heads 切，每卡拿 num_heads/TP 个完整 head。
  • FFN 部分按中间维切。up 投影 [H, 4H] 按列切成 [H, 4H/TP]，down 投影 [4H, H] 按行切成 [4H/TP, H]——切的是那个 4H，不是 H。

这个合并掩盖了一个重要事实：TP 的上限来自 head 数。TP ≤ num_heads（用 GQA 时更严，受 num_kv_heads 约束），这正是 §11 里 num_attention_heads % TP == 0 那条约束的来源。把 h 当成一根连续可切的轴，会让人以为 TP 可以一直加大——实际上撞到 head 数就到顶了。

其二，全文默认均匀切分。§10 那组区间公式（ℓ ∈ [pp_rank·L/PP, …)）假设每根轴都均分。实际上 PP 常做非均匀切分（§06 勘误 D）、CP 用 zigzag 取不相邻的两段（§11）、MoE 的 expert 分配也可能不均。公式给的是骨架，不是实现。

其三，34·B·S·H 这个激活值系数有适用条件。它假设开启 SP、用 flash-attention 消掉了 [B,heads,S,S] 那两项、且不做重计算。三个条件任意一个变化，系数就不适用。文中所有显存估算都是量级估算，用于看趋势，不能拿去做容量规划。

其四，超节点内部一律按 UB 同一档计算，不区分板内 / 板间 / 机架间。为了让「载体」在 §09 / §15 里落成一个可判定的三值量（片内 / UB / RoCE），本文把超节点内三种物理距离——同 node、同机柜、跨机柜同超节点——都按同一带宽档处理（对齐 viewer 的 UB_TIERS9：三档 bps 全部取 196 GB/s）。这是为求可判定而做的简化，不是实测结论：板内 / 板间 / 机架间是否确实同带宽，公开资料未给出分层数据，待灵衢团队确认（见下表「超节点内的寻址与分档（灵衢 UB）」一行）。

三 · 有意划在范围外的

  • 推理。全文是训练视角。推理的并行语义相当不同——KV cache 是被冻结成状态的激活体（§03 已点到），prefill 与 decode 两阶段的瓶颈相反，还有 PD 分离、连续批处理这些训练里不存在的概念。本文的结论不要直接套到推理上。
  • 灵衢公开资料里的推理场景结论。UnifiedBus / CloudMatrix384 的公开资料（如 arXiv:2506.12708《Serving Large Language Models on Huawei CloudMatrix384》）本身是一篇推理服务论文，PD 分离、KV cache 跨超节点池化传输这些具体机制和吞吐数字，全部是在推理管线里跑出来的，该论文没有给出任何训练侧的实验数据；训练场景下的等价负载（梯度/参数同步、流水线激活值、checkpoint）它完全没有涉及。本文只借用其中训练/推理通用的拓扑与硬件规格（超节点规模、UB 平面的非阻塞全互联），不把推理侧的具体机制结论套到训练场景。
  • 故障恢复与弹性训练。checkpoint 的存取格式与并行配置强耦合，改并行度就要重切 checkpoint。这是工程上很重的一块，与本文的静态参照系正交。
  • 定量性能模型。§12 只给了「计算密集 / 访存密集」两类定性判据，没有 roofline、算术强度这类可以算的模型。要做性能预测得另起一套。
  • 具体框架的 API。除 §11 引用 Megatron 源码作为机制佐证外，全文不涉及任何框架的具体用法。

能：某个东西被谁切了、切完落在哪张卡、单卡手里剩多大、通信插在哪、为什么嵌套顺序是这样、某个术语在这套体系里的准确位置、这条通信走哪张网（片内 / UB / RoCE）、按这张网的带宽算出来的传输下界是多少（≥ 多少 ms）。
