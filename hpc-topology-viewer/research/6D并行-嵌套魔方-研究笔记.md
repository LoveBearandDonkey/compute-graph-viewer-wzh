# 6D 并行 · 嵌套魔方 —— 研究笔记

> 用途：沉淀「整网图（模型计算图）上看 rank 状态」这条线的资料与讨论。
> 持续更新，尤其是**图与显示形式**。本文件是 `public/vendor/rubik-cube/`（逻辑魔方 +
> 整网对象透镜 + 卡上切分 + CP 维）的设计依据之一。
>
> 研究语境（用户原话）：**整网 = 整网图（model-graphviz）= 模型计算图**。目标是在整网图上
> 看 **rank 的状态**。难点在**整网对象的并行切分** —— 核心是**把算子装进对应的 rank 里**；
> 有 CP/SP 时还涉及**上下文与序列**的切分。这些对象的输入/输出与 **Attention、MoE** 强相关，
> 也与 **HCCL 算子**强相关（并行切分点就是通信算子的插入点）。

---

## 0. 一句话

**并行策略决定了「逻辑计算图」如何展开成「物理 rank 上的算子实例图」；通信算子（HCCL）是
展开后各 rank 子图之间的缝合线。** 一个 rank 的内容 = 六维坐标 `[DP,PP,TP,EP,CP,SP]` 在
每个整网对象上各切一刀之后，落到这个交点上的那一份。

## 1. 资料来源 · 6D 并行架构图解

来源：用户提供的一张 6D 混合并行训练架构图（大模型 / MoE），OCR 原文与解析如下。
图本身是一张**逐级 Zoom-in 的嵌套图**，这个显示形式是本研究的关键参考。

### 1.1 六大并行维度

| 缩写 | 全称 | 切分对象 | 组内核心通信原语 | 典型物理映射 |
| --- | --- | --- | --- | --- |
| **DP** | Data Parallel 数据并行 | 数据 batch（整模型复制 D 份 replica） | 梯度 All-Reduce（或 ZeRO 的 RS + AG） | 跨节点，最外层 |
| **PP** | Pipeline Parallel 流水并行 | 模型**层数**（连续层切成 Stage 0..P-1） | P2P Send/Recv（传激活值） | 跨节点，Stage 边界量小 |
| **TP** | Tensor Parallel 张量并行 | 单层内的**权重矩阵**（按行/列切片） | All-Reduce（前向合输出、反向合梯度） | 节点内高带宽域（4/8 卡一组） |
| **EP** | Expert Parallel 专家并行 | MoE 的 **FFN 专家**（专家分布到不同卡） | All-to-All（Dispatch + Combine token） | 节点内或跨节点，通信极密集 |
| **CP** | Context Parallel 上下文并行 | **超长上下文**沿序列长度切块（chunk） | All-Gather / Reduce-Scatter（算 attn 前收齐全局 context） | 长序列训练 |
| **SP** | Sequence Parallel 序列并行 | LayerNorm/Dropout 等**非 TP 运算**沿 token 维切 | All-Gather / Reduce-Scatter（进出 TP 区转布局） | 与 TP 同组，省激活显存 |

记忆锚点：**DP 复制整模型 · PP 切层 · TP 切矩阵 · EP 切专家 · CP 切上下文 · SP 切序列杂项。**

### 1.2 原图的层次结构（Zoom-in 嵌套）—— 显示形式重点保留

```
第 1 层（宏观）：DP Replica 0 … DP Replica D-1        ← 横向并排的完整副本
  └─ 第 2 层：每个 Replica 内 PP Stage 0→1→2→3         ← 流水线箭头串联（Layers 分段）
       └─ 第 3 层：每个 Stage 内 TP Group（size=4）      ← 标注具体 GPU 编号，全局 rank 连续
            GPU 0-3 | 4-7 | 8-11 | 12-15 | 16-19 | …

Zoom-in A：单个 Pipeline Stage（如 Stage 1）
  ├─ TP Group 内 4 张 GPU（TP shard 0..3）+ Pipeline Send/Recv（activations）
  ├─ Attention Block（TP + CP + SP）
  │    Q/K/V 按 heads 切片 → Local Attention（Partial Heads）
  │    → CP All-Gather（Context）→ All-Reduce（Attention Output）[within TP]
  └─ FFN Block（TP + EP + SP，MoE）
       Column-Parallel Linear（W₁ shard）→ GELU
       → Dispatch（Token Router）→ All-to-All → Expert 0..E-1 [within EP]
       → Combine（All-to-All）→ Row-Parallel Linear（W₂ shard）
       → All-Reduce（FFN Output）[within TP]

Zoom-in B：CP 沿序列长度切
  CP Rank 0（seq chunk 0）| CP Rank 1（chunk 1）| … | CP Rank C-1
  → All-Gather / Reduce-Scatter（Context）→ 每卡拿到 Full Context 做 attention

Zoom-in C：SP 沿序列长度切
  SP Rank 0（tokens 0..k）| SP Rank 1 | … | SP Rank S-1
  → Reduce-Scatter / All-Gather（用于 dropout、layernorm 等）→ 需要时恢复 Full Sequence

侧边图例：DP(replicas) / PP(stages) / TP(within stage) / EP(experts) / CP(sequence) / SP(main stage)
底部注记：各并行维度可灵活组合、不必正交 —— 映射方式取决于硬件拓扑。
```

**三个可借鉴的显示形式**：
1. **嵌套 Zoom-in**：宏观（集群→replica→stage→TP组→GPU）与微观（单 stage 内算子级数据流）
   分层展示，同一实体在不同层级有不同粒度。
2. **通信原语作为「边」显式画出**：All-Reduce / All-Gather / Reduce-Scatter / All-to-All /
   Send-Recv 各自标注**作用的并行组**（within TP/CP/EP group）—— 这正是算子→rank 映射的关键。
3. **图例即维度语义**：每个维度一句话说清「切什么」，颜色/位置编码维度归属。

### 1.3 Attention Block 数据流（TP + CP + SP）

1. **进入前**：序列 token 已被 SP 切分（每卡持有部分 token 的 layernorm 结果）→ All-Gather 恢复 TP 布局。
2. **QKV 投影（TP）**：Q/K/V 权重按 **attention heads 切片**，每卡只算部分 heads。
3. **CP 介入**：每卡只持有部分上下文 chunk。算全局 attention 前，CP 组内 **All-Gather(Context)**
   收齐 K/V 全局上下文，再做 **Local Attention**。
4. **输出合并**：TP 组内 **All-Reduce(Attention Output)**。
5. **退出**：进入 SP 区时 Reduce-Scatter 回 token 切分布局。

### 1.4 FFN / MoE Block 数据流（TP + EP + SP）

1. **Column-Parallel Linear**（W₁ 列切）→ 各卡独立算 GELU。
2. **Token Router（Dispatch）** 决定每 token 去哪个专家。
3. **All-to-All（EP）**：token 跨卡派发到目标专家所在 rank —— MoE 最密集的通信。
4. **专家计算**：每卡持有 E/ep_size 个专家。
5. **Combine（All-to-All）**：结果按原顺序送回 token 原 rank。
6. **Row-Parallel Linear**（W₂ 行切）→ TP 组内 **All-Reduce(FFN Output)**。

### 1.5 通信原语 ↔ 并行组 ↔ HCCL 算子（核心表）

| 通信原语 | 出现位置 | 绑定并行组 | 对应 HCCL 算子（昇腾） |
| --- | --- | --- | --- |
| All-Reduce | Attention 输出合并 / FFN 输出合并 / DP 梯度同步 | TP 组 / DP 组 | `HcclAllReduce` |
| All-Gather | SP→TP 布局转换 / CP 收齐全局 context / ZeRO 参数聚合 | SP / CP / DP 组 | `HcclAllGather` |
| Reduce-Scatter | TP→SP 布局转换 / CP / ZeRO 梯度分片 | SP / CP / DP 组 | `HcclReduceScatter` |
| All-to-All | MoE Dispatch / Combine | EP 组 | `HcclAlltoAll` / `HcclAlltoAllV`（不均时用 V） |
| Send / Recv | PP Stage 间传激活/梯度 | PP 相邻 stage | `HcclSend` / `HcclRecv` |
| Broadcast | 初始化参数分发 | 各组 | `HcclBroadcast` |

要点：**同一 rank 同时隶属多个通信组**（一个 TP 组、一个 PP stage、一个 DP 组、可能还有
EP/CP/SP 组）。整网图上每个通信算子节点**必须标注它绑定的是哪个组**，否则无法判断它牵连哪些 rank。

### 1.6 rank 的多维坐标模型

```
rank = (dp_idx, pp_idx, tp_idx [, ep_idx, cp_idx, sp_idx])
全局 rank 号 = 按某种维度序（TP 最内层连续）展开的线性编号
```

- GPU 0-3 是一个 TP 组 → **TP 是最内层维度**（rank 连续、物理上同节点高带宽域）。
- **通信组 = 固定其它维度、只让一个维度变化的坐标切面**（GPU 5 的 TP 组 = {4,5,6,7}）。
- **算子装进 rank 的规则**：
  - 计算算子（MatMul/Attention/Expert…）：按所属层(→pp)、所属分片(→tp/ep)、
    所属序列块(→cp/sp) 落到哪些 rank，每 rank 上是一个 shard 不同、shape 不同的**算子实例**。
  - 通信算子（HCCL）：不属于单个 rank，而**属于一个通信组**，在组内所有 rank 上同时出现。
- **底注**：各维度不必正交，实际映射依赖硬件拓扑（TP/EP 优先放高带宽域）。

`public/vendor/rubik-cube/` 已经实现了本笔记的大部分「算子→rank」映射。逐条对应：

| FFN/MoE = TP+EP+SP | `dense_ffn`（TP ffn）· `experts`（EP）· `shared_expert`（TP，不按 EP 切）· `router`（复制） |

| 一 rank 同属多个通信组 | 信息卡「HCCL 通信域」段 + `commGroup(r, dim)`（固定其余坐标、含 cp） |
| 「把算子装进 rank」的读数 | 装载清单（侧栏）+ 装载板（3D）+ 卡上切分（方块沿切分维切开、亮本卡这片） |
| Zoom-in 单片看细节 | 放大细节视窗（左下角独立视口，点片切换 rank） |
| 「rank 内部」= 本卡的一串对象 | 细节窗页脚 `‹ 本卡对象 N/M ›`（换对象不换卡） |

**已实现的两条正交导航**（务必区分，见 README）：
- 换**片**（同一对象的别的分片）→ **换 rank**（片长在别的卡上）；
- 换**对象**（本卡持有的别的东西）→ **不换 rank**（这才是「在 rank 内部走」）。

## 3. 目标形态 · 嵌套六面魔方（用户设想，待研究）

用户设想的整体结构是一个**嵌套的、可 Zoom-in 的三维体系**，六个面各显示一个维度：

```
从 DP 切分 → 一个 Stage(PP) → TP 切分 / CP 切分 / SP 切分 / EP 切分
  → 在 EP 中再 Zoom-in 到一条条 CP / SP 的 sequence line
```

大三维体的**六面映射**（用户版）：DP 顶 · PP 前 · TP 背 · EP 底 · SP 左 · CP 右。

### 3.1 可行性判断（重要 · 已评估）

- **6 面各管一维是「助记图」，不是真坐标**：一个立方体只有 3 根轴（3 对面），对面共享同一根轴。
  - 顶 DP / 底 EP（同 Y 轴）—— **恰好成立**，因为 EP 本就折入 DP 轴；
  - 前 PP / 背 TP（同 Z 轴）—— PP 与 TP 无关，摆成对面是**假坐标**；
  - 左 SP / 右 CP（同 X 轴）—— 半相关（都切序列），也不是真轴。
  - 结论：可做成**悬浮的标注参考魔方（图例）**，但不能当卡的真实空间含义（违背「位置不说谎」）。
- **Zoom-in 嵌套穿梭 ~80% 已具备**：现有五形态本就是「转动魔方看不同切面」——
  DP平铺=看 DP 顶面 · PP流水=看 PP 前面 · TP切片=看 TP 背面 · EP聚簇=看 EP 底面。
  「缩放穿梭导览」= 把这些现成的 `形态+视角+对象+阶段` 切换**串成一条带旁白的下钻动画**。
- **真正的递归嵌套（cube-in-cube-in-cube）**：与当前「4000 rank 平铺一层」的模型是两套渲染。
  「宏观→微观」的**效果**可用形态+相机过渡达成，不必真的做几何嵌套。
- **CP 维已补齐**（本轮）：`rank = ((dp·PP+pp)·CP+cp)·TP+tp`，CP 与 TP 共轴、CP=1 逐位不变。
  于是穿梭到「左 SP / 右 CP」那一层**已经有空间可落**（此前 CP 不在模型里、是最后一层的空缺）。

### 3.2 下一步候选（按成本排）

1. **缩放穿梭导览**（中）：现成形态切换串成带旁白下钻，最像资料里的 Zoom-in 嵌套体验。
2. **6 面助记参考魔方**（低）：角落一个半透明标注魔方，六面标 DP/PP/TP/EP/SP/CP 各切什么。
3. **attn_core 双切完整表达**（中）：被 TP 与 CP 同时切的对象，在一片里再叠一维。
4. **SP 作为可读维**（中）：SP 现在复用 TP 组、只在 norm 区读数体现；若要在空间上区分需专门处理。

## 3B. 用什么图组织 rank：2D / 3D 与多种组织逻辑

> 语境（用户原话）：「每张卡领一个门牌号，如果要用图把它们组织起来，2D 好还是 3D 好？
> 怎么组织看得最清楚？还是会有多种组织逻辑？」这一节把答案定成可复用的选型框架。

### 3B.0 先纠正问题本身：门牌号放不进任何画布

rank 门牌 `(pp, dp, cp, tp)` 是 **4 根独立轴**（MoE 加 ep = 5 根）。屏幕只有 2 根空间轴，
3D 场景名义 3 根、实际第三根被透视与遮挡打折。**所以 2D / 3D 都是投影**——区别只是
「哪几根轴上屏幕、哪几根折叠、哪几根做选择器」。呼应参照系：*十九张图每一张都是同一个坐标系的
一个投影*。**「2D 还是 3D」是被误设的问题**；真正先回答的是「要让人看清哪件事」，答案一定，
投影基本就定了，维数只是副产品。

### 3B.1 选轴规则（几乎机械）

来自参照系既有结论——**有序维优先上轴，对称维可折叠或分面**：

| 维度 | 性质 | 处理 |
|---|---|---|
| **PP** | 有序（stage 0→1→2 有因果方向，本质是时间） | 几乎总占一根屏幕轴，**不折叠**（详见 3B.1a） |
| **TP / DP** | 完全对称（组内换编号不改变任何东西） | **看一个组 = 看全部** → 只画一个代表；4000 卡不必真铺（README「落地 128 卡」即此） |
| **CP** | 视实现而定 | Ring 有序该上轴；Ulysses 对称可折叠 |
| **EP** | 折入 DP 轴（非独立乘数维） | 不单占轴，随 DP 轴表达 + A2A 域高亮 |

规则一上，「画哪几根轴」不再是审美选择，而由配置本身决定。

#### 3B.1a PP 为什么不能折、是不是「一长条」

**为什么不能折**：折叠靠对称性——TP/DP 组内成员可互换编号、锁步做同样的事，所以「画一个代表 =
看全部」。PP 三条都对不上，无对称可用：① 每个 stage 装**不同的层**（首尾 stage 还多背
embedding/lm_head，即 net-sharding 实测「缺席数 5/8/8」，结构就不同）；② 是**有向链**不是对称集合，
同一 micro-batch 必须 stage k 先于 k+1，方向不能反；③ 任一时刻各 stage 处于流水线**不同位置**
（阶梯错开、气泡）。折叠 PP = 把顺序/方向/阶梯/气泡全扔掉，剩下的就不是流水线。

**是不是一长条**：老实几何确实是**一根有方向的线**，但两处要修正——① 它**短且必须带箭头**
（长度 = PP 值，典型 4/5/8；关键在方向不在长短）；② 每一站不是点，是那个 stage 的**整个
TP×DP×CP 截面折叠成一个盒子**，所以是「一串盒子，其余维折进每个盒里」，PP 是唯一保留不折的轴。

**而且招牌画法不是这根静态 strip**：PP 有两张脸（参照系 FIG 16 铰链）——**空间脸**（一串 stage 盒子，
答「哪 stage 装哪些层」，静态划分）与**时间脸**（PP 一轴 × 时间一轴的 2D 图，真正内容是那条斜向
右上的**对角线** = 一个 micro-batch 流过各 stage；不同 micro-batch 的对角线错开重叠 = 流水线并行，
两角空白 = 气泡）。只画空间脸就把 PP 最独特的东西（它本质是被空间化的时间）藏了。

### 3B.2 多种组织逻辑是分工，不是备选（每种回答不同问题）

| 想让人看清 | 组织逻辑 | 2D/3D | 落点 |
|---|---|---|---|
| 谁和谁一个通信组、门牌空间长什么样 | 坐标网格：有序维上轴、对称维折叠成代表、旋转看切面 | **3D** | 逻辑魔方 `rubik-cube` |
| 一张卡算子图相对整网**减了/增了**什么 | 共享布局 + 差分着色（small multiples），逐点对齐 | **2D** | `net-sharding` rank 卡 |
| 通信**什么时候**发生、PP 气泡 | rank × 时间 | **2D** | 参照系 FIG 15 / 16 |
| 一张卡显存装了什么、会不会 OOM | 容器：所有空间维折叠到一张卡 | 2D/2.5D | 参照系 FIG 11 |
| 哪根轴切哪个对象（切分因果） | 双链斜映射 | **2D** | 参照系 FIG 09 |

### 3B.3 3D 何时值回票价，何时是税

**值得用**（满足其一）：① 有 ≥3 根**必须同时看见**的轴，且交互是「旋转 / 导航」（魔方）；
② **嵌套 zoom-in** 本身是叙事（宏观→微观穿梭，见 §3.2 候选 1）。

**是税**：带来遮挡、用高度/体积表达数量（3D 柱高会因透视说谎）、或摆出**假第三轴**——
即 §3.1 的铁律 **位置不能说谎**。六面魔方只能当助记图，正因前 PP / 背 TP 摆成对面是假坐标；
魔方能成立恰恰因为它只用 3 根真轴（EP 折进 DP、CP 与 TP 共轴），没硬凑六面。

### 3B.4 一句话决策法

**先问要回答什么问题，再套投影规则：有序维上屏幕轴、对称维折叠成一个代表、被比较的维做
small multiples、剩下的塞进选择器。** 维数是这套规则的结果——只有剩下 ≥3 根必须同看的轴
且交互是旋转/下钻时才用 3D；否则 2D 更干净，且不会在数量上撒谎。
